## Improvements to make

Ordered by expected value. "Built" means the code is committed and unit-tested. "Measured" means a real-checkpoint number exists.

### A. Qwen prefill: read each expert once per window (built, not measured)

**Why it is first.** Chunk-major prefill rereads most experts. Measured today on the real checkpoint, 512-token prompt, 128-token chunks (`results/flashnext/20261114-184228-stage12-512-128-cold-prefill16-readstats`):

- 36,363 expert reads, of which 22,362 (61.5%) reread an expert an earlier chunk of the same layer had already read
- 111.7 GB read from SSD for one 512-token prompt; time to first token 45.8 s; prefill 11.2 tok/s
- the ring never fell back (0 of 240 calls)

The recorded route trace predicts the same: four 128-token chunks read 591 experts per layer against a union of 288.

**What exists.** `FLASHNEXT_PREFILL_ROUTE_UNION=1` with `FLASHNEXT_PREFILL_ORDER=layer` (`models/flashnext/layer_major.py`), mode `prefill-16gb-union` (`models/flashnext/prefill_16gb.py`, `settings/modes.py`), read counters behind `FLASHNEXT_PREFILL_READ_STATS=1` (`models/flashnext/prefill_reads.py`). Bit-identical to chunk-major on the tiny streaming model (`test_route_union.py`, `test_prefill_reads.py`).

**Why it is not measured.** The qualification harness loads the backend in process, without the session's memory watchdog. Layer order makes `models/flashnext/request_admission.py` require that watchdog, so the cell was refused: `RequestMemoryRefused: independent memory watchdog is unavailable or stale` (`results/flashnext/20261114-184423-stage12-512-128-cold-union`). Nothing ran.

**Next step.** Either measure through the supervised server (`--enable prefill-16gb-union --pool-gb 0`, then a 512-token request, comparing `prefill_reads` and the token digest with the chunk-major run above), or teach `veystrix/bench/qualification.py` to start the watchdog and memory controller the way `veystrix/session.py` does. Do not set `FLASHNEXT_REQUEST_ADMISSION=0` to get past the refusal: layer-major prefill caused two memory stops and one 3.25 GiB swap stop earlier this month, and that switch removes the check that was added because of them.

**Accept when:** the 128-token digest equals the chunk-major digest (`97a7af9e5a890b33…` for this cell), reads fall to roughly 40% of 36,363, time to first token falls accordingly, the floor stays above 3 GiB and swap is flat. Also record the ring capacity on a first and a later prefill: once a decode pool exists, a later prefill gets half the pool's slots, which can be fewer than the 384 the profile asks for.

### B. Qwen decode cannot reach 20 tok/s on this Mac with the current design (analysis done)

This is the falsification that item 2 of fable 5.2 asked for. It rests on recorded data, not new real runs.

- Time outside I/O is 93–110 ms per token in the recorded runs (fable 5.2 quotes 110 ms). 20 tok/s allows 50 ms in total. Even with no I/O at all the ceiling is about 10 tok/s.
- I/O: replaying the 768-token route trace through the pool with perfect foresight (Belady) needs 265 MB/token at 4 GB, 161 at 8 GB and 92.5 at 16 GB. At the measured 2.79 GB/s that is 95, 58 and 33 ms. The cost-aware policy in the tree needs 425, 291 and 159 MB/token.
- Native MTP did not help on either model (morning runs). Two conversations share only 6.3% of their experts at the same layer, so co-stepping requests cannot share reads on Qwen.

Evidence: `results/flashnext/20261114-132001-pool-policy-trace-manual`, `results/flashnext/20261114-132303-route-overlap-manual`, tools `bench_pool_policy_trace.py` and `bench_route_overlap.py`.

**What is still worth doing.** The gap between the cost-aware policy and the optimum is 1.6× at 4 GB, so a better eviction or prefetch policy can still buy I/O time. A token shares 40.8% of its experts with the previous token, and the 32 most used experts per layer cover 47% of routings, so a pinned popular set is the obvious candidate. The paired runs for Stage 3 (cost-aware against LRU, and `--resident-experts 0` against `8` in the qualification harness) have not been run.

**Owner decision needed.** The 20 tok/s gate for Qwen on 16 GB should be restated or dropped. Nothing found today suggests it is reachable without a different checkpoint or more memory.

### D. Nemotron numerical drift (closed; two small follow-ups)

Item 3 of fable 5.2 is answered. `models/nemotron35/trace_real.py` compares the streamed engine with stock mlx-lm layer by layer on the real checkpoint.

- With one-token steps the engine equals stock bit for bit: all 52 layers, every recurrent state, and the logits, over a 192-token prompt and three decode steps (`results/nemotron35/20261114-183740-drift-trace-chunk1-vs-stock-chunk1-192`).
- With multi-token prefill chunks and identical chunk edges on both sides, the only operation that differs is the routed-expert projection, first at MoE layer 1. Mamba, attention, RMSNorm, gating, shared experts and cached state are identical (`results/nemotron35/20261114-182426-drift-trace-bf16`).
- The cause is MLX choosing a different kernel by row count. A quantized matmul over several rows rounds about one BF16 step differently from the same rows computed one at a time. Stock `SwitchMLP` does this too once a call holds 64 routes.
- Stock disagrees with itself by the same amount. Stock token by token against stock in 128-token chunks differs by 0.17–0.34 in the logits (`…183845-drift-trace-chunk1-vs-stock-chunk128`). The engine against stock differs by 0.19–0.41. Greedy tokens agreed in every run. The 1.129 figure in fable 5.2 is this noise.
- INT8 KV: attention outputs differ from BF16 by at most 0.75 on a range of 848 per layer, and the logit difference (0.23–0.40) is no larger than the chunking noise in this probe (`…183345-drift-trace-int8kv-exact-rows-chunk128-ref-rows8`). That probe is 192 tokens; a long-context budget is still undeclared.

Consequence: the continuation digest changes when chunk edges change (for example when the prefix store is on or off). That is a property of the MLX kernels, not an engine fault, and it cannot be removed by fixing one layer.

`VEYSTRIX_NEMOTRON_EXACT_ROWS=1` (default off) makes the routed experts use the per-row kernel. With it the engine equals stock exactly at 16-token chunks. It does not make results independent of chunk edges, because the shared experts and the Mamba and attention projections also change kernel with row count. Keep it as a diagnostic.

Follow-ups: (1) the prefix-cache compatibility record does not include `VEYSTRIX_NEMOTRON_GATHER` or `VEYSTRIX_NEMOTRON_EXACT_ROWS`, so a snapshot written under one kernel can be restored under another; add them if either flag is ever used in production. (2) `GATHER_MAX_EXPERTS = 24` silently sends larger chunks down the per-expert path, which is why enabling the gather kernel appeared not to help; the cap should be reported in telemetry.

### E. Decode-first scheduling (built, not measured)

`VEYSTRIX_CONTINUOUS_BATCHING=1` and `veystrix/bench/concurrency.py` exist. Not run on a real checkpoint: overhead at one conversation against the 3% budget, and throughput and inter-token tails at two and four.

Known limits to fix or accept:

- Production admission needs more than 4 GiB available beyond the request's need, so on this Mac a second conversation gets a 503. The benchmark has `--ignore-admission` for measurement only.
- `decode_many` is not transactional. If a grouped pass raises mid-layer, every member of the group is unusable and the server drops their forks.
- `_run_decode_group` calls `should_cancel` inside the group's try block, so one client's disconnect check can fail the group.
- Flash-Next layer-local expert reuse across requests is ruled out by the 6.3% overlap (item B). Resumable speculative rounds were not built because MTP gave no gain.

### F. Harness and test hygiene

- `patch_rmsnorm.apply()` replaces `Qwen4ExpRMSNorm.__call__` for the whole process and several test modules never undo it. It made four route-union tests vacuous until the fixture pinned its own convention. Tests that install the patch should restore it.
- `veystrix/bench/qualification.py` cannot run any layer-order prefill (item A).
- The matrix runner's zero swap tolerance (see the rules section).
