# Handover, 15 November 2026 (night of 14–15 November)

This continues [the 14 November handover](handoff-2026-11-14.md). The owner asked three things: find out why Nemotron uses about 15% of the GPU while it decodes and fix it, complete the open items of that handover, and put the result into the installed app. This page says what was measured, what changed, what was tried and rejected, and what is still open. The rules for real-checkpoint runs in the 14 November page still apply unchanged.

## Why Nemotron leaves the GPU idle

The GPU is waiting for the SSD. This is a memory limit of the 16 GB Mac, and no software change in this session removes it.

- The checkpoint has 23 MoE layers of 128 experts. Each expert is 5.61 MB, so the routed experts are 16.52 GB and the dense core is 1.25 GB. A token uses 6 experts per layer: 138 experts, 775 MB.
- Decode of one token on the real checkpoint (512-token prompt, 128 output tokens, BF16 KV, no pool, 7.05–7.96 tok/s) takes 125–142 ms. About 41 ms of that is GPU work. The other 78–92 ms is fetching experts and waiting for them.
- 128 decoded tokens touched 2,349 of the 2,944 experts (13.2 GB). A least-recently-used cache replayed over that route trace hits 47% at 2 GiB, 74% at 6 GiB, 84% at 8 GiB and 92% at 10 GiB. A token shares 33.5% of its experts with the previous token.
- On this Mac the file cache has room for about half the experts, so each token still reads 110–250 MB from the SSD (measured 178–233 MB physical). The SSD's parallel read rate measured about 3.3 GB/s, which makes 35–75 ms per token.

Qwen looks different in Activity Monitor because its GPU share of a token is much larger (93–110 ms per token outside I/O, item B of the 14 November page), not because its expert reads are cheaper.

The only lever that changes the picture is more memory for the file cache: a Mac with 32 GB holds every expert, and the same engine would then be bound by the 41 ms of GPU work. That is about 24 tok/s by arithmetic (1000 / 41); it has not been measured on such a machine. On 16 GB the useful work is to waste less of the memory that exists, which is what the changes below do.

Evidence: `results/nemotron35/20261114-231253-gpu-util-baseline-pool0`, `…233438-gpu-util-streamed-pool0-512-128-r2`, `…234029-applike-streamed-baseline`; the owner's usage log (766 Nemotron requests, contexts of 14–31K tokens, decode 5.2–6.2 tok/s, 3.2–3.8 tok/s after prefills of 10–17K new tokens).

## Tried and rejected (kept behind flags, default off)

- **Memory-mapped expert pack** (`VEYSTRIX_NEMOTRON_EXPERT_MAP=auto|1`, pack built by `python -m models.shared.pack_experts nemotron35 <checkpoint>` in 17 s, 16.6 GB). Experts are used in place from a 64 KiB-aligned copy of the checkpoint, so nothing is copied and the kernel's file cache is the only cache. Bit-identical, 8.0 tok/s against 7.8–8.0, physical reads 112 MB/token. Rejected because the GPU's first touch of each view costs about 0.17 ms (21 ms per token), macOS compressed 6–31 GiB during 30 s runs, and holding every view pinned memory until the floor crossed 3 GiB. `madvise(WILLNEED)` blocks and costs 0.2 ms per call. The pack is needed at all because checkpoint tensors sit 2 bytes off a 4-byte boundary, and MLX returns wrong results from some operations (`array_equal`, `sum`, `take`) on views at such addresses.
- **Zero-copy import of streamed reads** (`VEYSTRIX_NEMOTRON_EXPERT_ZERO_COPY=1`): same digest, 6.3–6.7 tok/s against 7.1–7.4.
- **Decode overlap** (`VEYSTRIX_NEMOTRON_DECODE_OVERLAP=1`): 6.19 tok/s, no gain.
- **Read-ahead of the mapped pack** (`VEYSTRIX_NEMOTRON_MAP_READ_AHEAD`): no gain.
- **A larger pool**: slower at every size tried, as the table above shows. A pool takes memory from the file cache and then holds fewer experts than the file cache did.

Evidence: `results/nemotron35/20261114-2315*` to `…2334*` (`gpu-util-mapped-*`, `gpu-util-cold-probe`, `expert-pack-build`), `…234457-applike-streamed-overlap`, `…234959-applike-streamed-pool0-zerocopy`.

## Known and not changed

- **Staging never evicts a wrong prediction.** A staged expert that the router then does not pick stays in the 384 MB staging area, so the area fills with misses and the next-layer prefetch is mostly dead after a few tokens. It still acts as a small cache (about 19% of fetches at pool 0). Evicting unused predictions and measuring prefetch again is the next Nemotron decode experiment worth a guarded run.
- The 20 tok/s gate stays open on both models. For Nemotron on 16 GB the floor is the I/O above; an owner decision is needed, as for Qwen (item B).
