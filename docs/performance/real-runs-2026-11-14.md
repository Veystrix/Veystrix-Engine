# Real-checkpoint runs, 14 November 2026

Owner-approved measurements on the 16 GB fanless M4 MacBook Air, on AC power
with Low Power Mode off. One model at a time. Every run went through
`scripts/flashnext/real_run_guard.py`, which samples the machine once a second
from outside the benchmark and stops the run when

- available memory (free plus inactive pages) stays under 3 GiB for 3 s,
- swap in use rises more than 512 MiB above its value at launch,
- the compressor's floor rises in four consecutive 30 s windows, or it stays
  more than 4 GiB above launch for 20 s,
- OS thermal pressure is at level 2 or higher for 15 s,
- the machine leaves AC power, enters Low Power Mode, or the battery is under 25%.

Swap in use was 1,232 to 1,264 MiB before every run and never rose. The other
applications open on the machine left about 9.4 GiB available at launch; that
figure, not the engine, decided which configurations could run inside the
3 GiB floor.

All Flash-Next arms are greedy and are compared by the SHA-256 of their token
IDs. Rates are engine decode tokens per second, median of the arms.

## Flash-Next (Qwen 3.8 Flash-Next, MLX 4-bit, MTP head)

### What a token costs

| Quantity | Measured |
|---|---|
| Experts routed per token | 480 (48 layers x 10) |
| Expert bytes per token with no cache hit | 1,253 MB |
| SSD throughput during decode | 2.5 to 3.0 GB/s |
| Non-I/O time per token, plain decode | 93 ms (pool path) to 122 ms (buffered path) |

Plain decoding with a perfect expert cache would therefore reach 8 to
11 tok/s. With no cache it would reach about 1.9 tok/s. Everything measured
below lies between those two.

### Which configurations fit the 3 GiB floor

| Configuration | Decode tok/s | MB read per token | Available floor | Outcome |
|---|---|---|---|---|
| Legacy policy, no pool, 8 pinned experts per layer, 23-token prompt | 3.22 | 477 | 3.03 to 3.12 GiB | ran |
| Same, 103-token prompt | - | - | 2.74 GiB | guard stop |
| Legacy policy, no pool, no pinned experts, 103-token prompt | 2.58 | 780 | 3.50 GiB | ran |
| Default elastic planner (2 GiB pool) | - | - | 2.62 GiB | guard stop at 11 s |
| Elastic planner, pool capped at 1 GiB | 1.91 | 1,253 | 3.11 GiB | ran, no cache hits |

The legacy policy reads through the OS file cache, which then serves as the
expert cache and still counts as available memory. A 1 GiB pool holds about
411 expert records, fewer than one token routes, so least-recently-used
eviction never produces a hit; the planner also drops the pinned experts when
a pool is on. The 2 GiB pool the planner picks by default did not fit beside
the other applications.

The comparisons below use the legacy policy with no pool and no pinned
experts, the realistic 103-token prompt (a system line plus a request for an
explanation and a Python B-tree), and
`FLASHNEXT_PREFILL_CACHE_LIMIT_MB=512`.

### Stage 0: telemetry overhead

Seven reversed pairs of 64 tokens, telemetry off against timing mode
(`results/flashnext/20261114-060914-bench-production-manual`): generation-time
overhead median 0.04%, p90 0.86%, resolution half-width 0.90%,
`under_one_percent: true`. The same check read 2.08% before the memory
sampler stopped launching `vm_stat` every second.

### Native MTP against plain decoding (128 tokens)

| Decoder | Replay (existing) | Rollback (`FLASHNEXT_MTP_ROLLBACK=1`) | Accepted drafts per round | MB per token |
|---|---|---|---|---|
| Plain | 2.58 (5 arms) | | | 780 |
| MTP depth 1 | 2.36 (4 arms, thermal stop) | 2.55 (4 arms, memory stop at 2.91 GiB) | 0.78 of 1 | 911 / 886 |
| MTP depth 2 | 2.17 (2 arms, memory stop) | 1.66 (5 arms, range 1.58 to 2.32) | 1.33 of 2 | 1,278 / 1,293 |
| MTP depth 3 | 1.35 (5 arms) | 1.72 (2 arms, thermal stop) | 1.78 of 3 | 1,546 / 1,484 |
| MTP adaptive, ceiling 3 | 1.45 (1 arm, thermal stop) | | 1.42 | 1,414 |

Every arm in the table produced the same token digest
(`b9155a40b3158017...`), including the rollback arms.

Native MTP does not speed up decoding on this checkpoint and machine. The
draft head is not the cause: the first draft position is accepted 78% of the
time. The measured causes are these.

- A verification round with one extra row takes 660 ms against 381 ms for a
  plain step, so the extra row costs 0.73 of a step and is kept 78% of the
  time. The best possible ratio is (1 + 0.78) / (1 + 0.73), about 1.03, before
  the draft and fold are paid. Consecutive tokens route to mostly different
  experts, so the second row's reads are nearly a full token's reads.
- With the existing replay, every accepted token of a partly rejected block
  is decoded again one at a time. Rollback removes that, which is why depth 1
  rises from 2.36 to 2.55.
- Multi-row passes allocate fresh buffers for every layer. macOS compressed
  577 GiB during the depth-3 run (519 s) and none during plain decoding. The
  churn also evicts the file cache, so bytes per token nearly double, and the
  MTP runs were the only decode runs to reach thermal level 2.

Speculation can pay only when decode is no longer read-bound. Exact sampled
speculation and MTP state in the prefix cache were therefore not built in
this pass; they remain open in [Stage 5](stage-5.md).

The 8K record of 13 November
([native MTP at 8K](native-mtp-8k-1024-2026-11-13.md)) showed the same sign:
decode fell 42 to 50% with native MTP on both models. In that record the
Flash-Next MTP sequence also differed from the standard path because native
MTP prefills on a different chunk schedule; in today's 103-token runs the
digests are equal.

### Sustained plain decoding (512 tokens, 5 arms)

`results/flashnext/20261114-102624-bench-production-manual`: 2.66 tok/s
median (2.64 to 2.69), 741.5 MB read per token, 110 ms non-I/O per token,
storage 2.79 GB/s, prefill 9.1 tok/s on the 103-token prompt. Available
memory stayed at or above 3.48 GiB, swap was flat, thermal pressure was at
level 1 for 863 of 1,018 s and never at level 2.

### Prefill compression

Every short prefill makes macOS compress memory in a burst and release it:
about 5 GiB for the 23-token prompt, 30 GiB for the 103-token prompt, and
17 GiB for the same prompt with `FLASHNEXT_PREFILL_CACHE_LIMIT_MB=512`. Each
MoE layer reads its routed experts into newly allocated buffers, and the
kernel finds the pages by compressing other memory. Plain decoding, whose
buffers have the same size every layer and are reused, compresses nothing.
A prefill that reads into one reused region (the opt-in prefill ring does
this for long prompts with the pool on) would avoid it for short prompts too;
that was not built here.

### Stage 3: pool policy pair

Not measured. The paired server harness crossed the 3 GiB floor with a 1 GB
pool (2.66 GiB while loading) and, with a 0.5 GB pool, after the first arm
(2.84 GiB). That one arm, least-recently-used at 0.5 GB, decoded at
2.5 tok/s with a hit rate of 0.0. No cost-aware arm ran.

### Why 20 tok/s is out of reach here

20 tok/s leaves 50 ms per token. Plain decoding spends 93 to 122 ms per
token outside I/O, so it cannot reach 20 tok/s even with every expert
resident. Speculation would have to deliver more than two accepted tokens per
round while the reads per round stay near one token's; measured, an extra
row costs 0.73 of a round's time and a token's reads are 741 to 780 MB at a
cache hit rate of about 40%. Reads alone at 2.8 GB/s take 265 ms per token.
Getting reads under 20 ms per token needs about 95% of expert bytes resident;
the route replay of Stage 3 puts the best possible 2 GB cache at 68% and each
further GB at about 9 points, and the machine has roughly 3.6 GiB for experts
once the dense weights and the 3 GiB floor are set aside.

## Nemotron 3.5 Lightning (30B-A3B, MLX 4-bit, Sevren MTP sidecar)

### Equivalence with the stock model

`models.nemotron35.verify_real` compares the streamed engine with a stock
mlx-lm reference built one layer at a time, on a 48-token random prompt and
forced continuation (BF16 KV, no pool).

| Run | Steps | Greedy token agrees | Max logit difference | Mean difference | Logit range |
|---|---|---|---|---|---|
| Default expert kernel | prefill + 3 | 4 of 4 | 1.129 (third decode step) | 0.03 to 0.16 | 13 to 15 |
| Stock `gather_qmm` kernel (`VEYSTRIX_NEMOTRON_GATHER=1`) | prefill + 3 | 4 of 4 | 1.117 (same step) | 0.03 to 0.15 | 13 to 15 |
| Default expert kernel | prefill + 16 | 17 of 17 | 1.129 | 0.03 to 0.16 | 13 to 31 |

The difference does not grow: over 16 decode steps its per-step maximum moves
between 0.16 and 1.13 with no trend. The expert kernel is not its source,
since the stock kernel gives the same figures. The engine is not
bit-identical to the stock model; the operation that differs was not located.
One BF16 step at these logit magnitudes is 0.06 to 0.125. The production
default stores attention keys and values as INT8; this check uses BF16 and
does not cover that setting.

### Decode, plain against native MTP

Paired server harness, greedy, fresh server per arm, reversed order on
alternate rounds, no expert pool (`--flag-pool-gb 0`), INT8 KV, context 8,192.
The prompt is the harness's short one (576 tokens: copy repeated code lines),
which favours draft acceptance.

| Pair | Tokens | Plain tok/s (arms) | MTP tok/s (arms) | Medians |
|---|---|---|---|---|
| MTP depth 2 | 128 | 5.30, 4.92, 4.94 | 5.16, 4.94, 4.87 | 4.94 against 4.94 |
| MTP adaptive, ceiling 4 | 512 | 5.43, 5.03, 4.91 | 4.78, 4.71, 4.52 | 5.03 against 4.71 |

The six arms of each pair share one token digest. Native MTP at depth 2 is
level with plain decoding; adaptive depth with a ceiling of 4 is 6% slower
over 512 tokens. Prefill ran at 84 to 92 tok/s on the 576-token prompt.
Available memory stayed at or above 3.53 GiB, swap was flat, and thermal
pressure stayed at level 0 (749 s in the longer run).

Plain decoding reads about 367 MB per token here (the difference in physical
reads between the 512- and 128-token arms, over 384 tokens). At the 2.8 GB/s
measured for Flash-Next that is about 130 ms of the 199 ms per token, leaving
roughly 70 ms outside I/O. A perfect expert cache would therefore give about
14 tok/s; removing all compute at today's reads would give about 7.6 tok/s.
Neither reaches 20 tok/s.

### What did not fit the 3 GiB floor

- The 8K code-review prompt: available memory fell to 2.28 GiB with the
  harness's 2 GiB pool and to 2.85 GiB with no pool, both during prefill.
  There is no 8K Nemotron figure from this pass; the 13 November record has
  one, taken without this floor.
- Any pool of 1 GiB or more beside the other open applications.
- The traced decode profile (`bench_decode_profile`), which uses the 8K
  prompt. Without it there is no shape corpus for Nemotron kernels, so no
  Nemotron kernel was written (Stage 8).

## Reproduce

```sh
# Flash-Next, one guarded condition (5 arms)
VEYSTRIX_MEMORY_POLICY=legacy FLASHNEXT_EXPERT_POOL_GB=0 FLASHNEXT_SLAB_GLOBAL=0 \
  FLASHNEXT_SLAB_PACK=0 FLASHNEXT_PREFIX_CACHE=0 FLASHNEXT_PROMPT_LOOKUP=0 \
  FLASHNEXT_PREFILL_CACHE_LIMIT_MB=512 FLASHNEXT_NATIVE_MTP=off \
  .venv/bin/python scripts/flashnext/real_run_guard.py --log guard.jsonl -- \
  .venv/bin/python -m models.flashnext.tests.bench.bench_production \
  --telemetry timing --tokens 512 --arms 5 --min-arms 5 --drop 0 \
  --resident-experts 0 --prompt-file PROMPT.txt

# Nemotron pair
.venv/bin/python scripts/flashnext/real_run_guard.py --log guard.jsonl -- \
  .venv/bin/python -m models.flashnext.tests.bench.bench_server_short_paired \
  --runtime nemotron35 --checkpoint "$NEMOTRON_CHECKPOINT" --performance-v2 \
  --set-flag VEYSTRIX_NEMOTRON_NATIVE_MTP=1 --flag-pool-gb 0 --max-tokens 128 --rounds 3
```

For MTP arms set `FLASHNEXT_NATIVE_MTP=on`, `FLASHNEXT_MTP_DEPTH`, and
optionally `FLASHNEXT_MTP_ROLLBACK=1` or `FLASHNEXT_MTP_ADAPTIVE=1`. The guard
exits with status 90 when it stops a run; if it stops the server harness,
check that no `veystrix.cli` server is left running.
