# Apple Silicon (M4) Mechanisms to Split, Overlap, or Accelerate MoE SSD-Offloaded Decode (macOS 26 / MLX / Metal; no new hardware, no quality loss)

Machine context used throughout: base M4 MacBook Air, 16 GB unified memory, single internal NVMe ~3.36 GB/s cold (project measurement), 200–870 MB/token of MoE experts, GPU compute already overlaps SSD reads with ~10% inflation, perfect prefetch only +25%. Previously rejected: F_NOCACHE, mmap, mlock, F_RDADVISE (EPERM attempt), MTLIO warm-only, wired limits, 6–32 workers.

Hardware identity established from primary sources: M4 GPU = **Apple9 / arch gen 16**, 120 GB/s public memory bandwidth, **no GPU neural accelerators (NAX)** — NAX begins with M5/Apple10 — Metal 4 *is* supported on Apple7+ (so M4 can use Metal 4 argument tables, command barriers, decoupled command queues) — [Metal Feature Set Tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf); [MTLGPUFamily.apple9](https://developer.apple.com/documentation/metal/mtlgpufamily/apple9); [pmetal hardware support](https://github.com/Epistates/pmetal/blob/main/docs/hardware-support.md). M4 CPU matrix unit = **SME** (not the older AMX), SVL=512 — [sme-gemm](https://github.com/electricapp/sme-gemm).

## Q1. Can expert gather reads be issued as GPU-side async copies that overlap compute inside the SAME Metal command buffer (single sync), rather than from Python threads?

### Takeaway
No — there is no Metal API that issues a *file/SSD* read as a GPU command inside a compute command buffer. The only in-command-buffer "copy" primitive (`MTLBlitCommandEncoder` / Metal 4's unified `MTL4ComputeCommandEncoder`) copies **buffer→buffer or texture↔buffer in already GPU-visible memory**; it cannot source from a file. Disk reads live on a separate `MTLIOCommandQueue` (or in the kernel via `pread`) and can overlap GPU compute only via `MTLSharedEvent` between two queues, which is a multi-buffer/multi-queue design, not a single-sync one. Metal 4 does reduce CPU-side submission overhead (decoupled command queues, `commit:count:`, barriers, command allocators), but that shrinks host launch time, not the ~130–157 ms `io_await`.

### Cited Findings
- `MTLBlitCommandEncoder` encodes `copy(from:sourceOffset:to:destinationOffset:size:)` between `MTLBuffer`s, texture↔buffer copies, fill, mipmap, indirect-buffer management and CPU/GPU synchronization — all on resources already allocated in GPU-visible memory. No file-handle source exists. — [Apple: MTLBlitCommandEncoder](https://developer.apple.com/documentation/metal/mtlblitcommandencoder)
- Metal 4 merges blit, compute and acceleration-structure encoders into a single `MTL4ComputeCommandEncoder`, and adds `MTL4CommandQueue.commit:count:` to submit multiple command buffers encoded on separate worker threads as one group; work between queues is synchronized with `MTLEvent`/`MTLSharedEvent`, work within a queue with barriers. These are available on Apple7+ (hence M4). — [Apple: Understanding the Metal 4 core API](https://developer.apple.com/documentation/metal/understanding-the-metal-4-core-api); [Metal Feature Set Tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf)
- `MTLIOCommandQueue` reads files directly into `MTLBuffer`/textures (`load(buffer:...)`) or CPU memory (`loadBytes`) on a **separate queue**; Apple explicitly shows synchronizing that IO queue with a render/GPU queue using Metal shared events. Commands within an IO command buffer execute concurrently, and IO command buffers themselves execute concurrently and complete out of order. — [Apple: Resource loading](https://developer.apple.com/documentation/metal/resource-loading); [WWDC22 "Load resources faster with Metal 3"](https://developer.apple.com/videos/play/wwdc2022/10104)
- Argument buffers / Metal 4 argument tables and indirect command buffers (`executeCommandsInBuffer`) can describe many buffers/gathers to the GPU with one binding, but they still only address resident memory; Apple's feature tables list "Argument tables" as a Metal 4 feature from Apple7, and indirect-command-buffer raster/depth-state support only from Apple10. — [Metal Feature Set Tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf); [iOS Metal header (executeCommandsInBuffer declarations)](https://github.com/xybp888/iOS-SDKs/blob/master/iPhoneOS13.0.sdk/System/Library/Frameworks/Metal.framework/Headers/MTLComputeCommandEncoder.h)
- Apple's own guidance: batch encoders into fewer command buffers, but "if your app spends time waiting for GPU results to inform what should be dispatched next, then bubbles will appear in the GPU timeline" — i.e. launch overhead is a separate problem from storage latency. — [Apple Tech Talk: Metal Compute](https://developer.apple.com/videos/play/tech-talks/10580)
- Colibri's M4 Max Metal backend gets overlap by submitting *resident-expert GPU work before missed-expert disk reads* (separate CPU/Metal work), reporting ~1.4× CPU→Metal — evidence that overlap comes from queue/order engineering, not a GPU-side disk command. — [colibri docs/metal.md](https://github.com/JustVugg/colibri/blob/v2.1.0/docs/metal.md)

### Inferences
- The mechanism the question proposes does not exist as stated: a "GPU-side async copy" of a *file range* is impossible because the GPU has no file descriptor / filesystem path; the storage stack (kernel + ANS3 controller) must place bytes in unified memory first. Any "simulated DMA" is either MTLIO writing the MTLBuffer directly or a blit copying an already-resident buffer.
- The closest achievable design: issue expert reads on an `MTLIOCommandQueue` with `MTLIOPriority.high`, signal an `MTLSharedEvent` on IO completion, and have a Metal 4 compute command buffer wait on that event — overlap without a Python-side sync per layer. On Metal 4, `commit:count:` lets multiple CBs be encoded in parallel and committed as one group (lower CPU overhead than the old one-CB-per-commit path).
- Bit-exactness: automatic for all of these (raw byte movement or event ordering); no arithmetic changes. The risk is scheduling contention changing *which* experts are selected only if a speculative variant is introduced — keep advice prefill-only.
- Realistic gain on this machine: **~0 ms of SSD `io_await` hidden** from the single-command-buffer idea itself; possibly a few ms/token from lower Metal 4 submission overhead. MTLIO cold is untested (see Q6/ranking). Feasibility high for a prototype, but it addresses the wrong bottleneck.

### Gaps
- No source documents a public Apple API for file→GPU DMA inside a compute command buffer; treat this as a confirmed negative, not an under-researched lead.
- No measurement of Metal 4 `commit:count:` / decoupled queues on an M4 *Air* decode loop; gains from the old per-CB commit path may be smaller here because MLX already batches subgraphs.
- Whether MLX's Python API exposes the needed `MTLSharedEvent` + external `MTLIOCommandQueue` hooks is unresolved; likely requires a native extension (the `mlx-c` C API cannot inject an existing MTLBuffer pool — [ONNX Runtime EP-MLX evaluation](https://github.com/onnxruntime/onnxruntime-ep-mlx/blob/main/docs/MLX_EVALUATION.md)).

## Q2. Can one Apple GPU kernel do async global loads while others compute — is there a TMA equivalent, and is `MTLIO.loadBytes` usable cold and overlapped with compute on M4?

### Takeaway
M4 has the *hardware* for a TMA-like device→threadgroup DMA (`simdgroup_async_copy`), but **Apple never exposed it as a supported MSL API**; on macOS 26 / Metal 4 the old asm-label trick is deliberately blocked and the replacement workgroup builtins are unlowered on M4. The only way to use it is hand-written LLVM IR + `metal-as` + `metallib`. Crucially, this path moves bytes **device RAM → threadgroup SRAM on the GPU**, not SSD → RAM, so it cannot touch the bottleneck. On M4 the async copy is also *slower* than a cooperative `float4` load (≤~950 GB/s vs ~1454 GB/s) and costs ~4.7 µs latency per round trip; its value is fire-and-forget overlap of tile N+1 with matmul on tile N. M4 also has no GPU neural accelerators/NAX (M5+ only), so no new tensor-core path exists on this chip.

### Cited Findings
- On M4 (`AGXMetalG16G_B0`), macOS 26.0, Xcode 26.4, Metal toolchain 32023.883 / AIR v28 / MSL Metal 4: declaring `__asm("air.simdgroup_async_copy_2d...")` now fails with `illegal string literal in 'asm'`; the front end specifically rejects asm labels beginning with `air.`. The new builtins `air.async_wg_copy` / `air.async_wg_strided_copy` compile but PSO creation fails with `Encountered unlowered function call` because they are absent from `libapplegpu-nt.dylib`. — [Subho, "Reverse engineering Apple's simdgroup async copy on M4" (2026-05-21)](https://ighoshsubho.bearblog.dev/reverse-engineering-apples-simdgroup-async-copy-on-m4) — hobbyist reverse engineering, but toolchain-specific and reproducible; treat as credible primary experiment, not peer-reviewed.
- The old `air.simdgroup_async_copy_{1d,2d}.read/.write` lowerings are still present in the M4 GPU backend and *do* work via hand-written LLVM IR. Measured: 256 B copy ≈70 GB/s, 2 KB ≈951 GB/s; async soft-caps around **950 GB/s**; >16 KB in flight collapses occupancy at the 32 KB per-workgroup threadgroup limit. A manual cooperative `float4` load peaks **1454 GB/s** (>50% faster). Minimal async round-trip latency **4.7 µs**. 8 simdgroups participating ≈6× faster than 1 on M4 (opposite of the older M2 result). — [same source](https://ighoshsubho.bearblog.dev/reverse-engineering-apples-simdgroup-async-copy-on-m4)
- Independent glossary: `simdgroup_async_copy` was Apple's undocumented "cp.async/TMA-equivalent" device→threadgroup copy engine; "Apple's hardware has such an engine, but Apple never exposed it in MSL." Metal 4 closes the `__asm("air.*")` route; `<metal_cooperative_tensor>` ships only a generic layout interface, **not a DMA primitive**. The modern substitute is cooperative loads + double buffering (ILP overlap, not a copy engine). — [metalworking: simdgroup_async_copy](https://metalworking.vercel.app/metal/simdgroup-async-copy)
- The undocumented intrinsic was first catalogued from MPS's `NDArrayMatrixMultiplyNNA14` kernel (`air.simdgroup_async_copy_2d`) — [dougallj/applegpu issue #28](https://github.com/dougallj/applegpu/issues/28). A separate 2026 M4 port had to replace it with synchronous per-lane copies because the AIR Intrinsic crashed JIT compilation on `AGXMetalG16X` — [apstenku123/metal_fast_attention](https://github.com/apstenku123/metal_fast_attention) (note GPU-family microcode string differs from the bearblog machine; likely different M4 SKU).
- Metal 4's inline tensor ops explicitly state that Apple silicon GPUs "don't require an explicit software pipeline to overlap memory and compute operations," and that **neural accelerators exist per core only from `MTLGPUFamily.apple10`** (M5) — [Apple: Running inline ML operations in a shader with Metal 4](https://developer.apple.com/documentation/metal/running-inline-ml-operations-in-a-shader-with-metal-4). Apple9/M4 has none — [Metal Feature Set Tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf).
- `MTLIO.loadBytes` is a documented async file→CPU-memory load; IO command buffers execute concurrently and can be synchronized with GPU work via shared events — [Apple: Resource loading](https://developer.apple.com/documentation/metal/resource-loading); [objc2-metal `MTLIOCommandBuffer.loadBytes` binding](https://docs.rs/objc2-metal/latest/src/objc2_metal/generated/MTLIOCommandBuffer.rs.html). Nothing in the API requires warm data; the project's own probe measured only warm MTLIO (13.1–13.3 GB/s), with cold `loadBytes` explicitly untested — [Mference experiment log](https://github.com/NeelM0906/Mference/blob/main/docs/experiments/summaries/01-model-install-and-expert-io.md).

### Inferences
- **Answer to "async loads while others compute": only within a single kernel for on-GPU tiles, via unsupported IR, and it is not faster than manual loads on M4.** There is no supported "one kernel loads globally while other kernels compute" primitive; concurrency is across threads/encoders, and Apple's own Metal 4 tensor sample says no explicit software pipeline is needed on Apple GPUs.
- `simdgroup_async_copy` is a red herring for this workload: even a perfect 1454 GB/s device→threadgroup copy starts *after* the bytes are already in unified memory, i.e. after the 3.36 GB/s SSD wall has been paid. It could shave a small amount of GEMM staging time once weights land, but not hide `io_await`.
- `MTLIO.loadBytes` **can** be issued cold and its IO command buffer can overlap a compute pass on a different queue via `MTLSharedEvent`; this is feasible (it is just an async read into CPU memory) and bit-exact. The open question is empirical: does Apple's storage stack issue a cold `loadBytes` with better queueing/large-request behavior than 6–32 `pread` workers? That is the only cold-read variant of MTLIO worth testing.
- Realistic gain: **0 ms from simdgroup async copy on the SSD wall; unknown (plausibly small) from cold MTLIO.** Feasibility: low for async-copy IR (private, brittle, closed on Metal 4), medium-high for cold MTLIO.
- Risk note: an async copy whose result is never read is reported to hang an M1-era GPU until reboot — [metalworking](https://metalworking.vercel.app/metal/simdgroup-async-copy); not worth touching on a production machine.

### Gaps
- No public measurement of cold `MTLIO.loadBytes` (or `MTLIOPriority.high`) reducing tok/s on any Apple Silicon machine; the project probe measured only warm reads.
- No reliable source on whether M4 exposes a *supported* device→threadgroup async copy through Metal Performance Primitives (MPP) 2026 APIs; MPP's GEMM guide describes a standard simdgroup/threadgroup/grid tile hierarchy, not a public DMA intrinsic — [Metal Performance Primitives Programming Guide](https://developer.apple.com/download/files/Metal-Performance-Primitives-Programming-Guide.pdf).
- No M4 Air-specific thermal/sustained-clock data for long decode runs; all GPU microbenchmarks found were M4 Pro/Max or M5.

## Q3. Is the SSD→RAM path the bottleneck or RAM→GPU? Can zero-copy / `MTLStorageModeShared` remove a memcpy, and why was zero-copy import slower in our test?

### Takeaway
The bottleneck is **SSD→unified RAM** (~3.36 GB/s cold for 200–870 MB/token), not RAM→GPU: on Apple silicon CPU and GPU share the same DRAM pages, so there is no PCIe-style H2D copy to remove. Zero-copy import was slower because wrapping a host pointer with `makeBuffer(bytesNoCopy:)` defers a **page-mapping cost to the first command buffer that uses it** (~15 µs/MB for malloced memory), loses the allocator's buffer cache/recycling, and only works for whole page-aligned allocations (sub-tensor offsets are not page-aligned → silent copy). Removing a copy that was never on the critical path cannot beat the SSD wall.

### Cited Findings
- With a discrete GPU, host/GPU memory is physically separate and every tensor crosses PCIe; Apple silicon UMA shares DRAM, so `makeBuffer(length:)` normally allocates a Metal region "and you still end up copying from your host-side buffer into the GPU-side buffer" — the copy is avoidable with `makeBuffer(bytesNoCopy:)` but requires a page-aligned pointer (16 KB on arm64 macOS) from `mmap`/`vm_allocate`, not `malloc`. — [lilting.ch, zero-copy inference on Apple Silicon](https://lilting.ch/en/articles/wasm-metal-zero-copy-gpu-inference-apple-silicon)
- **Measured cause of zero-copy being slower:** "Making the buffer is quick, but the first command buffer that uses it pays to map its pages for the GPU: on an M5 Pro some 15 us a MB of malloced memory, and about 0.7–1.4 ms for 64 MB of memory that is already a Metal buffer, against 0.2–0.6 ms when the buffer object itself is reused." With MLX's buffer cache on, the same call dropped from 5.9 ms to 3.9 ms and commit-to-start from 2.4 ms to 0.1 ms. `MTLResidencySet` cut commit-to-start but cost 1.7 ms/call to make resident and broke MLX allocator recycling. — [metal-linalg "MLX's buffers, not wrapped again"](https://c0rmac.github.io/metal-linalg/docs/proposals/known-buffers.md) (M5 Pro; mechanism transfers, numbers do not)
- MLX arrays always live in Metal buffers with `ResourceStorageModeShared | ResourceHazardTrackingModeUntracked`; the `mlx-c` C API cannot wrap an existing `MTLBuffer` as an `mlx_array` or inject a custom allocator. `mlx_array_new_data` **copies**; `mlx_array_new_data_managed` adopts the pointer zero-copy but requires page alignment, and pooled sub-tensor offsets are not page-aligned → copy. — [ONNX Runtime EP-MLX evaluation](https://github.com/onnxruntime/onnxruntime-ep-mlx/blob/main/docs/MLX_EVALUATION.md); [Vocello performance guide](https://github.com/PowerBeef/Vocello/blob/main/docs/reference/performance-guide.md)
- MLX added a "known buffers" mechanism in 2.16.0 (2026-10) so externally owned Metal buffers are registered instead of re-wrapped, precisely because re-wrapping costs mapping time — [MLX issue #2855](https://github.com/ml-explore/mlx/issues/2855); [mlx-native `MlxBuffer::from_raw`](https://docs.rs/mlx-native/0.9.2/mlx_native/graph/struct.MlxBuffer.html).
- Empirical zero-copy loading of MLX models via mmap is "mixed": some models 20×/4× faster to *load*, others 0.69–0.77× slower, and inference generation speed is essentially unchanged (e.g. 16.2 → 16.5 t/s); memory doubling was observed where the mmap region coexisted with materialized tensor copies. "MLX's pread-based loader is already highly efficient." — [OptMLX](https://atomgradient.github.io/OptMLX)
- Apple's published base M4 memory bandwidth is 120 GB/s — roughly 36× the SSD's 3.36 GB/s — [pmetal hardware support](https://github.com/Epistates/pmetal/blob/main/docs/hardware-support.md); [zolotukhin.ai Apple Silicon reference](https://zolotukhin.ai/zinc/docs/apple-silicon-reference).

### Inferences
- Arithmetic: at 300 ms/token with 156.9 ms `io_await`, even *eliminating* every RAM→GPU copy leaves the SSD transfer intact; the only way to move the wall is to issue fewer/different bytes, overlap more, or use a faster medium. Zero-copy is an overhead optimization, not a wall-breaker.
- The "zero-copy is slower" observation is fully explained by first-use page mapping + loss of caching + alignment/copy fallbacks, not by an actual physical copy of every token. Falsifiable fix: pre-touch/pre-map every expert buffer once at load time and reuse a fixed pool of page-aligned `MTLBuffer`s registered with MLX's known-buffer path; if the slowness is mapping, the per-token cost should disappear.
- Bit-exactness: automatic — same physical bytes, no arithmetic. Only lifetime/lazy-evaluation races are a correctness risk (MLX warns against mutating a buffer while an `MLXArray` still holds it) — [Vocello guide](https://github.com/PowerBeef/Vocello/blob/main/docs/reference/performance-guide.md).
- MTLIO writing directly into a pre-created, reused, page-aligned `MTLBuffer` (`load(buffer:)`) is the one variant that combines "no staging copy" with "async read" and is worth a cold-read test; it still traverses the SSD at ~3 GB/s.

### Gaps
- No measurement isolating first-use page-map cost on a base M4 Air with 200–870 MB/token expert buffers; the 15 µs/MB figure is M5 Pro.
- No source confirms MLX's Python `mx.array` can be made from an externally created `MTLBuffer` without a copy via a supported public API (Swift `asMTLBuffer(noCopy:)` exists but is output-direction and lifetime-constrained) — [mlx-swift docs](https://swiftpackageindex.com/ml-explore/mlx-swift/main/documentation/mlx/mlxarray/asmtlbuffer(device:nocopy:)).
- No published Apple doc on whether `MTLIOCommandQueue.loadBuffer` requires the destination MTLBuffer to be in a particular storage mode; needs an empirical check.

## Q4. Multiple independent I/O queues on one SSD — NAND channels, queue depth, chunk size, alignment; are flat 6–32 workers SSD saturation or a Python/GIL issue? Any 2024–2026 controller/DMA reverse engineering?

### Takeaway
The base M4 SSD is a genuine single-device wall with ~8 NAND channels aggregated by the SoC's ANS3 controller, and published base-M4 sequential reads (~2.0–2.9 GB/s in third-party tests) are close to the measured 3.36 GB/s cold — so flat 6–32 workers most likely means the media/controller path is saturated, not the GIL. `os.pread` releases the GIL and pure-I/O worker pools scale linearly until the device saturates; the NAND parallelism is inside the controller and is not addressable from userspace (no API to choose channels, queue, or physical blocks). Reverse engineering documents the Apple Fabric/NVMMU path but exposes no controllable knob.

### Cited Findings
- Apple Silicon storage = ANS3 NVMe controller inside the SoC + one or more **MSP (S5E) firmware cores** on each NAND package doing ECC/wear-leveling/Toggle DDR channel control; links are Apple-proprietary "Apple Fabric," not standard M.2 PCIe. `ioreg -lrw0 -d1 -c AppleANS3NVMeController` exposes `num-bus`, `bus-to-msp`, `dies-per-bus`, `chip-id`, `msp-version`, `nand-marketing-name`. A sampled M3 Pro 512 GB has `num-bus=8`, `bus-to-msp=(0,0,1,1,2,2,3,3)`, 8 dies, 4 MSPs; base-chip small/mid-capacity machines typically have 1–2 MSPs; base 256 GB parts keep 2 packages. — [zenn.dev, Reading the NAND architecture of Apple Silicon with ioreg (2026-06-18)](https://zenn.dev/ext_ta1/articles/apple_nand_architecture?locale=en) — hobbyist but reproducible with one command on the target machine.
- Same source, measured with Blackmagic Disk Speed Test: M3 ≈2735 MB/s, **M4 ≈2881 MB/s (nearly flat)**, M5 ≈6323 MB/s (2.3× jump from NAND generation + controller, not more packages) — [zenn](https://zenn.dev/ext_ta1/articles/apple_nand_architecture?locale=en). Independent 512 GB M4 MacBook Pro tests: read ≈2031 MB/s vs M5 ≈6323 MB/s; base chips route 4 PCIe lanes, Pro/Max 8 — [TechSpot](https://www.techspot.com/news/110030-early-tests-show-m5-macbook-pro-ssd-about.html); [Tom's Hardware](https://www.tomshardware.com/laptops/macbooks/m5-macbook-pros-ssd-is-2-5x-faster-on-average-than-last-gen-m4-exceeding-apples-own-claims-m5-achieves-6-000-mb-s-across-both-read-and-write-speeds). (Note spread between ~2.0 and ~2.9 GB/s across tests/capacity; the project's 3.36 GB/s is at or above these, consistent with a saturated healthy drive.)
- Apple SSD reads are hardware-AES encrypted with no performance penalty; controller functions are split between NAND packages and the SoC Fabric — [Eclectic Light, Apple silicon memory and internal storage](https://eclecticlight.co/2024/03/06/apple-silicon-memory-and-internal-storage).
- Asahi/Black Hat reverse engineering: Apple's NVMe uses a custom **NVMMU** (NVMe IOMMU) where the NVMe transaction ID is the slot index into a DART-style page table; NAND access over NVMe happens in long blocks; A14/M1 use a non-standard NVMe queue format. This is device/firmware-level observation, not a userspace API — [Black Hat USA 2021, "Reverse Engineering the M1" (PDF)](https://i.blackhat.com/USA21/Wednesday-Handouts/us-21-Reverse-Engineering-The-M1.pdf).
- Python: blocking file I/O releases the GIL; pure-I/O worker pools scale near-linearly with thread count (e.g. 1→64 threads ≈843→39,610 TPS in a control experiment), and multi-threaded file reads only help "if you have I/O to spare; if your disk's read speed is slow/saturated, threading will do you no good" — [arXiv 2601.10582, GIL saturation study](https://arxiv.org/html/2601.10582); [Stack Overflow: Do file I/O operations release the GIL?](https://stackoverflow.com/questions/70509732/do-file-i-o-operations-release-the-gil-in-python).
- APFS's documented parallel-I/O weakness is a **global lock in metadata/readdir paths**, not demonstrated for large-file `pread` streaming — [Gregory Szorc, Global kernel locks in APFS](https://gregoryszorc.com/blog/2018/10/29/global-kernel-locks-in-apfs/).

### Inferences
- The "6–32 workers flat" result is most parsimoniously SSD saturation: pread releases the GIL, so a flat curve across a 5× worker range with large span-merged reads is what a saturated ~3 GB/s link looks like. GIL/Python overhead would more plausibly show *degradation* at high worker counts (the saturation-cliff literature), not a flat line from 6 onward. A definitive falsification test is to profile with `fs_usage`/Instruments: if aggregate bytes/s sit at ~3.0–3.4 GB/s with multiple threads blocked in `pread`, it is the device.
- 8 NAND channels and 1–2 MSPs on the base M4 do **not** imply 8× usable userspace parallelism: the channels are aggregated behind one NVMe logical device and one file cache; the controller already interleaves a single large sequential read across them. Increasing queue depth cannot raise media bandwidth that the controller already saturates. Chunk size/alignment tuning is plausible only at the margins (e.g. 16 KB page multiples, large spans), and the project's span-merged reads already did this.
- No 2024–2026 source was found showing a public or private macOS API to pin reads to specific NAND dies/channels, raise NVMe queue depth, or bypass the file cache via NVMe pass-through. The ioreg reverse engineering is *observability*, not control.
- Bit-exactness: not applicable (no arithmetic). Realistic gain: **~0** from more workers/channel tricks; this is a hard wall on this hardware. Feasibility: n/a.

### Gaps
- No direct measurement on the user's M4 Air of `ioreg ... AppleANS3NVMeController` (num-bus / bus-to-msp) — this is a one-command falsifiable test of how many MSPs/NAND channels this specific machine has, and should be run before concluding.
- No Apple Silicon NVMe pass-through / direct-IO API found; "no reliable sources" is the honest answer.
- No instrumented `fs_usage`/Instruments trace separating GIL contention from device saturation in the project's worker sweep; the conclusion is an inference from independent sources, not a direct measurement.

## Q5. Can CPU AMX/SME do MoE dequant+GEMM while the GPU reads a different layer's experts, splitting work across execution units that share one memory bus?

### Takeaway
M4's CPU SME units can produce correct bf16→f32 GEMMs and can run concurrently with the GPU, but this is the **wrong split for an SSD-bound decode**: CPU and GPU share the same unified-memory bus and the same file-cache pressure, so moving GEMM work to the CPU does not add bandwidth for the SSD reads and can actively slow the model because "the CPU is part of every layer." Bit-exactness vs MLX's GPU bf16 GEMM is not guaranteed (different reduction order / accumulation width). At best a small compute-overlap win on compute-bound phases, not an I/O win.

### Cited Findings
- M4 uses **SME** (SVL=512), with a 64×64-byte ZA accumulator: two 32×32 f16/bf16 tiles, four 16×16 f32. M4 bf16 uses `BFMOPA` accumulating in **f32**; native bf16 accumulate (`B16B16`) is an M5-only feature. Fused epilogues (bias, SiLU, clamp, per-column scales) exist in hand-written SME libraries — [sme-gemm](https://github.com/electricapp/sme-gemm).
- Hand-written SME GEMM beats Accelerate by ~1.23× on M4 (MpGEMM); Accelerate dispatch to AMX (M1–M3) / SME (M4+) is the normal path — [arXiv 2606.25426](https://arxiv.org/html/2606.25426).
- Peer-reviewed 2026 GEMM comparison: M4 Pro's two matrix accelerators reach up to **68% of GPU FP32 performance at 42% of its power**; AMX is most efficient for FP32/FP64, ANE is FP16-only — [ScienceDirect, A comparative performance and efficiency analysis of Apple's M architectures (2026)](https://www.sciencedirect.com/science/article/pii/S0167739X26000270). MIT thesis characterizes AMX as load-issue bound with a practical latency model — [MIT CSAIL thesis (2025)](https://commit.csail.mit.edu/papers/2025/Jonathan_Zhou_SB_Thesis.pdf). (These are M4 Pro / M1 data; base M4 has fewer cores and one P-cluster SME.)
- **Direct CPU/GPU split experiment on M4 Pro:** GPU MLX bf16 ≈5.75 TFLOPS (6.46 peak), CPU SME via Accelerate fp32 ≈3.3–3.7 TFLOPS. A 70%/30% MLP split cut one unguided forward pass 236→208 ms (~12%), **but** "Splitting each MLP between the GPU and the CPU's SME units makes all CPU work compete with the model... the CPU is part of every layer, any other CPU work lengthens the steps it overlaps." Moving a codec stage to the GPU helped more than the split. fp16 GEMMs + fp32 residual were 1.9–2.6e-3 from fp32; bf16 GPU error came mostly from bf16 GEMM inputs — [Diffio blog, 2026-09-23](https://diffio.ai/blog/diffio-apple-silicon) (vendor blog, M4 Pro Mac mini, diffusion not MoE).
- ANE is FP16-only and cannot be used for bit-exact bf16 (project already found ANE unusable); SME bf16 on M4 accumulates in f32 and rounds — same nominal recipe as GPU bf16 GEMM but **different accumulation order**, so token-level bit identity must be verified — [sme-gemm](https://github.com/electricapp/sme-gemm); [Diffio blog](https://diffio.ai/blog/diffio-apple-silicon).
- Apple9 M4 has no GPU NAX; base M4 public memory bandwidth 120 GB/s shared by CPU, GPU, and the file cache — [Metal Feature Set Tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf); [pmetal hardware support](https://github.com/Epistates/pmetal/blob/main/docs/hardware-support.md).

### Inferences
- The premise "CPU computes while GPU reads a different layer's experts" is attractive in theory (both units share memory but not issue pipelines), but the bytes the GPU needs must still cross the same SSD→RAM path at 3.36 GB/s. In an I/O-bound decode there is idle compute already; giving some of it to the CPU cannot make the SSD faster. It only helps if there is compute that would otherwise be *on the critical path after* the I/O — and even then Diffio's M4 Pro result shows only ~12% on a compute-bound MLP, with strong contention warnings.
- Bit-exactness: **not automatic**. bf16 GEMM on SME (f32 accumulate, different K-order) vs MLX Metal bf16 GEMM will generally differ in low bits; any such split must pass a ≥200-token greedy digest/router-record gate. Quantized dequant epilogues can also reorder arithmetic. Treat "bit-exact bf16" as *false until proven*.
- Feasibility on this exact machine: low. Base M4 MacBook Air has a 10-core CPU (4P+6E) with SME per cluster and no fan; the fast P-cluster SME is a small fraction of the M4 Pro numbers. MLX's CPU stream uses Accelerate, so a prototype is possible, but integrating per-expert CPU GEMM into MLX's lazy graph is nontrivial.
- Realistic gain on THIS machine: ~0 ms of `io_await`; plausible small negative from bus/cache contention. Rank below all I/O-side mechanisms.

### Gaps
- No published CPU-SME-vs-GPU MoE decode experiment on any Apple Silicon machine; the closest data is diffusion MLPs on M4 Pro.
- No bit-exactness measurement (token digest) between M4 SME bf16 GEMM and MLX Metal bf16 GEMM.
- No base-M4 Air (8-core GPU / 16 GB / fanless) SME throughput measurement; all found benchmarks were M4 Pro/Max or M5.

## Q6. mmap with MADV_WILLNEED/DONTNEED, F_RDADVISEV batching 64 ranges, POSIX_FADV, purgeable/compressed memory — anything left after the earlier rejections?

### Takeaway
The only mechanism here with a measured >wall cold-ish number is `F_RDADVISE`/`F_RDADVISEV`: genuinely asynchronous, up to 64 ranges per syscall, ~5 ms to fill 24 MB, and the project's own untimed probe reached 3.61–3.78 GB/s. `MADV_WILLNEED` is **synchronous on Darwin** (~11 ms/24 MB) and cannot overlap; `MADV_DONTNEED` and purgeable/pressure APIs do not change bytes that must be read; `posix_fadvise` does not exist on macOS (surrogate: `F_RDADVISE`/`F_RDAHEAD`). Even perfect prefetch was measured at only +25%, so this is a bounded win and must be advice-only to preserve token parity.

### Cited Findings
- Xcode `fcntl(2)` man page: `F_RDADVISE` "Issue an advisory read async with no copy to user"; `F_RDADVISEV` issues multiple advisory reads, `rav_count` 1..64, with `struct radvisory {off_t ra_offset; int ra_count;}` / `struct radvisoryv {...}`. Documented errors are EBADF/EFBIG/EINVAL — **EPERM is not a documented RDADVISE error** (it belongs to F_PUNCHHOLE/F_SETSIZE/F_SETFL), so the project's earlier EPERM is likely a struct/fd/sandbox mistake or confusion with kqueue's regular-file EPERM. — [Xcode fcntl(2) man page](https://keith.github.io/xcode-man-pages/fcntl.2.html)
- Bun's production macOS arm64 cold-start work: 24 MB `F_RDADVISE` returns in **0.5 ms**, pages resident ~5 ms later; `MADV_WILLNEED` is synchronous (11 ms/24 MB) and useless for overlap. Measured gains 156→125 ms (40k-function app), 388→344 ms (`--help`), 636→596 ms (first render); over-prefetching 62 MB regressed first render because it competed with faults actually being waited on. — [oven-sh/bun commit](https://github.com/oven-sh/bun/commit/adc354d9983fe1866ceeb28e6a6ecd30ce443cca)
- PostgreSQL patch: "macOS doesn't have posix_fadvise(), but fcntl() with the F_RDADVISE command does the same thing." fio's macOS shim likewise maps readahead control to `fcntl(F_RDAHEAD)`. — [PostgreSQL patch](https://postgresql.org/message-id/attachment/164300/v3-0001-Add-prefetching-support-on-macOS.patch); [fio commit](https://github.com/axboe/fio/commit/407491a84e257a60a09209c624014757b816ee8e)
- Project log: "Untimed ahead advice reached 3.61-3.78 GB/s"; speculative *use* of predicted experts (IO-08) fell 4.937→4.742 tok/s and **emitted IDs diverged**; `mlock` recovered ~0 ms (IO-06); skipping expert streaming recovered 12–14 ms, proving contention not eviction; MTLIO warm-only 13.1–13.3 GB/s with only 5.4–7.5% of misses warm. — [Mference experiment log](https://github.com/NeelM0906/Mference/blob/main/docs/experiments/summaries/01-model-install-and-expert-io.md)
- Darwin `madvise(2)` documents WILLNEED/DONTNEED but no huge-page data flag; macOS uses 16 KB pages on arm64 (which already reduces TLB pressure vs 4 KB). Memory-pressure APIs (`DISPATCH_MEMORYPRESSURE_*`, purgeable `NSCache`/`vm_purgeable`) let apps drop their own caches but give no control over the file cache or compressor. — [Darwin madvise(2)](https://leancrew.com/all-this/man/man2/madvise.html); [XNU memorystatus_notify.md](https://github.com/apple-open-source/macos/blob/master/xnu/doc/vm/memorystatus_notify.md); [Bun commit](https://github.com/oven-sh/bun/commit/adc354d9983fe1866ceeb28e6a6ecd30ce443cca); [mac-ram-cleaner](https://github.com/chumafox/mac-ram-cleaner)

### Inferences
- `F_RDADVISEV` is the one genuinely new primitive in this whole space for this machine: 64 ranges in one syscall maps cleanly to "top-k experts × next layer(s)", is advice-only (bit-exact by construction), and issues with no user-space copy or blocking thread. Its 3.61–3.78 GB/s project probe is the only measured cold-ish throughput above the ~3.36 GB/s wall.
- The earlier EPERM is almost certainly fixable; the decisive 2-minute test is `fcntl(fd, F_RDADVISE, &(struct radvisory){off,count=1<<20})` on a freshly opened regular file and print errno. Use advice only for router-selected experts (never substitute a predicted expert) to avoid IO-08's token divergence; gate on bit-identical token IDs.
- All other knobs in this question are dead ends: WILLNEED blocks the caller, DONTNEED/purgeable/pressure APIs only change *which* pages are resident (the 12–14 ms recovery came from removing streaming entirely, not pinning), and there is no POSIX_FADV or file-backed huge-page API on macOS. This is consistent with the user's "perfect prefetch only +25%" ceiling — advice can at best approach that ceiling.
- Bit-exactness: automatic for advice-only prefetch. Feasibility: high (documented syscall, production usage). Realistic gain on this machine: bounded by +25% perfect-prefetch result; realistically less due to contention and lead-time limits at 200 MB+/token.

### Gaps
- No end-to-end real-decode measurement of `F_RDADVISE`/`F_RDADVISEV` exists (the project explicitly deferred it) — the single most valuable missing experiment.
- No published numbers for `F_RDADVISEV` with >1 range, or for a 400+ MB expert blob (Bun measured 24 MB).
- No measurement of advised-page residency under 16 GB streaming pressure, nor of the over-prefetch contention boundary for 200–870 MB/token.
- Exact cause of the earlier EPERM is unknown without a reproduction; cannot assert struct error vs sandbox vs fd type.

## Q7. Ranked plausibility of all mechanisms for THIS machine (base M4 Air, 16 GB, single SSD)

### Takeaway
Rank by (expected hiding of ~130–157 ms `io_await`) × (feasibility on macOS 26 / MLX) × (bit-exactness). Nothing found breaks the single-SSD wall; the realistic ceiling is the already-measured "perfect prefetch +25%," and most Metal-side tricks are overhead optimizations that hide ~0 ms of SSD wait.

### Cited Findings / Ranking
1. **`F_RDADVISE` / `F_RDADVISEV` (advice-only, correct struct, end-to-end decode)** — only documented async kernel path with a project probe above the wall (3.61–3.78 GB/s); EPERM likely fixable; bounded by +25% perfect-prefetch ceiling. [fcntl(2)](https://keith.github.io/xcode-man-pages/fcntl.2.html); [Bun commit](https://github.com/oven-sh/bun/commit/adc354d9983fe1866ceeb28e6a6ecd30ce443cca); [Mference log](https://github.com/NeelM0906/Mference/blob/main/docs/experiments/summaries/01-model-install-and-expert-io.md)
2. **Cold `MTLIO.loadBytes` / `MTLIOPriority.high`, overlapping a compute CB via `MTLSharedEvent`** — feasible, bit-exact, but cold benefit entirely unmeasured; warm-only result does not transfer. [Apple resource loading](https://developer.apple.com/documentation/metal/resource-loading); [WWDC22](https://developer.apple.com/videos/play/wwdc2022/10104)
3. **Metal 4 decoupled queues / unified encoder / `commit:count:` / pre-registered page-aligned MTLBuffers** — real but small host-overhead win; hides ~0 ms `io_await`. [Metal 4 core API](https://developer.apple.com/documentation/metal/understanding-the-metal-4-core-api); [metal-linalg known buffers](https://c0rmac.github.io/metal-linalg/docs/proposals/known-buffers.md)
4. **CPU SME / AMX split of dequant+GEMM** — compute-only, shared bus contention, bf16 bit-exactness unproven; ~0 I/O gain and possible regression. [Diffio](https://diffio.ai/blog/diffio-apple-silicon); [ScienceDirect 2026](https://www.sciencedirect.com/science/article/pii/S0167739X26000270)
5. **`simdgroup_async_copy` via hand-written IR** — device→threadgroup only, closed on Metal 4, slower than manual loads on M4; ~0 SSD gain. [bearblog RE](https://ighoshsubho.bearblog.dev/reverse-engineering-apples-simdgroup-async-copy-on-m4); [metalworking](https://metalworking.vercel.app/metal/simdgroup-async-copy)
6. **More workers / channel tricks / mmap / zero-copy / mlock / purgeable memory** — already rejected or physically incapable of raising media bandwidth; hard wall. [zenn NAND analysis](https://zenn.dev/ext_ta1/articles/apple_nand_architecture?locale=en); [OptMLX](https://atomgradient.github.io/OptMLX); [Mference log](https://github.com/NeelM0906/Mference/blob/main/docs/experiments/summaries/01-model-install-and-expert-io.md)

### Inferences / Falsifiable tests (priority order)
1. `ioreg -lrw0 -d1 -c AppleANS3NVMeController` on the target M4 Air to record `num-bus`/`bus-to-msp`; then `fcntl(F_RDADVISE, &radvisory{1MB})` sanity check (expect 0, errno untouched). Minutes.
2. End-to-end advice-only `F_RDADVISEV` (≤64 ranges) for router-selected next-layer experts; gates: tok/s ≥ baseline, **bit-identical token IDs**, prefill wall time unchanged. This is the decisive experiment.
3. Cold `MTLIO.loadBytes` + `MTLIOPriority.high` vs parallel `pread`, 200 tokens, with output-parity gate; add a combined "RDADVISE into page cache, then MTLIO loadBytes from cache" arm (never tested).
4. Metal 4 host-overhead A/B: old per-CB commit vs `commit:count:` with pre-registered page-aligned buffers; expect few ms/token at most, no `io_await` change.
5. CPU-SME 30% expert-GEMM split with a 200-token digest gate; predict no `io_await` reduction and likely regression from bus contention. Drop if digest changes or tok/s falls.
6. Instruments/`fs_usage` trace of the 6→32 worker sweep to definitively separate device saturation from scheduling overhead; if aggregate bytes/s ≈3.0–3.4 GB/s with threads blocked in `pread`, declare the SSD a hard wall.

### Gaps
- No mechanism found that raises the ~3.36 GB/s single-SSD wall in software; no Apple API for NVMe pass-through, NAND-channel affinity, or SSD→GPU DMA; no public supported async-copy/TMA primitive on M4.
- All hardware-specific GPU/SME benchmarks found were on M4 Pro/Max or M5, not the fanless base M4 Air; numbers should be treated as upper bounds.
