# Cerebras Inference and the I/O Wall

Scope: how Cerebras wafer-scale inference works, with emphasis on how it avoids the SSD/HBM weight-read wall that limits GPU inference of large MoE models, and what (if anything) transfers to a 16 GB Apple M4 doing bit-exact MoE decode. All quantitative claims below are inline-sourced. Where Cerebras marketing and third-party sources conflict, both are given.

Important framing correction up front (verified across sources): Cerebras uses **two different weight-residency models** that must not be conflated.
- **Training / trillion-parameter scale:** weights live in external **MemoryX** DRAM/flash and are *streamed* onto the wafer one layer at a time; weights are "never stored on the CS-3 system, not even temporarily" ([Cerebras Architecture Deep Dive](https://www.cerebras.ai/blog/cerebras-architecture-deep-dive-first-look-inside-the-hw-sw-co-design-for-deep-learning); [WSE whitepaper, bojielimirror](https://raw.githubusercontent.com/bojieli/ai-infra-book/main/references/text/cerebras-wse3.txt)).
- **Inference (the served 8B/70B/120B models):** the *entire model is held in on-chip SRAM*; models too large for one wafer are split at layer boundaries across multiple CS systems ([Introducing Cerebras Inference](https://www.cerebras.ai/blog/introducing-cerebras-inference-ai-at-instant-speed); [Blackwell vs Cerebras](https://www.cerebras.ai/blog/blackwell-vs-cerebras)). The "no off-chip weight read per token" property applies to the *inference* path and is the crux of this research.

## Key Question 1: WSE-2 / WSE-3 physical specs, SRAM, cores, memory & fabric bandwidth — and how weights/activations live entirely in on-chip SRAM

### Takeaway
WSE-3 is a single 300 mm wafer (46,225 mm², ~57× a large GPU) with ~4T transistors, 900,000 small programmable cores, and 44 GB of *distributed* SRAM delivering 21 PB/s aggregate bandwidth — large enough that a 20B model (and, across wafers, a 70B/120B model) resides in SRAM, so decode requires **zero off-chip weight reads per token**. This is a physical property of the wafer, not a software trick.

### Cited Findings
- **Generational specs (third-party peer comparison):** WSE-1 (2019, TSMC 14 nm): 46,225 mm², >1.2T transistors, 400,000 cores, 18 GB SRAM, 9 PB/s memory BW. WSE-2 (TSMC 7 nm): 2.6T transistors, 850,000 cores, 40 GB SRAM, 20 PB/s memory BW, 220 Pb/s fabric BW. WSE-3 (2024, TSMC 5 nm): 4T transistors, 900,000 cores, 44 GB SRAM, 125 PFLOPS peak, 21 PB/s memory BW ([arXiv:2503.11698](https://arxiv.org/html/2503.11698v1)).
- **Cerebras primary specs:** WSE-3 press release confirms 900,000 AI cores, 44 GB on-chip SRAM, external memory tiers 1.5 TB / 12 TB / 1.2 PB; up to 256 exaFLOPs across 2048 nodes ([Cerebras press release](https://www.cerebras.ai/press-release/cerebras-announces-third-generation-wafer-scale-engine)).
- **Wafer geometry:** one full wafer is 46,225 mm² (~462 cm²) vs ~815 mm² reticle limit for a conventional die; 84 dies of ~10,000 cores each are stitched into one homogeneous chip by crossing <1 mm scribe lines repurposed as wires ([WSE whitepaper](https://raw.githubusercontent.com/bojieli/ai-infra-book/main/references/text/cerebras-wse3.txt); [arXiv:2503.11698](https://arxiv.org/html/2503.11698v1)).
- **Per-core memory physics:** each core is ~38,000 µm², half of it 48 kB of local SRAM (8 single-ported 32-bit banks; 192–256-bit access/cycle = two 64-bit reads + one 64-bit write; plus a 256 B software-managed cache for accumulators), 110k standard cells, 1.1 GHz, 30 mW peak. Memory is independently addressed per core; there is "no shared memory in the traditional sense" — all sharing is explicit via the fabric. Cerebras claims ~200× more memory bandwidth per GPU-equivalent silicon area directly to the datapath ([Architecture Deep Dive](https://www.cerebras.ai/blog/cerebras-architecture-deep-dive-first-look-inside-the-hw-sw-co-design-for-deep-learning); [WSE whitepaper](https://raw.githubusercontent.com/bojieli/ai-infra-book/main/references/text/cerebras-wse3.txt)).
- **Aggregate numbers (Cerebras):** 21 PB/s on-chip memory bandwidth = ~7,000× an H100's ~3 TB/s HBM; 214 Pb/s fabric bandwidth ([Introducing Inference](https://www.cerebras.ai/blog/introducing-cerebras-inference-ai-at-instant-speed); [WSE whitepaper](https://raw.githubusercontent.com/bojieli/ai-infra-book/main/references/text/cerebras-wse3.txt)). WSE-3 Turbo (CS-4, 2026): 250 PFLOPS and **43.2 PB/s** memory BW (~2× WSE-3), 2 μs wafer-to-wafer I/O ([CS-4](https://www.cerebras.ai/cs4)).
- **The "no off-chip read per token" arithmetic:** a 70B model at 16-bit = 140 GB; one token requires moving all 140 GB once. 10 tok/s needs 1.4 TB/s (an H100's 3.3 TB/s suffices); ~1,000 tok/s needs ~140 TB/s, "far exceeding the memory bandwidth of any GPU server or system." Cerebras eliminates the transfer entirely by storing the model on-chip ([Introducing Inference](https://www.cerebras.ai/blog/introducing-cerebras-inference-ai-at-instant-speed)).
- **How a 70B fits:** 20B models fit on one CS-3 (44 GB at 16-bit ≈ 40 GB); 70B fits on "as few as four systems" (4 × 44 GB = 176 GB > 140 GB), split at layer boundaries ([Introducing Inference](https://www.cerebras.ai/blog/introducing-cerebras-inference-ai-at-instant-speed)).
- **Yield mechanism enabling the wafer:** cores are ~0.05 mm² vs an H100 SM ~6 mm², giving ~164× better core fault tolerance; a dynamically reconfigurable fabric routes around defects, so ~900,000 working cores are guaranteed ([arXiv:2503.11698](https://arxiv.org/html/2503.11698v1); [SC25 walkthrough, Charbax/YouTube](https://www.youtube.com/watch?v=tlvfZulPYaw)).
- **Source-quality caveat:** arXiv:2503.11698 is a useful third-party comparison but internally inconsistent (e.g., it variously lists on-chip memory as 44 GB / 0.05 GB / 0.4 GB / 1.6 GB depending on table row, and claims WSE-3 supports "up to 24 trillion parameters"). Treat its tables as indicative, not authoritative; prefer Cerebras primary sources for specs.

### Inferences
- **Mechanism:** on-chip residency means the weight operand is read from local SRAM tens of microns from the FMAC datapath at full datapath bandwidth; there is no DRAM/HBM/SSD transaction in the decode critical path. The 21 PB/s figure is an *aggregate* SRAM bandwidth, roughly matched to the aggregate compute, which is why a token can be produced in ~0.5 ms rather than waiting on 140 GB of HBM traffic.
- **Verdict — transferability to 16 GB M4:** **Fundamentally impossible to transfer.** A 16 GB unified-memory M4 cannot hold a 70B/120B MoE at bit-exact precision (a 70B at 16-bit alone is 140 GB). The SRAM capacity and 21 PB/s bandwidth are a wafer-level physical artifact; no software on M4 can synthesize them. The *principle* "keep the whole working set in the fastest tier so there is no per-token weight read" is transferable only for models that actually fit in 16 GB.

### Gaps
- No public teardown of the exact SRAM hierarchy mapping for the *inference* (vs training) 70B/120B serving configuration — e.g., whether some weights spill to external memory on CS-3 under specific batch/concurrency conditions.
- "Memory prefix" (from the assignment) did not resolve to a named Cerebras feature in any source found; see Key Question 2 Gaps.

## Key Question 2: How Cerebras Inference works; weight streaming, "memory prefix," 70B/120B+ fit, decode/prefill throughput, latency, dense & MoE, 2024–2026

### Takeaway
Cerebras Inference keeps the full model in on-chip SRAM (no per-token off-chip weight read), runs native 16-bit weights, and since Aug 2024 has gone from 450 tok/s (70B) to 2,100 tok/s (70B, Oct 2024) to >3,000 tok/s (GPT-OSS-120B MoE, 2025–26), with TTFT among the best measured. Speed comes from a software/hardware stack rewrite (kernels, async wafer I/O, speculative decoding) that finally exploited the wafer's bandwidth — not from a new chip.

### Cited Findings
- **Launch (Aug 27, 2024):** 1,800 tok/s Llama-3.1-8B and 450 tok/s Llama-3.1-70B; 20× faster than GPU hyperscale clouds; 2.4× faster than Groq on 8B; 1/3 the power of DGX; original 16-bit Meta weights ([Introducing Inference](https://www.cerebras.ai/blog/introducing-cerebras-inference-ai-at-instant-speed)).
- **3× speedup (Oct 24, 2024):** 2,100 tok/s Llama-3.1-70B (16× fastest GPU, 68× hyperscale clouds); full request/response in 0.4 s vs 1.1–4.2 s on GPUs. Mechanism: rewrote MatMul, reduce/broadcast, elementwise, activation kernels; made wafer I/O asynchronous with compute; added **speculative decoding** (small + large model in tandem), causing ±20% output-speed variance. Precision unchanged at 16-bit ([3× faster blog](https://www.cerebras.ai/blog/cerebras-inference-3x-faster); Artificial Analysis charts reproduced there; TTFT "tied second place").
- **DeepSeek-R1-Distill-Llama-70B (Jan 30, 2025):** >1,500 tok/s, 57× GPU-based solutions ([press release](https://www.cerebras.ai/press-release/cerebras-launches-worlds-fastest-deepseek-r1-distill-llama-70b-inference)).
- **GPT-OSS-120B MoE (Nov 2025):** >3,000 tok/s; Baseten's best Blackwell result (8× GB200, TP8, TensorRT-LLM, NVIDIA Dynamo, EAGLE-3 speculative decoding) was 650 tok/s → ~5× Cerebras lead even though WSE-3 launched in 2024. Pricing $0.75/M output tokens vs $0.50; price-performance index 4,000 vs 1,300 ([Blackwell vs Cerebras](https://www.cerebras.ai/blog/blackwell-vs-cerebras)).
- **2026 shared-inference catalog:** `gpt-oss-120b` 120B, 65k/131k context, ~3,000 tok/s; `qwen-3.8-27b` 27B, 64k/128k context, ~1,850 tok/s. Many more models (Kimi, GLM, Gemma, etc.) via Dedicated Inference ([inference docs](https://inference-docs.cerebras.ai/models/overview)).
- **Quantization nuance (2026 docs):** "selective weight-only quantization only during storage" — weights stored at partial 16/8/4-bit "in line with industry standards," dequantized on the fly so operations run in high precision; activations, attention, and **KV cache remain full precision and unquantized**; all shared-inference models are unpruned/original ([inference docs](https://inference-docs.cerebras.ai/models/overview)). This softens the 2024 "native 16-bit only" claim: storage may be quantized, math is high-precision.
- **CS-4 / WSE-3 Turbo (2026):** up to 30× faster than production GPUs; 10× throughput/W vs CS-3; 2 μs wafer-to-wafer interconnect; >1,000 tok/s on models exceeding 50 trillion parameters; heterogeneous/disaggregated inference enabled by faster wafer I/O ([CS-4](https://www.cerebras.ai/cs4)).
- **Weight streaming (training) mechanics, for contrast:** weights in MemoryX DRAM/flash stream onto the wafer at full I/O bandwidth; each weight triggers an AXPY on a *batch* of resident activations and is then discarded; reused across a batch to amortize streaming; gradients stream back to MemoryX ([Architecture Deep Dive](https://www.cerebras.ai/blog/cerebras-architecture-deep-dive-first-look-inside-the-hw-sw-co-design-for-deep-learning); [WSE whitepaper](https://raw.githubusercontent.com/bojieli/ai-infra-book/main/references/text/cerebras-wse3.txt); [Linear Scaling blog](https://www.cerebras.ai/blog/linear-scaling-made-possible-with-weight-streaming)).

### Inferences
- **Decode vs prefill:** the sources report decode output speed (tokens/s per user) and TTFT but do not break out prefill compute separately. The architecture is a giant MatMul array, so prefill (matrix–matrix) and decode (matrix–vector/batched AXPY) are both executed as weight-broadcast + activation-resident FMAC; decode's low arithmetic intensity is exactly why SRAM residency matters most there.
- **Scale-out for huge models:** 70B spans ≥4 wafers split at layer boundaries; CS-4 extends this to tens-of-trillions of parameters with 2 μs wafer-to-wafer links, claiming interactive decode (>1,000 tok/s) even at that scale ([Introducing Inference](https://www.cerebras.ai/blog/introducing-cerebras-inference-ai-at-instant-speed); [CS-4](https://www.cerebras.ai/cs4)).
- **Verdict — transferability to 16 GB M4:** the *product-level* tricks that are software and DO transfer: (a) **speculative decoding** to reduce full-model passes; (b) **asynchronous I/O overlapped with compute**; (c) **store-time quantization with on-the-fly dequant** (but this breaks bit-exactness). The *defining* property — no off-chip weight read per token — is only achievable on M4 for models ≤ ~8B at 4-bit or ≤ ~4B at 16-bit, not for 70B/120B bit-exact MoE.

### Gaps
- **"Memory prefix":** no Cerebras feature by that name found in the docs or blogs. The closest concepts: (i) KV cache/KV-prefix kept on-chip in full precision ([inference docs](https://inference-docs.cerebras.ai/models/overview)); (ii) prefix caching (common in LLM serving) not specifically documented for Cerebras. Report-writer should treat "memory prefix" as likely referring to KV-cache/prefix residency, not a distinct Cerebras technology.
- No published prefill throughput (tokens/s input) or TTFT absolute millisecond values for 2025–26 models; only relative TTFT rankings.
- No disclosure of per-watt/per-token decode energy for the M4-relevant small-model case.

## Key Question 3: How Cerebras handles MoE (Qwen, GPT-OSS, Llama) — sparse expert activation on wafer

### Takeaway
Cerebras avoids expert parallelism entirely: because it has ~900× a single GPU's on-chip SRAM, it can hold big MoE models on-chip (or use weight streaming) with no all-to-all shuffling. Its own analysis shows GPU expert-parallelism spends ~91% of an MoE layer in communication; on the wafer the real problem is instead sparse experts becoming I/O/compute-underutilized, which Cerebras fixes with **Batch Tiling on Attention (BTA)** — a batch-decoupling technique proven on Qwen3-30B-A3B.

### Cited Findings
- **Why MoE is an I/O wall on GPUs:** non-deterministic routing means you must load *all* experts into memory "just in case"; moving expert weights per token is "too slow given memory-bandwidth and latency limits." Expert parallelism (GShard/DeepSeek-style) uses all-to-all token shuffling; on 8×H100 at NVLink ~350 GB/s, expert compute is ~0.08 ms but communication ~0.77 ms → **communication consumes ~91% of MoE layer time**. Qwen3-30B-A3B needs ~472 GB total (464 GB weights+grads+optimizer + ~8 GB activations) → ≥8 H100s ([MoE at Scale](https://www.cerebras.ai/blog/moe-guide-scale)).
- **Cerebras advantage:** "about 900 times more on-chip memory (SRAM) than a latest single GPU," so bigger models fit directly; with weight streaming it trains trillion-parameter MoE (Kimi K2) on a single device using pure data parallelism — no model parallelism ([MoE at Scale](https://www.cerebras.ai/blog/moe-guide-scale)).
- **The wafer's MoE problem — arithmetic intensity:** sparse routing subdivides the batch; at top_k=1 each expert sees only b/N sequences. For Qwen3-30B-A3B this is ~88% lower arithmetic intensity than dense (minimum sparsity), making experts I/O-bound; attention is activation-memory-bound (quadratic in sequence length) ([MoE at Scale](https://www.cerebras.ai/blog/moe-guide-scale)).
- **BTA mechanism:** split attention's input batch into G tiles of size B, process each independently, concatenate to batch G×B fed to experts — decoupling attention's small-batch memory need from experts' large-batch utilization need (analogous to FlashAttention tiling along sequence, but along batch). Results on Qwen3-30B-A3B (128 experts, top_k=8, 3B active, single CS-3): conventional batching loses up to 53% throughput (2× slowdown) at 128 experts and up to 86% (7× slowdown) at high sparsity; BTA keeps throughput near dense across all settings ([MoE at Scale](https://www.cerebras.ai/blog/moe-guide-scale)).
- **Served MoE models:** GPT-OSS-120B is the flagship MoE at ~3,000 tok/s; Qwen3.8-27B ~1,850 tok/s; several MoE families (Kimi, GLM) available via Dedicated Inference ([inference docs](https://inference-docs.cerebras.ai/models/overview); [Blackwell vs Cerebras](https://www.cerebras.ai/blog/blackwell-vs-cerebras)).
- **Model compression for MoE serving:** shared-inference MoE models are original/unpruned; only storage-level selective quantization, dequantized on the fly; Cerebras researches REAP (Router-weighted Expert Activation Pruning) but those pruned models are not served ([inference docs](https://inference-docs.cerebras.ai/models/overview)).

### Inferences
- **Mechanism distinction:** BTA is published as a **training** optimization; the served-inference MoE speed comes from on-chip weight residency. Do not claim BTA is the reason GPT-OSS decode is fast — there is no source for that. The transferable idea from BTA (raise expert arithmetic intensity by growing effective batch, e.g., via speculative decode / continuous batching) is relevant to decode at batch=1.
- **Verdict — transferability to 16 GB M4:** the *diagnosis* transfers perfectly: on an SSD-offloaded M4 MoE, router-nondeterminism forces you to keep all experts resident in the fast tier or pay all-to-all/offload costs, and sparse top_k makes each expert I/O-bound. The *fix* only partially transfers: BTA and expert batching help training/throughput, not single-stream decode; and a 16 GB M4 cannot keep a 120B MoE (even ~5–6B active params with all experts resident) in memory at bit-exact precision. So the Cerebras MoE advantage is again primarily a capacity/BW property, not a portable algorithm.

### Gaps
- No published Cerebras latency/throughput breakdown of *which experts* are activated or expert-load-balancing behavior during **inference** decode of GPT-OSS-120B.
- No source confirming whether Qwen3.8-27B is dense or MoE; Qwen3-30B-A3B (MoE) is documented but is a different model.
- No quantitative decode-only (not training) BTA benchmark.

## Key Question 4: Dataflow / spatial computing execution model — how a transformer layer maps to the grid and why it avoids the von Neumann bottleneck

### Takeaway
Each core is an independent programmable dataflow engine: computation is *triggered by arriving data* (and its control tag), not by fetching instructions from a shared program memory; SRAM is distributed next to the datapath so bandwidth equals operand bandwidth. A transformer layer is mapped by tiling B/S over y and H over x, holding activations resident in core SRAM, broadcasting weights across columns so each weight fires an AXPY into local accumulators, then ring-reducing partial sums — overlapping the next weight row via microthreads.

### Cited Findings
- **Dataflow core:** "all the computation is triggered by the data. The fabric transports both the data and the associative control directly in the hardware. Once the cores receive that data, the hardware triggers a lookup of instructions to run." Zero data is filtered at the sender; only nonzero data triggers compute → native unstructured sparsity with no performance loss; up to 10× GPU utilization on sparse compute ([Architecture Deep Dive](https://www.cerebras.ai/blog/cerebras-architecture-deep-dive-first-look-inside-the-hw-sw-co-design-for-deep-learning); [WSE whitepaper](https://raw.githubusercontent.com/bojieli/ai-infra-book/main/references/text/cerebras-wse3.txt)).
- **Static instruction loading:** ML instructions are statically loaded upfront via a configuration interface and do not change during execution — avoiding per-instruction fetch from shared memory ([WSE whitepaper](https://raw.githubusercontent.com/bojieli/ai-infra-book/main/references/text/cerebras-wse3.txt)).
- **Microthreads:** 8 simultaneous tensor-operation contexts switched cycle-by-cycle, with independent per-core scheduling and priorities; reductions are overlapped with FMAC of the next weight row ([Architecture Deep Dive](https://www.cerebras.ai/blog/cerebras-architecture-deep-dive-first-look-inside-the-hw-sw-co-design-for-deep-learning)).
- **Layer-to-grid mapping:** activation tensor dims (Batch, Sequence, Hidden) are split over the 2-D grid — Hidden (H) in x, Batch+Sequence (B,S) in y — enabling efficient weight broadcast and reductions. Activations sit in the SRAM of the cores where compute occurs; weights/data/commands are broadcast over columns; each arriving weight triggers FMAC (AXPY) into a local accumulator in the SW cache; partial sums reduced across a row via a ring pattern using static fabric "colors," driven by PSUM (all columns) / FSUM (one column) command packets; output features stored with the same distribution for the next layer ([Architecture Deep Dive](https://www.cerebras.ai/blog/cerebras-architecture-deep-dive-first-look-inside-the-hw-sw-co-design-for-deep-learning); [WSE whitepaper](https://raw.githubusercontent.com/bojieli/ai-infra-book/main/references/text/cerebras-wse3.txt)).
- **Fabric design enabling it:** 2-D mesh, 5-port routers (32-bit bidirectional × 4 directions + core port), single-cycle node-to-node latency, 24 static nonblocking "colors" time-multiplexed on links, native broadcast/multicast, die-to-die crossing <1 mm scribe lines. Per 826 mm² equivalent: 4.3 TB/s and 0.15 pJ/bit vs GPU estimate 0.6 TB/s and 10 pJ/bit ([Architecture Deep Dive](https://www.cerebras.ai/blog/cerebras-architecture-deep-dive-first-look-inside-the-hw-sw-co-design-for-deep-learning); [WSE whitepaper](https://raw.githubusercontent.com/bojieli/ai-infra-book/main/references/text/cerebras-wse3.txt)).
- **No partitioning needed:** MatMults up to 100,000×100,000 run without splitting; layer-by-layer execution devotes the whole wafer to one layer at a time ([Architecture Deep Dive](https://www.cerebras.ai/blog/cerebras-architecture-deep-dive-first-look-inside-the-hw-sw-co-design-for-deep-learning); [arXiv:2503.11698 §3.3](https://arxiv.org/html/2503.11698v1)).

### Inferences
- **Why von Neumann is avoided:** the classic bottleneck is the instruction/operand fetch from a centralized memory through a narrow bus. Cerebras removes both fetches: program is resident and static per core; operands are resident in per-core SRAM at full datapath bandwidth; coordination is data-driven over a low-latency mesh. Compute moves to data (weights stream past stationary activations) rather than data moving to a distant ALU. This is "in-memory/spatial computing," and it is the structural reason decode has no memory wall.
- **Verdict — transferability to 16 GB M4:** **Hardware-level dataflow is impossible to transfer** (no wafer mesh, no per-core SRAM, no data-triggered core hardware; M4 is a conventional load/store GPU/CPU with a unified LPDDR memory hierarchy). **Software analogies** exist — static graph capture/fused kernels (Metal, MPS), double-buffering/async copies to overlap I/O with compute, keeping activations resident in registers/SRAM — but they cannot remove the memory hierarchy, only hide latency partially. The insight worth stealing: *make weights stream past stationary activations, overlap reduction with next-step math, and keep the working set in the fastest tier.*

### Gaps
- No source quantifying how Cerebras's compiler decides the x/y split for a given (B,S,H) beyond the coarse description above.
- No public details on how the dataflow model interacts with *speculative decoding* draft/target models on the same wafer.

## Key Question 5: The transferable insight for a conventional machine (Apple M4, 16 GB unified memory, SSD-offloaded MoE) — impossible vs software idea

### Takeaway
Fundamentally impossible to transfer: wafer SRAM capacity (44 GB), 21–43 PB/s bandwidth, on-wafer fabric, dataflow cores, vertical power delivery — these are the *source* of the I/O-wall elimination. Transferable as software ideas: keep the entire active working set in one fast tier, stream/move *activations* (not weights) where possible, overlap I/O with compute asynchronously, speculative decoding, store-time quantization with on-the-fly dequant, and raise MoE arithmetic intensity via effective-batch tricks. For **bit-exact MoE decode of a 70B/120B model on 16 GB**, the central trick cannot apply — the weights cannot fit at all.

### Cited Findings
- M4-class context (for reasoning, not from a Cerebras source): unified memory is LPDDR-class (~100–150 GB/s), orders of magnitude below HBM's ~3 TB/s and Cerebras's 21 PB/s; SSD is far slower still. A 16-bit 70B model is 140 GB ([Introducing Inference](https://www.cerebras.ai/blog/introducing-cerebras-inference-ai-at-instant-speed)).
- Cerebras's own comparison frames the whole problem as bandwidth: 10 tok/s needs 1.4 TB/s, 1,000 tok/s needs 140 TB/s; the solution chosen is "build the largest chip and store the entire model on-chip" ([Introducing Inference](https://www.cerebras.ai/blog/introducing-cerebras-inference-ai-at-instant-speed)).
- Cerebras's inference stack gains (portable in spirit): async wafer I/O overlapped with compute; optimized fused kernels; speculative decoding ([3× faster](https://www.cerebras.ai/blog/cerebras-inference-3x-faster)).
- Cerebras's storage-level quantization with on-the-fly dequant and full-precision activations/KV cache ([inference docs](https://inference-docs.cerebras.ai/models/overview)) — directly analogous to common "quantize weights in storage, dequant in registers" schemes on Apple Silicon, though not bit-exact.
- MoE-offload diagnosis that transfers: non-deterministic routing forces all-experts-resident or per-token offload; sparse top_k lowers arithmetic intensity ~88% and makes experts I/O-bound ([MoE at Scale](https://www.cerebras.ai/blog/moe-guide-scale)).

### Inferences
- **What is fundamentally impossible (requires the wafer):** (1) holding >16 GB of bit-exact weights in the fastest tier; (2) petabyte/s SRAM bandwidth; (3) stationary-activation, streaming-weight dataflow with per-core local memory; (4) single-cycle global fabric + broadcast/reduce; (5) multi-wafer 2 μs layer-parallel scaling. Any M4 16 GB solution remains I/O-bound for large MoE.
- **What is a software idea and transfers:** (1) keep the *hot* weights (active experts + attention) in one fast tier and stream the rest lazily; (2) overlap NAND/SSD reads with Metal compute via double buffering; (3) speculative decoding to cut full-weight passes; (4) quantize only in storage, dequant on load (sacrifices bit-exactness); (5) group/batch tokens or use BTA-like tiling to raise expert arithmetic intensity; (6) keep KV cache in fast memory and full precision.
- **Bottom-line verdict:** For a 16 GB M4 with **bit-exact MoE decode**, the Cerebras insight reduces to a *limiting principle* — "every off-chip weight read per token is a tax; minimize, amortize, and overlap it" — not a portable recipe. Bit-exact 70B/120B decode is physically impossible without ≥140 GB of fast memory, so quantization/offload is mandatory and the wall remains. The realistic M4 target is small dense or heavily quantized MoE that fits in 16 GB, where these software ideas help but cannot reproduce Cerebras-class speed.

### Gaps
- No source directly addresses Apple M4 / unified memory in the Cerebras materials; the M4-specific verdict is an inference from the bandwidth arithmetic, not a cited Cerebras claim.
- No benchmark of speculative-decoding overhead vs benefit on a 16 GB machine for bit-exact MoE.

## Key Question 6: Cerebras vs Groq (LPU, SRAM) vs GPU HBM — same idea of eliminating off-chip weight reads? Compare

### Takeaway
All three attack the memory wall, but only Cerebras and Groq *eliminate* off-chip weight reads by holding weights in on-chip SRAM; GPUs instead maximize off-chip HBM bandwidth and rely on reuse/batching. Cerebras = huge SRAM + dynamic dataflow + sparsity (one big chip); Groq = small SRAM + fully deterministic compiled schedule (many chips); GPU = large HBM + flexible general-purpose parallelism.

### Cited Findings
- **Groq LPU:** flat SRAM-first architecture, ~500 MB high-speed on-chip SRAM as primary working storage (older docs: 220 MiB/chip), **no HBM on chip**, ~80 TB/s SRAM bandwidth, ~1–5 ns SRAM latency; execution is fully deterministic ("every execution step completely predictable to the smallest execution period") by eliminating contention for data bandwidth and compute ([NVIDIA Groq 3 LPX developer blog](https://developer.nvidia.com/blog/inside-nvidia-groq-3-lpx-the-low-latency-inference-accelerator-for-the-nvidia-vera-rubin-platform/); [Groq LPU explained](https://groq.com/blog/the-groq-lpu-explained); [Hacker News discussion](https://news.ycombinator.com/item?id=39431989); [DigitalOcean comparison](https://www.digitalocean.com/community/conceptual-articles/inferentia2-tpu-groq-lpu-vs-gpu-llm-serving)).
- **Groq scale-out cost:** because SRAM per chip is tiny (220 MiB–500 MB), large models (e.g., Mixtral 8×7B) need many chips and a deterministic scale-up network; no off-chip memory means weights for big models must be distributed across chips ([DigitalOcean](https://www.digitalocean.com/community/conceptual-articles/inferentia2-tpu-groq-lpu-vs-gpu-llm-serving); [HN](https://news.ycombinator.com/item?id=39431989)). New "Groq 3 LPX" (2026) raises on-chip SRAM to 8 GB per tray with a 500 MB working SRAM block ([NVIDIA Groq 3 LPX](https://developer.nvidia.com/blog/inside-nvidia-groq-3-lpx-the-low-latency-inference-accelerator-for-the-nvidia-vera-rubin-platform/)).
- **Cerebras vs Groq directly:** Cerebras was 2.4× faster than Groq on Llama-3.1-8B at launch (1,800 tok/s) ([Introducing Inference](https://www.cerebras.ai/blog/introducing-cerebras-inference-ai-at-instant-speed)); by 2025 Cerebras argued Blackwell had "leapfrogged small-chip AI competitors like Groq" while Cerebras still led by ~5× on GPT-OSS-120B ([Blackwell vs Cerebras](https://www.cerebras.ai/blog/blackwell-vs-cerebras)).
- **GPU HBM baseline:** H100 80 GB HBM3 @ ~3 TB/s (or 3.3 TB/s in Cerebras's framing); B200 8 TB/s HBM3e + 1.8 TB/s NVLink; GPU datapath bandwidth is typically ~100× memory bandwidth, forcing operand reuse (GEMM-only at full rate) ([arXiv:2503.11698](https://arxiv.org/html/2503.11698v1); [Introducing Inference](https://www.cerebras.ai/blog/introducing-cerebras-inference-ai-at-instant-speed); [Architecture Deep Dive](https://www.cerebras.ai/blog/cerebras-architecture-deep-dive-first-look-inside-the-hw-sw-co-design-for-deep-learning)).
- **Cerebras architecture comparison (third party):** WSE-3 ~3.5–3.9× H100 FP8 peak, ~7–7.8× FP16; vs B200 ~1.1–1.16× FP8, ~2.15–2.31× FP16; but on ISO perf/watt/$ the B200 is 1.5–3× better due to wafer cost ([arXiv:2503.11698](https://arxiv.org/html/2503.11698v1)).

### Inferences
- **Same idea at the abstract level:** both Cerebras and Groq say "put weights in SRAM so decode doesn't read off-chip memory per token." The difference is *capacity and control*: Cerebras has 44 GB per chip and dynamic dataflow (handles sparsity, bigger models per chip, splits at layer boundaries); Groq has ~0.2–8 GB and a fully deterministic, compiler-scheduled machine (predictable latency, but many chips and rigid scheduling for large models). GPUs accept off-chip reads but provide the largest, most flexible memory (80–192 GB HBM) and amortize via batching/parallelism.
- **The von-Neumann angle:** Groq attacks *control* unpredictability (determinism) plus keeps weights local; Cerebras attacks *both* memory locality and control via dataflow and distributed SRAM. GPUs retain the classic fetch/decode/execute with off-chip operands.
- **Verdict — transferability to 16 GB M4:** none of the three SRAM fabrics is present on M4. The only portable lesson across all three is "minimize off-chip weight movement per token." For bit-exact 70B/120B MoE on 16 GB, none of the architectures' central mechanism fits; Groq's approach (many deterministic chips) and Cerebras's (one huge wafer) are both hardware-scaling answers unavailable on a laptop. M4 must rely on the software mitigations in Key Question 5.

### Gaps
- No apples-to-apples 2026 third-party benchmark of Cerebras vs Groq vs Blackwell on the *same* model and precision under identical latency constraints (Cerebras's comparison blog is first-party).
- Groq SRAM figure differs across sources (220 MiB older, 500 MB current, 8 GB for Groq 3 LPX tray); these likely refer to different generations/levels of the hierarchy — report-writer should be precise about which.
