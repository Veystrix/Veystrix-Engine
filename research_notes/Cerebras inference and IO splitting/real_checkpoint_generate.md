# real_checkpoint_generate — C++ generation from the REAL 113 GB checkpoint

Owner note for `cpp/engine/tools/real_checkpoint_generate.cpp`,
`cpp/engine/tools/gen_real_config.py`, `cpp/engine/tools/check_real_parity.py`.
No shared engine source was modified.

## What was built

A standalone C++ executable that runs the full Qwen3.8-Flash-Next decode stack
against the real Q4 affine checkpoint, entirely in C++ after the flat config is
generated:

* **Dense weights**: `mx::load_safetensors` reads every non-expert tensor from
  the 17 shards that hold them; affine-Q4 triplets are materialized with
  `mx::dequantize(w, scales, biases, 32, 4, "affine")` (scales/biases byte-viewed
  as bf16 where needed). `mx::load_safetensors` is mmap-backed, so only the
  tensors actually dequantized become anonymous GPU memory.
* **Embedding / lm_head**: kept packed. The embedding row is dequantized after a
  `mx::take` (exactly what Python's `QuantizedEmbedding` does), and the final
  projection uses `mx::quantized_matmul` (exactly what `nn.Linear` + `nn.quantize`
  does). This saves ~2.5 GB and removes two sources of divergence.
* **Experts**: served per step by `StreamingMoE` (36 single-shard layers) and by
  an in-file `CrossShardMoE` (12 layers whose 9 expert tensors split across two
  adjacent shards — the shared `StreamingMoE` deliberately fails closed on
  those). Both use the same native pager (`plan_remap` + `run_batched_reads`)
  and the same `moe_block` gather_qmm path.
* **Decoder loop**: a byte-for-byte adaptation of `run_decoder_step_full` with
  the routed-expert source swapped to the streamers. `run_decoder_step_full`
  cannot accept streamed experts: it recomputes the raw router indices
  internally and would gather stale slots. Every other primitive call (`gated_residual`,
  `gdn_layer_forward`, `router`, `moe_block_with_shared`'s shared-expert combine,
  `final_head`'s mixer) is identical and in the same order.
* **Attention**: 36 GDN linear layers + 12 QSA full-attention layers from
  `config.json`'s `layer_types` (3:1 cadence). For <2048 past tokens the QSA
  indexer returns `None` in production, so the dense causal-attention fallback
  is composed here (the library's `full_attention_forward` throws on `None`).
* **Generation**: 16 deterministic prompt tokens (regenerated by the config
  helper from numpy seed 20261117 and verified against `prompt_sha256`), fed as
  sequential single-token steps, then greedy decode. Per-step logit SHA-256 is
  the float32-LE digest of the full logit row, identical to
  `veystrix_native_generate.cpp` / `capture_real_reference.py`.

## Why the flat config instead of a C++ JSON parser

`gen_real_config.py` reads `config.json` + `model.safetensors.index.json` +
`reference.json` and emits `key=value` lines including `shard.<tensor>=<file>`
and the verified prompt ids. The C++ generator accepts it as an optional 4th
argument, or finds it at `<reference-dir>/real_config.txt` automatically, so
the documented 3-argument invocation works unchanged. This avoids a C++ JSON
parser and avoids re-implementing numpy's PCG64 RNG for the prompt ids.

experts, and produces greedy tokens + logit digests without Python in the loop.

**Additional finding: run-to-run nondeterminism.** Three independent invocations
of the same binary/config produced three DIFFERENT step-0 tokens + digests:
`out=186204 sha=0d77c7…` (first smoke test), `out=145166 sha=388147…` (the 8-token
gate run above), and `out=229910 sha=d6334e…` (an immediate 1-token rerun, same
binary). The most likely source is `mx::quantized_matmul` for the lm_head
(split-K/atomic GPU reduction); the custom GDN kernel and the fused SDPA are
other candidates. Consequently even a numerically-close port would not give a
stable SHA-256 gate. This is reported, not hidden.

Peak memory footprint ~13.5 GB on a 17.2 GB machine (dense dequantized weights
~8 GB, plus the mmap'd shards and MLX caches); a full 8-token run takes ~6 min,
dominated by the per-step expert-row reads (no sustained benchmark loop was
run). A single 1-token run takes ~4 min.

## Known divergence sources (all documented, none papered over)

1. **Quantized vs dense dense-matmuls.** Python's `nn.quantize` runs
   `mx.quantized_matmul` for every dense projection (GDN in/out, hyper-connection
   down/up/inject, MoE gate, shared expert, QSA q/k/v/o/index). The C++ engine
   primitives take dequantized bf16 weights and use `mx::matmul`; the two
   kernels accumulate in a different order. We matched the lm_head and
   embedding by keeping them packed, but the other ~48 layers' projections are
   dequantized. This alone changes the logits at step 0.
2. **PLE layer omitted.** `ple_layer_ids=[2]` gives layer index 1 a
   `Qwen4ExpPLELayer` (n-gram embedding + gated short conv) that is added to the
   hidden state before its hyper-connections. `run_decoder_step_full` has no PLE
   hook, so this additive term is missing.
3. **Sequential prefill.** The reference prefills 16 prompt tokens as one
   chunk (full conv + chunked GDN scan, dense SDPA); we feed them one token at a
   time (the only shape `run_decoder_step_full`'s MoE reshape supports, and the
   GDN path is token-by-token anyway). Different numerics.
4. **Dense vs int8 KV cache.** Production uses `QSAQuantizedKVCache`; the C++
   full-attention path concatenates dense bf16 K/V.
5. **Eager vs fused RoPE.** `qsa_apply_rope` reproduces `mx.cos/sin` (~1 ULP from
   the fused Metal kernel production uses).
6. **Shared expert as dense GLU.** The real shared expert is stored affine-Q4;
   `moe_block_with_shared` expects dense gate/up/down, so we dequantize them
   (divergence 1 applies again).
7. **No prefix cache / prompt lookup / MTP** replay in this single-shot run.

Bit-exact parity on the real model was explicitly not guaranteed (the primitives
are bit-exact only on tiny f32 configs); this note records where it breaks.
