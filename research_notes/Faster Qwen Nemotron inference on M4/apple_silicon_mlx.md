# Apple Silicon (M4) / MLX / Metal / macOS platform techniques for memory-bound MoE decode + prefill (zero quality loss)

Scope: 2024–2026 sources. Hard constraint from the parent task: NO quality loss — bit-identical digests, BF16 rounding must be preserved. Context: Veystrix, private macOS app, MLX, 16 GB M4, Qwen3.8-Flash-Next MoE 4-bit ~2.3 tok/s, SSD-read bound (~809 MB physical reads/token, memory pressure + compressor active), Nemotron ~6.7 tok/s; targets Qwen>=5, Nemotron>=15 tok/s.

ALREADY MEASURED AND REJECTED — do NOT propose as novel (from parent task): ANE as executor/expert cache (GPU 74.9 vs ANE 23.2 tok/s, ANE ~12x lower bandwidth, INT4 unsupported, 2 GB program cap); Core ML ANE offload (3.3% slower, 21 ms marshalling); F_NOCACHE (8% slower); F_RDAHEAD=0 (1.3%, below band); wired-limit sysctl iogpu.wired_limit_mb (+13.5% standalone, -0.4% in harness); more I/O workers (SSD saturated); pools >2 GB. **Every ANE-based approach is explicitly out of scope — flag as rejected.**

Epistemic note: this repository contains many 2026-dated community sources of variable quality. I have preferred primary sources (Apple ML Research, ml-explore GitHub, arXiv, llama.cpp issues/PRs) and flagged aggregator/estimate numbers. Where I found no controlled source, I say so.

## Key Question 1 — MLX-specific optimizations (mx.compile, custom Metal kernels, fused operators, lazy/async eval, unified memory zero-copy, array layouts, GPU residency, distributed/ring)

### Takeaway
For a memory-bandwidth-bound MoE decode, `mx.compile`/fusion helps mainly by removing dispatch overhead on the many small "glue" ops (2.8x on synthetic glue chains, but only 1.04–1.10x on real single-token decode), while hand-written Metal kernels win 1.7–3.3x specifically on reductions (RMSNorm) — but NOT on elementwise or big GEMVs. The genuinely underexploited MLX levers for this workload are async eval (mlx-lm already runs one step ahead via `mx.async_eval`), ResidencySet sharding (merged MLX PR #4211 for macOS 27), buffer-limit env vars (5–8%), and continuous batching/prefix caching (4.3x at 16 concurrent). Fusion is generally bit-exact in the sense that it preserves per-token math, but must be verified — one fully fused kernel was bit-exact yet 8% slower, and quantized kernels accumulate in fp32 for quality.

### Cited Findings
- MLX is lazy: ops build a graph, nothing runs until `mx.eval`; `mx.compile` traces the graph once and fuses ops so a forward pass goes to GPU as a single command buffer. Measured on M2 Max: a chain of small elementwise ops ran ~4.7 ms eager vs ~1.7 ms compiled (~2.8x); wrapping the same chain around two large matmuls gave NO speedup because matmuls dwarf dispatch overhead — fusion pays off on the small-op glue, not matmul-bound code. — [TensorFoundry](https://tensorfoundry.io/blog/mlx-under-the-hood)
- `mx.fast.*` ships four hand-written fused Metal primitives — `layer_norm`, `rms_norm`, `rope`, `scaled_dot_product_attention` — plus `metal_kernel`. On M2 Max (MLX 0.31.1), compile's inference gain is small because once SDPA and matmul do the heavy lifting, Python/dispatch overhead dominates: e.g. (12 layers, B=1,T=1,D=768,H=12,FF=3072) eager 1.92 ms/tok vs compiled 1.83 ms/tok = 1.05x; (8 layers, D=512) 0.66→0.64 = 1.04x. The real inference win is `mx.fast.scaled_dot_product_attention` (avoids materializing a ~4 GB attention matrix at long context). — [Nipun Batra](https://nipunbatra.github.io/blog/posts/2026-04-25-mlx-kernel-fusion.html)
- Hand-written Metal kernel decision rule on a 16 GB M3: elementwise SwiGLU fusion reached parity with `mx.compile` (0.98–1.17x, no point); RMSNorm reduction beat `mx.compile` by 1.7–3.3x every trial (cross-thread partial-sum reduction the compiler cannot generate); online-softmax correct version was 13–33x slower than expert FlashAttention kernel. — [Prasad Khake](https://prasadkhake.com/blog/metal-kernels-from-scratch)
- Ollama's June 2026 MLX engine update: "up to 20% faster" by fusing several ops into single Metal kernels via MLX's JIT compiler features and reworking GPU-backed sampling; NVFP4 generates ~20% faster than q4_K_M (NOTE: NVFP4 is a quantization change — OUT under the no-quality-loss constraint). — [Ollama blog](https://ollama.com/blog/mlx-performance)
- Unified memory is genuinely zero-copy: an MLX array is visible to CPU and GPU alike; no `.to("gpu")`; weights are GPU-readable the moment they load. Quantized matmul runs QMV (matrix-vector) for decode and matmul (matrix-matrix) for prefill; quantized kernels accumulate in fp32 for quality. — [TensorFoundry](https://tensorfoundry.io/blog/mlx-under-the-hood)
- MLX eval internals (M3 Ultra): a chain of 3,200 tiny dependent kernels costs ~2.75 µs each; each command-buffer boundary ~20 µs of GPU time; decode spans 45–90 command buffers because weights count toward MLX's 40–50 MB-per-buffer limit. mlx-lm runs one step ahead with `mx.async_eval` (generate.py); `mx.compile` fuses only elementwise/broadcast ops. CPU↔GPU sync ~181 µs by default; env `MLX_METAL_FAST_SYNCH` replaces shared events with a GPU spin-wait fence (documented as able to deadlock). — [jiazhihao/mpk-apple research notes](https://github.com/jiazhihao/mpk-apple/blob/main/docs/research/apple-inference-systems.md)
- Overhead-only wins demonstrated: +5–17% each, ~1.25–1.3x cumulatively — llama.cpp concurrent dispatch 1.10–1.17x; MoE routing/reduce fusion 1.12–1.16x on Qwen3.5-35B-A3B; MLX buffer limits 5–8% on a ~1,600-kernel/token model; mlx-swift-lm 1.25–1.3x on MoE decode. **Important negative:** dependent 4-bit GEMVs run as fast as independent ones (dispatch boundaries free at real sizes, mlx-lm PR #1676); a fully fused kernel was bit-exact but 8% SLOWER (mlx-vlm #2281); a fused cast+norm+projection prologue was 22x slower; MLX maintainers declined a fused-layer "mega kernel" (#3313) due to per-architecture maintenance burden. — [jiazhihao/mpk-apple](https://github.com/jiazhihao/mpk-apple/blob/main/docs/research/apple-inference-systems.md)
- Env-var evidence from PLaMo 3 Translate 2B (M1 Max 32-core, MLX 0.31.1): using `MLX_MAX_OPS_PER_BUFFER=4096` and `MLX_MAX_MB_PER_BUFFER=1000000`, fused 4-bit kernels hit 170 tok/s vs 107 tok/s plain MLX ops (~1.59x) with essentially unchanged chrF (87.4/84.5 vs 87.4/84.8 — small differences declared not a quality ranking); plain 4-bit was only 93 tok/s with default limits. Fused kernels broke 5.75 ms/token down as 96 projections 73%, 24 attention dispatches 13%, lm_head+argmax 8%, 48 norm dispatches 6%; 4-bit matvec ~650 GMAC/s vs 530 for `mx.quantized_matmul`. — [pfnet/plamo-translate-cli benchmark](https://github.com/pfnet/plamo-translate-cli/blob/main/benchmarks/plamo3_mlx_20261104/README.md)
- Residency sharding (merged into MLX main, PR #4211, 2026-08-12): macOS 27 makes GPU residency decisions per `MTL::ResidencySet`; with everything in one large set, any non-related GPU op (desktop update) forces the ENTIRE model to be re-wired, stalling decode. Fix spreads wired allocations across size-capped sets (`MLX_RESIDENCY_SET_MAX_PCT`, default 5, max 32 sets); `set_wired_limit` semantics unchanged. — [MLX PR #4211](https://github.com/ml-explore/mlx/pull/4211); [resident.h](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/resident.h)
- Continuous batching / prefix caching (vllm-mlx, arXiv 2601.19139, M4 Max 128GB, 4-bit): 4.3x aggregate throughput at 16 concurrent requests; text prefix caching 5.8x on shared prefixes; multimodal prefix cache 21.7s→0.78s (28x). Per-model throughput: Qwen3-30B-A3B 109.7 tok/s, Nemotron-30B-A3B 121.8 tok/s (1.43x over llama.cpp). — [arXiv 2601.19139](https://arxiv.org/pdf/2601.19139)
- Distributed/ring: Apple's MLX distributed inference over Thunderbolt on M5 Ultra with RDMA reports up to 4.6x TTFT and 1.6x generation (1.2 TB/s vs 819 GB/s on M3 Ultra); 4-machine tensor-parallel Qwen3.8 reached 50.89 TTFT metric vs 19.69 single M5 Ultra. This is scaling OUT, not in-place optimization. — [Apple ML Research: MLX distributed](https://machinelearning.apple.com/research/mlx-distributed-inference); [NukeTorch report](http://nuketorch.ai/reports/qwen-flash-next.pdf)

### Inferences
- For Veystrix's single-user, memory-bound MoE decode, the highest-value MLX-side changes are (a) confirm `mx.async_eval` one-step-ahead is active in the generation loop, (b) raise `MLX_MAX_OPS_PER_BUFFER`/`MLX_MAX_MB_PER_BUFFER` env caps to cut command-buffer boundaries (5–8% class), and (c) on macOS 27+, ensure MLX build includes ResidencySet sharding (PR #4211) — but note the parent already rejected the *sysctl* wired-limit lever, which is distinct from these.
- `mx.compile` and `mx.fast.*` should be treated as correctness-preserving (same math; f32 accumulation retained), hence compatible with the no-loss constraint, but expect only low-single-digit percent on single-token decode — not a path from 2.3→5 tok/s on its own.
- Do NOT pursue a fused "mega kernel" or monolithic fused GEMV: multiple independent sources show equal-or-worse performance and maintainers have declined it.
- Continuous batching/prefix caching improves throughput and prefill dramatically but not single-stream decode latency; prefix caching is bit-exact (reuses KV) and is the strongest prefill lever.

### Gaps
- No controlled measurement of `mx.compile` on a 100B-class MoE with experts paged from SSD — published gains are on models fully in memory. Whether fusion reduces the 809 MB/token SSD read is untested.
- Bit-exactness of Ollama's fused sampling path and the PLaMo fused kernels was not asserted by the sources (they report quality within noise, not identical digests) — must be validated in-repo before adoption.
- No numbers for MLX distributed/ring applied to a memory-bound single-machine 16 GB case (distributed helps by adding devices/RAM, essentially the "more memory" lever in distributed form).

## Key Question 2 — macOS-level techniques to reduce memory pressure and SSD read cost (purgeable memory, compressor tuning, large pages, VM flags, mmap/madvise, GCD I/O priorities, thermal state, low-power vs high-performance)

### Takeaway
The dominant macOS-level finding is that MLX/Metal shared-storage weight pages are pageable and get compressed by the WKdm compressor when "cold," so a large model silently pays a decompress-on-every-inference tax; the fix at the MLX API layer (`mx.metal.set_wired_limit` + cache limit + memory limit + clear_cache) dropped compressed memory 91% (19.69 GB→1.7 GB) in one case. Note this is DIFFERENT from the already-rejected `iogpu.wired_limit_mb` sysctl (which raises the system ceiling), and the parent's "pools >2 GB" rejection is a different knob again. Power/thermal state is a large, cheap lever: Low Power Mode can halve throughput (2.16–2.17x in one controlled test; 1.4–3.8x in another). There were no concrete, citable gains for large pages, GCD I/O priorities, or `madvise` tuning for LLM weights — note as gaps.

### Cited Findings
- macOS compressor (WKdm, ~2x typical, 2–4x range) compresses inactive anonymous/dirty pages; when the compressor pool fills, pages spill to actual swap. Compressor + swap are layered. When compressed memory climbs with swap, the kernel is thrashing. — [Locara macOS memory mgmt](https://locara.dev/docs/notes/macos-memory-management); [MacInternals XNU VM](https://www.macinternals.app/en/blog/virtual-memory-in-xnu)
- Metal shared-storage weight pages are pageable; if idle between inferences the kernel marks them inactive and compresses them, so the GPU must decompress before each read. `mx.metal.set_wired_limit(bytes)` marks N bytes resident/uncompressible; default 0 = nothing pinned. Case study on M1 Max with a 35 GB model: `set_wired_limit(45 GB)` + `set_cache_limit(512 MB)` + `set_memory_limit(48 GB)` before load dropped Compressed 19.69 GB→1.7 GB (-91%), free+reclaimable 3 GB→~30 GB. Author notes API works on M1/M2; untested M3/M4 Pro/Max but "behavior should be the same." — [SleepyQuant](https://sleepyquant.rest/blog/memory-compression-mlx-m1-max-april-2026)
- Six-layer MLX memory defense (same author) with 6-layer setup held compressed <1.7 GB, Metal cache <100 MB, zero freezes in 7-day run. Wired limit recommended ~70% of RAM; `mx.metal.set_wired_limit` is macOS 15+, must be strictly < total memory, cannot exceed system limit, raise via `sudo sysctl iogpu.wired_limit_mb=<MB>`. — [SleepyQuant checklist](https://sleepyquant.rest/blog/mlx-memory-safety-checklist)
- MLX 0.32.4 docs: `set_wired_limit` default 0; query real ceilings with `mx.device_info()` keys `memory_size`, `max_recommended_working_set_size`, `max_buffer_length` (single-array cap; a too-large embedding/KV tensor fails). Automatic wired limit example: M1 Max 64 GB → 51.84 GiB (~81%); 32 GB M2 Pro → ~26.8 GB (~78%). Table of optional `iogpu.wired_limit_mb` ceilings given (16 GB→12288, 32 GB→28672, 64 GB→61440, 128 GB→126976, leaving ~4 GiB out). — [MLX set_wired_limit docs](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_wired_limit.html); [Multigrid](https://multigrid.ai/learn/mlx-memory-management); [KinoMLX PERFORMANCE](https://github.com/dmlsrc/KinoMLX/blob/main/docs/PERFORMANCE.md)
- `set_memory_limit` is only a graph-evaluation guideline, NOT a hard cap (a 2 GB limit still allocated a 4.3 GB array); mlx-lm wires weights during generation via a `wired_limit` context manager in generate.py for steadier decode. — [dgrauet/mlx-field-guide](https://github.com/dgrauet/mlx-field-guide/blob/main/01-foundations/26-memory-metal-limits.md)
- mmap is the foundation for large weights: `mmap(PROT_READ, MAP_SHARED)` demand-pages only touched tensors; pages are clean/file-backed (evictable without swap write); `--mlock` wires them but is discouraged on memory-constrained Macs; `--no-mmap` only helps NFS/some cases. macOS will compress dirty pages, swap them, and slow disk I/O + GPU submission under pressure rather than jetsam-kill foreground apps. — [Locara Mac LLM playbook](https://locara.dev/docs/notes/mac-llm-optimization)
- Purgeable memory / VM flags: `NSPurgeableData`/`NSDiscardableContent`, or Mach `VM_FLAGS_PURGABLE` + `VM_PURGABLE_VOLATILE/NONVOLATILE`, let regenerable data (tokenizer caches, JIT kernels, thumbnails) be discarded first under pressure. Apple's standing advice (Quinn) is to use `DISPATCH_SOURCE_TYPE_MEMORYPRESSURE` + NSCache rather than free-memory polling. `mincore` can probe residency of mmap'd weight pages (MINCORE_INCORE/PAGED_OUT) but counts file-cache hits globally, not per-process faults. — [Locara](https://locara.dev/docs/notes/macos-memory-management); [LLMS-Explorer mincore](https://llms-explorer.com/tree/mincore-residency-probing-of-mmap-d-model-weight)
- XNU "available memory" = active+inactive+free+speculative (+compressed); pressure states trigger when non-compressed available dips below `VM_PAGE_COMPRESSOR_COMPACT_THRESHOLD`. One measurement: 8.59 GB zero-filled allocation grew working set only 3.75 GB (compressor absorbed it) — but the authors warn model weights are high-entropy and compress poorly, so this ratio is an artifact. — [XNU memorystatus_notify.md](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/doc/vm/memorystatus_notify.md); [Searoom memory pressure](https://searoom.app/blog/macos-memory-pressure)
- Power/thermal (controlled): on 32 GB M5 Air, Low Power ON vs OFF: lfm2.5:8b (MoE) 41.4 vs 89.5 tok/s (2.16x); qwen3:4b 17.9 vs 38.8 tok/s (2.17x); a 17 GB dense 27B crashed to 2.7 tok/s LP vs 6.6 tok/s HP (2.4x), thermal state stayed nominal — memory, not heat, was the wall; a 13 GB MoE (gpt-oss:20b) ran 29.4 tok/s flat and heat-free. — [Refract](https://refract.blog/en/posts/%ED%8C%AC%EB%A6%AC%EC%8A%A4-%EB%A1%9C%EC%BB%AC-llm)
- Power/thermal (controlled, M4 Max 128 GB): High Power (`powermode 2`) vs Low Power (`powermode 1`) gains 1.4–3.8x — oMLX Qwen3.6-35B-A3B-4bit 53.7→78.1 (1.45x); Ollama Qwen3.5-35B-A3B NVFP4 51.9→107.1 (2.06x); Gemma4 26B 41.8→75.2 (1.80x); dense 27B 11.1→22.3 (2.01x); DeepSeek V4 Flash 8.9→27.0 (3.03x). Diagnostics: `pmset -g therm`, `ProcessInfo.processInfo.thermalState`, `pmset -g | grep powermode`, `vm_stat` swap counters. — [kyu.co M4 Max benchmark](https://kyu.co/posts/local-llm-m4-max-benchmark-2026-05-10); [searoom thermal](https://searoom.app/blog/thermal-throttling); [vllm-metal benchmarking docs](https://docs.vllm.ai/projects/vllm-metal/en/stable/benchmarking-macos/)
- Caveat on power-mode magnitude: one survey notes the "Low Power halves speed" and "High Power avoids 15–25% sag" claims often trace to hearsay with no controlled benchmark; it recommends treating ~20–30% as a lower bound and 2x as an upper-range anecdote, and always pinning power mode when benchmarking. — [LLMS-Explorer thermal/power](https://llms-explorer.com/tree/thermal-power-and-battery-behavior-during-local)

### Inferences
- The user's "compressor active + memory pressure" symptom strongly matches the SleepyQuant pattern: without `set_wired_limit`, weight pages go cold between inferences and are compressed; because the parent's rejection was specifically the *sysctl* knob, the MLX-API `set_wired_limit` + `set_cache_limit` + `set_memory_limit` + `clear_cache` stack (and on macOS 27, ResidencySet sharding) remains an untested, zero-quality-loss candidate. Recommend measuring compressed-memory counters before/after, not assuming failure from the sysctl result.
- Ensuring High Power mode / AC power / Low Power Mode OFF is a near-zero-cost check that could alone move tokens/s by 1.4–2x — verify in the Veystrix harness before deeper work.
- mmap demand paging is already the default; `mlock`/`F_NOCACHE`/`F_RDAHEAD=0` were rejected by the parent, so avoid re-proposing file-cache VM flags.
- Purgeable memory is applicable only to regenerable scratch (tokenizer/JIT caches), not weights; it cannot reduce weight SSD reads.

### Gaps
- No concrete tok/s numbers for large pages, `madvise` flags, GCD I/O priorities, or `vm_purgeable` applied to LLM weights on Apple Silicon — no reliable sources found; likely not actionable beyond the already-rejected I/O levers.
- No direct measurement that `set_wired_limit` (MLX API) changes tok/s on a 16 GB M4 with an over-committed model (SleepyQuant only reports compressed-memory reduction and qualitative "latency drift"); the parent's harness may show a different result than the sysctl rejection.
- Apple publishes no figure for Low Power Mode's compute cost; magnitude estimates are community measurements.

## Key Question 3 — Measured effect of more unified memory (32/64/128 GB) on tok/s for 4-bit MoE (full residency eliminates SSD reads), with concrete reviewer numbers

### Takeaway
More unified memory is by far the largest-magnitude lever for the user's specific SSD-bound situation, because it converts per-token SSD reads into DRAM reads. The user's Qwen3.8-Flash-Next oQ4e is ~106.3 GB as shipped — it can never fit in 16 GB — so full residency requires a 128 GB M4 Max/M5 Max or 256 GB Ultra. Concrete measurements: the SAME model (Qwen3.8-Flash-Next oQ4e) delivers ~58.6 tok/s without MTP / 78.7 with MTP on a 128 GB M4 Max (oMLX), 63.38 tok/s mean (oMLX), 83.4 tok/s one-user (NukeTorch), and up to 160.5 tok/s on a 40-core M4 Max with Splash — versus the user's 2.3 tok/s SSD-bound. That is a ~25–70x magnitude class, dwarfing all software levers. Even holding bandwidth constant, Apple measures generation speed as purely bandwidth-bound (M5 vs M4: 1.19–1.27x from bandwidth alone).

### Cited Findings
- Apple ML Research (primary): TTFT is compute-bound; subsequent generation is memory-bandwidth-bound. M5 vs M4 MacBook Pro 24 GB: M5 bandwidth 153 GB/s vs M4 120 GB/s (+28%) → generation speedup only 1.19–1.27x, but TTFT speedup 3.33–4.06x. Qwen3-30B-A3B-MLX-4bit: 17.31 GB memory, 1.25x gen speedup, 3.52x TTFT. "24 GB can easily hold ... a 30B MoE 4-bit quantized, keeping the workload under 18 GB." — [Apple ML Research: M5/MLX](https://machinelearning.apple.com/research/exploring-llms-mlx-m5)
- mlx-lm official BENCHMARKS (64 GB M4 Max, mlx 0.29.2, mlx-lm 0.28.2): Qwen3-30B-A3B-Instruct-2507 4-bit = 1753.90 prompt tok/s, 113.33 generation tok/s, 18.20 GB; Qwen3-4B 4-bit = 1622 prompt, 134.52 gen, 3.35 GB; bf16 4B = 1780 prompt, 52.47 gen, 9.02 GB. — [mlx-lm BENCHMARKS.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/BENCHMARKS.md)
- vllm-mlx (M4 Max 128 GB, 4-bit): Qwen3-0.6B 525.5, Qwen3-4B 159.0, Qwen3-8B 93.3, Qwen3-30B-A3B 109.7, Nemotron-30B-A3B 121.8, all with full residency. — [arXiv 2601.19139](https://arxiv.org/pdf/2601.19139)
- Qwen3.8-Flash-Next specifically, 128 GB M4 Max (awesome-local-inference-recipes, sourced): Espetero oQ4e 58.6 tok/s without MTP, 78.7 with MTP (oMLX 81.1), 8-user aggregate 170.7; oMLX 63.38 mean (code 52.20, json 69.09); mlx-serve mixed-4 60.0 decode / 730.0 prefill; Splash 160.5 decode / llama.cpp 42.3 (3.8x) / 32K prefill 744.0; llama.cpp 23.2; one user M4 Max/M2 Ultra 45/25 tok/s. — [raytone-lab recipes](https://raytone-lab.github.io/awesome-local-inference-recipes/hw/mac-m4-max.html)
- oMLX community benchmarks, Qwen3.8-Flash-Next-oQ4e-mtp on 128 GB M4 Max 40-core: 8k context 55.7 TG tok/s, 593.5 PP tok/s, 74.3 GB peak; 1k 71.8 TG; 32k 38.0 TG / 449.7 PP; with MTP + TurboQuant KV 8-bit at 32k 61.4 TG / 786 PP; 64k 53.7–60.3 TG. On 64 GB M4 Max with the SAME model, SSD offload + expert offload was enabled (`qwen4_ple_ssd_offload true`, `moe_expert_offload_resident_fraction 0.45`) and TG fell to 12.1–16.1 tok/s at ~39–42 GB — a direct within-family demonstration that residency, not chip, is the difference. — [oMLX 128 GB](https://omlx.ai/benchmarks/performance/vrkx97zi), [oMLX 64 GB offload](https://omlx.ai/benchmarks/performance/9d5y2g2o)
- Direct SSD-paging analogy: Qwen3-Next 80B-A3B Q4_K_M on 24 GB M4 Pro via WebGPU with experts paged from disk: 2.9 tok/s, ~359 MB read from disk per token, 48.4 GB file with 4.89 GB resident, 48 s initial load; "Paged and unpaged replies were identical" — evidence that eliminating disk paging preserves outputs bit-for-bit. — [llamaperf Qwen3-Next](https://llamaperf.com/model/qwen3-next?sort=slowest)
- Hardware ceilings (rule of thumb): theoretical max tok/s ≈ memory bandwidth ÷ model size (GB); real world 60–80% of that. M4 120 GB/s / max 32 GB; M4 Pro 273 GB/s / 64 GB; M4 Max 546 GB/s / 128 GB; M2 Ultra 800 GB/s / 192 GB. — [NordicSilicon](https://nordicsilicon.io/blog/mac-mini-m4-pro-llm-benchmarks)
- NukeTorch report: model Jundot/Qwen3.8-Flash-Next-oQ4e-mtp is 106.3 GB as shipped; one user on one M4 Max (128 GB, High Power) = 83.4 tok/s default sampling, ~65 tok/s greedy per request at 8 concurrent; on four M5 Max relayed = 177.7 tok/s one user, 133.0 benchmark. — [NukeTorch report](http://nuketorch.ai/reports/qwen-flash-next.pdf)
- M4 Max vs M5 Max generation improvement is only ~12–15% (bandwidth 546→614 GB/s), while prefill improves up to 4x from Neural Accelerators; 128 GB max is unchanged. — [LLMCheck M5 Max guide](https://llmcheck.net/blog/apple-silicon-m5-max-local-ai-guide); [thebytelab](https://thebytelab.com/m5-max-local-ai-benchmark-qwen)

### Inferences
- The parent's 809 MB/token physical-read symptom means the ~106 GB model is almost entirely on SSD. Moving to 128 GB unified memory (M4 Max/M5 Max) makes the whole model resident and is the ONLY candidate that plausibly reaches the 5–15 tok/s target by 10x+ margin — it is a hardware/deferred lever, not a code optimization, and it is bit-exact (same weights, "paged and unpaged replies were identical").
- 32/64 GB is insufficient for a 106 GB model: the 64 GB M4 Max data shows fallback to SSD offload/expert offload at 12–16 tok/s — still below target. 128 GB is the minimum for full residency; 256 GB Ultra adds headroom for KV cache at long context.
- Even without a hardware change, reducing the WORKING SET (more aggressive expert residency, smaller KV cache) to minimize SSD reads per token is the software proxy — but the parent already rejected "pools >2 GB" and ANE expert caching, so explore in-RAM expert residency fractions within MLX only if not already covered.

### Gaps
- No reviewer benchmark isolates "same chip, same model, 16 GB vs 128 GB" for Qwen3.8-Flash-Next — the 16 GB figure (2.3 tok/s) is the parent's own and the 128 GB figures are on Max-class chips with higher bandwidth too, so the 25–70x estimate conflates residency and bandwidth/chip.
- No source giving tok/s specifically for Nemotron (the user's second model) at 4-bit MoE with full residency on M-series beyond the vllm-mlx 121.8 tok/s figure; M4 base 16 GB Nemotron ~6.7 tok/s is parent-supplied.

## Key Question 4 — llama.cpp Metal, mlx-lm, mlx-vlm, Apple MLX examples tok/s on M4 for 4-bit MoE (Qwen/GMix/DeepSeek) and undocumented flags

### Takeaway
For supported MoE architectures MLX is consistently the fastest engine (2–3x ollama, ~1.5x llama.cpp in controlled comparisons); llama.cpp Metal has a documented dense-decode dispatch-overhead deficit (~2x left on the table) but MoE decode is fine. Undocumented/env flags worth noting: `GGML_METAL_N_CB=4` (llama.cpp command-buffer count), `COREAI_CHUNK_THRESHOLD` (Apple Core AI prefill memory dial), and a family of oMLX acceleration flags (`qwen4_ple_ssd_offload`, `moe_expert_offload_resident_fraction`, `turboquant_kv_*`, `mtp_enabled`, `dflash_*`). Caveat: MTP/speculative decoding and token-dropping features change outputs and are NOT bit-exact — exclude them under the no-loss constraint.

### Cited Findings
- Ante Kapetanovic controlled comparison (M4 Max 128 GB, Qwen3.5-35B-A3B, 10 runs, both native eval and client-side): MLX ~130 tok/s native / 90–108 tok/s HTTP; llama.cpp ~71 tok/s; Ollama ~43 tok/s. "MLX is 2-3x faster than ollama and roughly 1.5x faster than llama.cpp." Different quantizations per engine noted as limitation. — [Ante Kapetanovic](https://antekapetanovic.com/blog/qwen3.5-apple-silicon-benchmark)
- BRlin-o M4 Pro 48 GB: Qwen3-Coder-30B-A3B (MLX both backends) LM Studio 79.0 vs Ollama 65.9 tok/s gen; Gemma 4 26B-A4B (GGUF/llama.cpp) 59.5; Qwen3.5-35B-A3B (GGUF) 27.5 tok/s. Llama.cpp/GGUF broader support but 2–3x slower than MLX when architecture is supported; 32K context on 48 GB causes heavy swapping/cliff. — [BRlin-o/M4Pro-LLM-Benchmark](https://github.com/BRlin-o/M4Pro-LLM-Benchmark)
- llama.cpp issue #27525 (M4 Max 36 GB): dense 27B decode 6.3–8.8 tok/s (~120–150 GB/s effective, 37% of peak) across all configs; same-machine oMLX ~35 tok/s (~280 GB/s, 68%). MoE unaffected (qwopus 35B-A3B 40–52 tok/s). Author attributes gap to per-token kernel dispatch overhead (op-by-op graph vs MLX fused graph) — a known llama.cpp Metal limitation, not hardware. — [llama.cpp issue #27525](https://github.com/ggml-org/llama.cpp/issues/27525)
- llama.cpp Metal env `GGML_METAL_N_CB=4` used with `-fa 0 -ub 16 -b 64`: Qwen3-30B-A3B Q6_K pp512 195.4 tok/s, tg128 71.0 tok/s (Intel Mac + AMD GPU via Metal v3 fork). — [llama.cpp discussion #19187](https://github.com/ggml-org/llama.cpp/discussions/19187)
- john-rocky/apple-silicon-llm-bench: Apple's new Core AI runtime matches/beats MLX on dense models but MLX wins on MoE (expert dispatch); gpt-oss-20b `COREAI_CHUNK_THRESHOLD` is a memory dial — unchunked 4096-token prefill 1439 tok/s (+16%) at 18 GB dirty footprint vs chunk-128 caps memory at 1.7 GB for 766 tok/s. - BillyMRX1/apple-silicon-llm-bench (M5 Max 128 GB, macOS 27.2, MLX 0.32.4 vs llama.cpp b12030): MLX-LM decoded faster in every config (+1.9% to +11.5%) and led prefill everywhere except 128-token prompts (llama.cpp ~6% ahead); prefill advantage +101% on 30B MoE at 8192 tokens; ~¼–½ of that gap from different default chunk sizes. Qwen3 30B-A3B MoE decoded 115–156 tok/s vs dense 8B 87–110 tok/s, needs ~18–19 GiB resident. MoE decode gap smallest between runtimes (+1.9% to +6.6%) because expert gather/scatter dominates. — [BillyMRX1/apple-silicon-llm-bench](https://github.com/BillyMRX1/apple-silicon-llm-bench)
- Mozilla benchmark (Mac Studio M4 Max 64 GB, Qwen3.5 0.8B/9B, Qwen3.8 27B): llama.cpp, llamafile, Ollama within ±3% on prompt processing; LM Studio trails on small-model prefill (fixed cost); token generation clustered for llama.cpp/llamafile/Ollama. — [Mozilla AI blog](https://blog.mozilla.ai/benchmarking-local-llm-servers-llama-cpp-llamafile-lm-studio-and-ollama/)
- llamaperf community medians: Qwen3 8B 4-bit M4 16 GB = 16.6 tok/s (2 runs), M4 32 GB llama.cpp Q4_K_M 19.7 tok/s, Qwen3-30B-A3B M4 Pro 64 GB llama.cpp 77.2 tok/s / 780.2 prefill. — [llamaperf Qwen3](https://llamaperf.com/model/qwen3)

### Inferences
- Engine choice matters less than residency for the parent's case: MLX is already the fastest and is required. Gains from switching engines are not available.
- Any "acceleration" flag that changes token distribution (MTP, DFlash draft, TurboQuant KV, A8 prefill, token-dropping) must be rejected under the bit-identical-digest constraint; prefix caching, continuous batching, fused kernels, wired memory and chunk-size tuning are the safe subset.
- llama.cpp's dense decode deficit is irrelevant (MoE is fine) and Veystrix uses MLX anyway.

### Gaps
- No mlx-vlm-specific MoE decode numbers were found (mlx-vlm appears in the fusion context only via mlx-vlm #2281). 
- The "undocumented" oMLX flags are documented in benchmark recipes, not official docs; their bit-exactness is unverified and must be tested individually.
- GMix MoE M4 benchmarks were not found (DeepSeek V4 Flash ~30 tok/s on M4 Max via ds4 q2 is the closest DeepSeek-class datapoint).

## Key Question 5 — Metal/GPU techniques (kernel fusion, quantization-aware kernels, weight layout for coalesced reads, threadgroup memory, SIMD) that reduce the SSD→GPU transfer bottleneck

### Takeaway
There is essentially no unexploited big kernel win on the compute side: on M5 Max MLX already routes ~98% of prefill matmul+attention through Neural Accelerator kernels, and 4-bit matmuls run within 1.03–1.15x of fp16 — a negative result for "find a faster kernel." For a memory/SSD-bound MoE, the transfer bottleneck is reduced less by kernel math than by (a) avoiding intermediate buffers (fused KV ops: 14.2x in one long-context case), (b) expert gather/scatter and MoE routing fusion (1.12–1.16x), (c) reduction-kernel rewrites (RMSNorm 1.7–3.3x), and (d) raising buffer/command-buffer limits. All are bit-exact or verifiable; none change quantization.

### Cited Findings
- Negative result (M5 Max 128 GB, MLX 0.32.3): ~98% of prefill matmul+attention time on NAX kernels; 4-bit matmul 1.03–1.15x fp16 cost across real Qwen3.8-27B shapes (56 TFLOPS 4-bit vs 57 fp16 on FFN up/gate); fp16 matmul tops out at 57–62 TFLOPS = hardware peak; ~80% of theoretical compute delivered. "There is no tile-tuning win to find in the dense path." — [al-engr M5 NAX coverage](https://al-engr.com/m5-nax-coverage-map.html)
- Fusing seven KV-cache ops (smooth scale, Hadamard, quantize, dequantize, inverse transform, unscale) into one Metal dispatch on Qwen3-8B-4bit M4 24 GB: at 2238-token prompt, 0.17→2.42 tok/s (14.24x) vs pure-MLX fallback; at short prompt near parity (3.16 vs 3.21); also used 6.7–12.3% less peak memory (fewer intermediate buffers). — [VeloxQuant-MLX](https://veloxquant-mlx.netlify.app/docs/blog/qwen3-8b-vecinfer-honest-benchmark)
- MoE routing/reduce fusion 1.12–1.16x on Qwen3.5-35B-A3B (llama.cpp PR #28948); concurrent dispatch 1.10–1.17x (PR #15929); per-dispatch savings ~2.6 µs; mlx-swift-lm 1.25–1.3x MoE decode. — [jiazhihao/mpk-apple](https://github.com/jiazhihao/mpk-apple/blob/main/docs/research/apple-inference-systems.md)
- Buffer-limit env vars as a GPU-side lever: `MLX_MAX_OPS_PER_BUFFER=4096`, `MLX_MAX_MB_PER_BUFFER=1000000` lifted PLaMo fused 4-bit from 116–166 (default limits) to 170 tok/s; command-buffer count 45–90 per decode step in MLX because weights count toward 40–50 MB/buffer limit. — [pfnet benchmark](https://github.com/pfnet/plamo-translate-cli/blob/main/benchmarks/plamo3_mlx_20261104/README.md); [mpk-apple](https://github.com/jiazhihao/mpk-apple/blob/main/docs/research/apple-inference-systems.md)
- SIMD/threadgroup detail that matters: reductions need cross-thread partial sums in threadgroup memory + barriers (RMSNorm example), which is exactly what `mx.compile` cannot generate — this is the one place hand Metal kernels reliably win (1.7–3.3x). Elementwise (SwiGLU) hand kernels only reach compiler parity. — [Prasad Khake](https://prasadkhake.com/blog/metal-kernels-from-scratch)
- Quantization-aware layout: MLX switches between QMV (decode, one activation vector) and matmul (prefill); quantized kernels dequantize on the fly and accumulate in fp32. At M=2048 prefill, 4-bit/5-bit GEMMs are within 3–15% of fp16; the small-M pathology (1.5–1.8x slower) from mlx issue #3584 appears only at small batch / speculative decode, not prefill. — [al-engr](https://al-engr.com/m5-nax-coverage-map.html); [TensorFoundry](https://tensorfoundry.io/blog/mlx-under-the-hood)

### Inferences
- For the SSD→GPU bottleneck specifically, kernel math is NOT the constraint — the parent has already established SSD saturation and rejected more I/O workers. The only kernel-side moves that help are those that reduce bytes moved or intermediate allocations: fused KV ops, expert-routing fusion, and keeping weights GPU-resident (wiring/residency) so the SSD is not touched at all.
- A fused KV-cache kernel (14.2x in the cited case) is the single most promising "novel" Metal technique that is also plausibly bit-exact (same arithmetic, fewer materializations) — but it was measured with TurboQuant 4/8-bit KV (a quantization change); verify whether an unfused-but-fused-dispatch version preserves BF16 KV exactly.
- Any quantization-aware kernel that changes bit-width or rounding is OUT under the constraint; the safe kernels are fused-dispatch versions of the existing fp32-accumulating ops.

### Gaps
- No source specifically measures coalesced weight layout / threadgroup reuse for MoE expert gather from SSD on M4; expert gather/scatter is cited as the dominant MoE decode cost in BillyMRX1 but no layout-level numbers were found.
- Bit-exactness of the fused KV ops and MoE routing-fusion kernels was not asserted (quality reported via chrF/GSM8K, not identical digests) — must be validated in-repo.

## Cross-cutting summary for the report writer (ranked, with quality-loss status)

1. **More unified memory → full residency (128 GB M4/M5 Max or 256 GB Ultra)** — largest magnitude (~25–70x vs SSD-bound; same-model 128 GB oQ4e = 58–83 tok/s, one 40-core M4 Max 160.5 with Splash). Bit-exact. Deferred hardware lever. [oMLX](https://omlx.ai/benchmarks/performance/vrkx97zi); [NukeTorch](http://nuketorch.ai/reports/qwen-flash-next.pdf); [raytone-lab](https://raytone-lab.github.io/awesome-local-inference-recipes/hw/mac-m4-max.html)
2. **High Power / AC / Low Power OFF** — 1.4–2.17x, zero quality loss, just verify harness state. [kyu.co](https://kyu.co/posts/local-llm-m4-max-benchmark-2026-05-10); [Refract](https://refract.blog/en/posts/%ED%8C%AC%EB%A6%AC%EC%8A%A4-%EB%A1%9C%EC%BB%AC-llm)
3. **MLX memory-residency API stack** (`set_wired_limit`/`set_cache_limit`/`set_memory_limit`/`clear_cache`) + macOS 27 ResidencySet sharding — compressor dropped 91%; distinct from already-rejected sysctl; bit-exact. [SleepyQuant](https://sleepyquant.rest/blog/memory-compression-mlx-m1-max-april-2026); [PR #4211](https://github.com/ml-explore/mlx/pull/4211)
4. **Async eval one-step-ahead + buffer-limit env vars + confirm mx.compile/mx.fast SDPA** — 5–8% class on dispatch glue, bit-exact-in-principle. [mpk-apple](https://github.com/jiazhihao/mpk-apple/blob/main/docs/research/apple-inference-systems.md); [pfnet](https://github.com/pfnet/plamo-translate-cli/blob/main/benchmarks/plamo3_mlx_20261104/README.md)
5. **Prefix caching + continuous batching** — prefill 5.8x/28x, aggregate 4.3x@16; bit-exact (KV reuse); best for prefill target. [arXiv 2601.19139](https://arxiv.org/pdf/2601.19139)
6. **Fused Metal kernels for reductions (RMSNorm 1.7–3.3x) and fused KV ops (14.2x long-context)** — conditional on verifying identical digests. [Prasad Khake](https://prasadkhake.com/blog/metal-kernels-from-scratch); [VeloxQuant-MLX](https://veloxquant-mlx.netlify.app/docs/blog/qwen3-8b-vecinfer-honest-benchmark)

**Explicitly out of scope / rejected:** ALL ANE execution/offload approaches (parent: GPU 74.9 vs ANE 23.2 tok/s, 12x lower bandwidth, INT4 unsupported, 2 GB cap); Core ML ANE offload; F_NOCACHE; F_RDAHEAD=0; iogpu.wired_limit_mb sysctl; more I/O workers; pools >2 GB. Also reject under no-loss constraint: NVFP4 / lower-bit quant, TurboQuant KV, A8 prefill, MTP/speculative decoding and any token-dropping (GSM8K 91.5 vs 95.1 with default vs exact sampling).
