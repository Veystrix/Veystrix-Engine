# KV-Cache, Attention, and Prefill Optimization for MoE Transformers on 16 GB Apple M4 / MLX (Zero Quality Loss)

Scope: research only (no experiments run). Hard constraint from the parent task: no quality loss = bit-identical token digests, BF16 rounding, exact routing. Verdicts below explicitly classify each method as PASS (exact/bit-preserving), RISKY (numerically different but usually "close"), or FAIL (changes output/quality). Note the strictness: almost every attention-kernel or KV-compression change alters either logits bits or token identity in some cases, so "mathematically exact" ≠ "bit-identical under BF16."

## Key Question 1: What exact, bit-preserving prefill/attention techniques are documented?

### Takeaway
The rigorously *bit-exact* class is mostly memory-management and scheduling (PagedAttention, prefix caching, chunked prefill, split-K/FlashDecoding, wired-memory pinning) plus "IO-aware exact attention" (FlashAttention family) which is exact in math but **not bit-identical at BF16** due to online-softmax rescaling. Any quantization, approximation, or token/token-range dropping is mathematically lossy and fails the bit-identical gate.

### Cited Findings
- FlashAttention/FA2/FA3 are "IO-aware **exact** attention" algorithms — tiling + recomputation + online softmax avoid materializing the N×N matrix, reduce memory O(n²)→O(n), and are advertised as mathematically exact (not approximations). FA2 ~2× over FA1 (up to ~230 TFLOPs/s on A100); FA3 1.5–2× over FA2 in BF16 (up to ~840 TFLOPs/s) and 1.5–1.75× backward on H100. — [Stanford CRFM](https://crfm.stanford.edu/2023/07/17/flash2.html); [FA3 paper (NeurIPS 2024)](https://proceedings.neurips.cc/paper_files/paper/2024/file/7ede97c3e082c6df10a8d6103a2eebd2-Paper-Conference.pdf); [FA2 paper](https://tridao.me/publications/flash2/flash2.pdf)
- BUT FA is not bit-identical at BF16: an isolated-forward microbenchmark found FlashAttention has ~10× more numeric deviation than baseline attention at BF16 vs an FP64 golden value; deviation grows with sequence length and with more (smaller) tiles, and shrinks with larger tile sizes / more mantissa bits. Models trained with FA converge to *different weights* than baseline attention (bounded at 2–5× less deviation than low-precision training). — [Is Flash Attention Stable?, arXiv:2405.02803](https://arxiv.org/html/2405.02803v1)
- HF guidance confirms FA2 vs eager is "almost always" not bit-identical in bfloat16; expected logit differences of ~1e-3–1e-2 are considered normal (kernel reordering/fusion). — [HF Forums](https://discuss.huggingface.co/t/inconsistent-output-between-flash-attention-and-eager/170448)
- PagedAttention (vLLM): eliminates external fragmentation, cuts KV memory waste from 60–80% to <4% via paged/block allocation; memory sharing cuts beam-search/parallel-sampling overhead up to 55% (up to 2.2× throughput). Memory-management only → exact. — [vLLM blog](https://vllm.ai/blog/2023-06-20-vllm); [Modular handbook](https://handbook.modular.com/inference-optimization/pagedattention)
- Prefix caching / RadixAttention (SGLang): retains prompt+output KV in a radix tree with LRU eviction and cache-aware scheduling; exact reuse of a *matching prefix* (same tokens → same KV), so bit-identical output. Overhead measured 0.2 s of 74.3 s for 100 ShareGPT requests (<0.3%); up to 5× higher throughput; TTFT cut 87–96.5% on cache hits with 2K–8K-word shared prefixes; 2,870/2,871 prompt tokens served from cache on a warm hit. — [SGLang arXiv:2312.07104](https://arxiv.org/pdf/2312.07104); [LMSYS blog](https://www.lmsys.org/blog/2024-01-17-sglang); [AWS Builder Center](https://builder.aws.com/content/3GUFqqZkV3SYF8hD9JSTSGfpWDe/prompt-caching-for-open-weight-llms-with-sglang-radixattention)
- Chunked prefill / splitfuse: splits long prompts along the token axis, interleaving prefill with decode. Scheduling/batching only → exact math. p95 TTFT improvements on H100 at 50 concurrent requests: 32K input 2,800 ms → 890 ms; 8K 1,100 → 620 ms; slight p50 regressions (e.g., 1K 380→390 ms). — [Spheron](https://www.spheron.network/blog/llm-serving-optimization-continuous-batching-paged-attention); [vLLM optimization docs](https://docs.vllm.ai/en/stable/configuration/optimization)
- Split-K / FlashDecoding: parallelize attention over KV chunks then combine with online-softmax correction — exact in math; the Open-TQ-Metal work implements split-K as chained MLX Primitives to avoid Metal dispatch races. — [Open-TQ-Metal arXiv:2604.16957](https://arxiv.org/html/2604.16957v1)
- MLX `mx.fast.scaled_dot_product_attention` natively supports MHA, GQA, MQA and performs softmax in float32 regardless of input precision; k/v need not be pre-tiled for GQA/MQA. — [MLX 0.32.4 docs](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.fast.scaled_dot_product_attention.html)
- QSA/sparse attention variants and token dropping are NOT bit-preserving: SpecPrefill/CritiPrefill keep only top-k% prompt tokens (quality retained ~95%, ≤0.5 F1 drop) — output is definitionally different. — [Speculative Prefill arXiv:2502.02789](https://arxiv.org/html/2502.02789v1); [emergentmind survey](https://www.emergentmind.com/topics/speculative-prefill)
- KV cache offloading / prefill-decode disaggregation: scheduling/memory-tier techniques (DistServe; vLLM NIXL push connector); exact math, important under memory pressure (see KQ4). — [DistServe](https://haoailab.com/blogs/distserve); [vLLM NIXL connector](https://vllm.ai/blog/2026-10-14-nixl-push-connector)

### Inferences
- Under Veystrix's strict gate, the only cleanly PASSING "exact" prefill wins are memory/scheduling ones: prefix caching (if prompts share prefixes), wired-memory pinning, chunk-size/batch tuning, and possibly using MLX's built-in fused SDPA (which already does FP32 softmax). FlashAttention-style tiling is mathematically exact but will very likely perturb BF16 logits and break bit-identical digests — flag RISKY unless Veystrix already accepts MLX SDPA (it appears to, since "QSA fused gather/SDPA (some accepted)").
- The parent task has already rejected "pipelined attention tiles," "compiling prefill injection," and "fused-gather rounding change" — consistent with the finding that attention-tile/rounding changes are the fragile boundary. Focus should shift to scheduling/memory (prefix caching, wired memory, batch size) rather than new attention math.

### Gaps
- No source gives a bit-identical guarantee for FlashAttention at BF16 (all report some deviation); cannot claim FA passes the bit-exact gate from literature alone — needs an in-repo digest test.
- No primary source found on "ring attention" specifically on MLX/Apple Silicon (split-K/FlashDecoding is the closest documented analog).

## Key Question 2: Which give concrete TTFT / prefill throughput gains on Apple Silicon / MLX specifically (with numbers)?

### Takeaway
On Apple Silicon, the documented, relevant wins are: MLX flash-attention/SDPA matching or beating llama.cpp at long-context prefill; large prefill batch sizes (2048); FlashAttention flag in llama.cpp; wired-memory pinning to avoid SSD paging (10× recovery in one Apple Silicon study); and prefix caching / chunked prefill numbers (mostly GPU-sourced). MoE-specific "layered prefill" reports up to 70% TTFT reduction.

### Cited Findings
- MLX has a critical weakness: it does full prefill before emitting any tokens, so TTFT rises linearly with input length. Benchmark (M1 Max, 8.5K ctx, Qwen3.5-35B-A3B): prefill 49.4 s (MLX) vs 37.8 s (GGUF/llama.cpp); prefill = 94% of total time; reported 51 tok/s decode but effective wall-clock 3 tok/s. — [starmorph guide](https://blog.starmorph.com/blog/apple-silicon-llm-inference-optimization-guide) (secondary source — verify against local repro)
- On M5 Ultra (192 GB), MLX 0.22 Flash Attention vs llama.cpp b4012 Metal FA2: Qwen 3.6 27B Q4_K_M prefill at 8K = 1,840 vs 1,720 tok/s; at 32K = 1,180 vs 940 tok/s (MLX wins prefill at long context); decode ~78 vs 81 tok/s. Llama 4 Scout 109B MoE prefill at 8K = 920 vs 880 tok/s. — [Contra Collective](https://contracollective.com/blog/mlx-flash-attention-vs-metal-flash-attention-m5-ultra-2026) (M5 Ultra, not M4 — directionally relevant only)
- llama.cpp on Apple Silicon: `--flash-attn` gives faster long-context prefill + smaller per-token attention memory; "no quality downsides." Setting logical/physical batch (`-b`, `-ub`) from default 512 to 2048 measurably accelerates prefill by giving Metal kernels more parallelism. — [Medium/Hannecke](https://medium.com/@michael.hannecke/tuning-llama-cpp-on-apple-silicon-843f37a6c3dc); [OmniForge](https://omniforge.online/blog/your-local-llm-is-slow-because-of-five-config-flags)
- Wired memory: on a 39 GB model on 64 GB Apple hardware, macOS pages weights to SSD; pinning via `mx::set_wired_limit()` recovered 10× throughput (0.6 → 6.0 tok/s). Directly relevant to 16 GB M4 where KV+weights+OS can exceed RAM. — [Open-TQ-Metal §3.4](https://arxiv.org/html/2604.16957v1)
- Open-TQ-Metal (M1 Max, 64 GB, preprint): hybrid prefill/decode attention gave "66% faster prefill"; fused int4 SDPA kernel 3×→48× attention speedup from 1K→128K; split-K gave flat latency 1.6 ms@1K → 9.9 ms@128K. Quality: identical top-1 token under greedy decode (NOT bit-identical logits). — [Open-TQ-Metal](https://arxiv.org/html/2604.16957v1)
- MoE-specific layered prefill (MLSys 2026): chunked prefill inflates MoE expert-weight memory traffic by up to 39% and energy; layering scheduling by layer groups cuts TTFT up to 70%, end-to-end latency 41%, per-token energy 22% vs chunked prefill while keeping TBT. — [MLSys 2026](https://mlsys.org/virtual/2026/oral/3732); [arXiv:2510.08055](https://arxiv.org/html/2510.08055v1)
- Chunked prefill numbers (GPU, H100): p95 TTFT 32K input 2,800→890 ms, 8K 1,100→620 ms at 50 concurrency; p50 slightly worse. — [Spheron](https://www.spheron.network/blog/llm-serving-optimization-continuous-batching-paged-attention)
- Prefix-caching numbers: TTFT drop 87–90% (2K-word prefix) to 96.5% (8K prefix); up to 6.4× higher throughput on prefix-heavy traffic (RadixAttention vs PagedAttention). — [AWS Builder Center](https://builder.aws.com/content/3GUFqqZkV3SYF8hD9JSTSGfpWDe/prompt-caching-for-open-weight-llms-with-sglang-radixattention); [Spheron](https://www.spheron.network/blog/prefix-caching-explained-why-repeated-prompts-get-cheaper-to)
- Qwen3.8-Flash-Next-GGUF discussion (relevant model): llama.cpp b10715 on Windows/CUDA, 25K prompt tokens → prefill ~628 tok/s, decode ~14.9 tok/s; other reports prefill ~1,500–1,650 tok/s and decode 84→32 tok/s as depth grows 4.5K→93K (attributed to KV-cache/attention scan, not weights). — [HF discussion](https://huggingface.co/unsloth/Qwen3.8-Flash-Next-GGUF/discussions/3) (user-reported, not controlled)
- Custom Python `mx.fast.metal_kernel` attention fused kernels were "3–4× slower than native SDPA due to Python dispatch overhead and inability to leverage MLX's internal kernel fusion and memory planning"; a C++ fork (`scaled_dot_product_attention_qv`) reached near-native decode speed. — [MLX issue #3404](https://github.com/ml-explore/mlx/issues/3404)

### Inferences
- For Veystrix on a single-user 16 GB M4 (not multi-tenant serving), the most transferable levers are: (a) increase prefill batch/chunk size toward 2048; (b) ensure MLX native fused SDPA is used rather than a Python Metal kernel; (c) wired-memory pinning to avoid swap; (d) prefix caching only if real prompt prefixes repeat; (e) chunked prefill mainly helps TBT not single-request TTFT and can slightly worsen p50 TTFT, so it is not a clear single-user TTFT win.
- Published "TTFT" numbers are overwhelmingly multi-tenant GPU/H100; exact single-user M4 numbers are scarce. Treat MoE layered-prefill (70% TTFT) as promising but not validated on MLX/M4.

### Gaps
- No controlled benchmark of the two Veystrix models (Qwen3.8-Flash-Next, Nemotron) on a 16 GB M4 for prefill/TTFT; user-reported HF numbers vary widely (628 vs 1,650 tok/s) by build/backend.
- No MLX-specific implementation of layered prefill or chunked prefill for single-user decode found; vLLM's chunked prefill is enabled by default in V1 but vLLM is CUDA-only per the Apple Silicon comparison. — [Silicon Showdown arXiv:2605.00519](https://arxiv.org/html/2605.00519v2)

## Key Question 3: KV-cache compression (FP8/INT8/INT4, MQA/GQA/MLA, eviction): bit-exact vs lossy, and error bounds?

### Takeaway
All KV quantization, KV sharing changes (MQA/GQA/MLA applied post-hoc), and KV eviction are **lossy** and fail a bit-identical gate. FP8 is "negligible accuracy loss" (not zero); INT4/2-bit and eviction show measurable task degradation. Error bounds from the literature are aggregate (cosine similarity, KL divergence, perplexity, pass@1), not bit-exact guarantees.

### Cited Findings
- FP8 KV cache (vLLM): 2× KV capacity, "negligible accuracy loss," matches BF16 throughput, best default; FP8 quantizes both storage and the attention computation using native FP8 tensor cores. — [vLLM TurboQuant study](https://vllm.ai/blog/2026-05-11-turboquant); [vLLM FP8 KV blog](https://vllm.ai/blog/2026-04-22-fp8-kvcache)
- FP8 quality is context-dependent: at 2K–32K the gap vs BF16 is within measurement noise on common benchmarks, but at 128K+ numerical precision matters more and FP8 can degrade output quality; must validate on target task (≥500 samples recommended). — [Spheron FA2/FA3 guide](https://www.spheron.network/blog/flashattention-2-vs-flashattention-3-h100-h200-guide)
- INT8 KV cache (GPU study): 4× memory reduction vs FP32; "maximum per-element error bounded at 0.004; attention score error <0.1 even for 8K-dimensional heads"; quantization overhead 6–58 ms. Bounded-error, not bit-exact. — [arXiv:2601.04719](https://arxiv.org/html/2601.04719v1)
- FP4/TurboQuant: KVQuant <0.1 perplexity degradation at 3-bit (WikiText-2/C4, four-technique method); KIVI nearly unchanged quality at 2-bit with 2.6× peak-memory reduction (includes weights). — [TensorMesh](https://tensormesh.ai/learn/kv-cache-quantization)
- vLLM's controlled study (4 models incl. MoE Qwen3-30B-A3B): FP8 and TurboQuant-k8v4 recover >98% (reasoning) / match BF16 long-context within std; TQ-4bit-nc ~96% recovery with 1–4 point drops; TQ-k3v4-nc and 3bit-nc drop ~20 points on AIME25/LiveCodeBench and ~30% relative on 256K retrieval. All TQ variants reduce throughput 10–68% and add TTFT/latency overhead; FP8 is the only quant that helps. — [vLLM TurboQuant study](https://vllm.ai/blog/2026-05-11-turboquant)
- Apple-Silicon-specific: Open-TQ-Metal int4 (group=32) gives K/V cosine sim 0.998 (Llama, α=0.0884) / 0.992 (Gemma, α=1.0), KL <1e-10/<1e-8, identical top-1 under greedy — but still NOT bit-identical logits; value quantization hurts more than key (int4 K + FP32 V: 0.998 cosine vs FP32 K + int4 V: 0.994). PolarQuant is architecture-sensitive: 4-bit cosine 0.958 (Llama) vs 0.621 (Gemma, gibberish); QJL 1-bit collapses at depth (0.85^80 ≈ 0). — [Open-TQ-Metal](https://arxiv.org/html/2604.16957v1)
- K8V4 on llama.cpp (Apple Silicon patch): 59% KV-memory reduction with 0.86% perplexity loss; K4V8 same memory reduction but 6.06% perplexity loss — keys need higher precision than values. — [KVSplit / Hacker News](https://news.ycombinator.com/item?id=44009321)
- MQA/GQA/MLA are architectural (training-time) changes: MQA reduces KV by factor N but "measurable reasoning quality degradation"; GQA is the middle ground; MLA (DeepSeek-V2) compresses KV ~93.3% vs 67B dense MHA while reportedly matching/beating MHA. These are model properties — cannot be applied at inference to an existing Qwen/Nemotron checkpoint without changing weights/output. — [apxml](https://apxml.com/courses/designing-and-sizing-production-llm-infrastructure/chapter-3-inference-dynamics-attention/attention-topologies-mha-gqa); [DeepSeek-V2 discussion](https://vizuara.substack.com/p/decoding-multi-head-latent-attention); [fin.ai research](https://fin.ai/research/low-rank-key-value-attention-reducing-kv-cache-memory-and-maintaining-head-diversity)
- KV eviction: H2O 2–5× compression at ~1–2% quality loss; SnapKV 4–8× reduction at 1–3% quality loss (with ~92% prompt-KV compression at 1024 tokens on ~13K inputs); StreamingLLM keeps sink+recent tokens but drops ~39% F1 vs full cache; RefreshKV shows eviction methods fail badly on long-form tasks (0 F1 on HTML→TSV). All are irreversible token dropping → FAIL bit-exact gate and flagged "truncating invisible keys" already rejected by parent. — [daily.dev](https://daily.dev/posts/how-llms-decide-what-to-forget-kv-cache-eviction-explained-k6kfg62tc); [SnapKV NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/file/28ab418242603e0f7323e54185d19bde-Paper-Conference.pdf); [H2O analysis](https://ashwanijha.dev/blog/h2o-heavy-hitter-oracle-kv-cache-eviction-what-the-paper-actually-says); [RefreshKV ACL 2025](https://aclanthology.org/2025.acl-long.1211.pdf)
- Llama.cpp KV-quant reality check: perplexity is more sensitive to model-weight quantization than KV quantization; community verdict "more quantization = less quality." — [Reddit r/LocalLLaMA](https://www.reddit.com/r/LocalLLaMA/comments/1mhlj69/whats_the_verdict_on_using_quantized_kv_cache)

### Inferences
- For the parent's hard gate, **no** KV quantization/eviction passes. Even FP8 changes attention math and logits; "negligible" is a benchmark-level statement, not bit-identity. The relevant safe direction is memory *management* (paged allocation, prefix sharing, freeing caches promptly, avoiding over-reserved `n_ctx`) rather than compression.
- If the gate were relaxed to "argmax/token identity on a held-out set," FP8 KV would be the safest first candidate, then k8v4/4-bit; INT4/2-bit and all eviction are too risky. Error bounds worth quoting: INT8 max per-element error 0.004; int4 cosine 0.998 / KL <1e-10; K8V4 perplexity +0.86%.

### Gaps
- No published error bound of the form "BF16-rounded logits identical" for any KV quantization — such a guarantee does not exist in the literature; can only be established empirically per model/prompt.
- No source quantifies FP8/INT8 KV error specifically for Qwen3.8-Flash-Next or Nemotron on MLX.

## Key Question 4: KV-cache size vs memory pressure on 16 GB M4, and exact ways to reduce KV memory without changing output?

### Takeaway
On 16 GB Apple Silicon, KV cache + weights + OS compete for one unified pool; exceeding it triggers macOS compression/swap that can collapse throughput. Exact (bit-preserving) mitigations are memory *management*: paged/block allocation (stop over-reserving max context), prefix-cache sharing, prompt-size budgeting, wired-memory pinning, and choosing GQA-native models — not quantizing or evicting KV.

### Cited Findings
- Baseline: 16 GB unified memory is the absolute minimum for local LLMs; 24–32 GB is the balanced tier. When memory is exceeded, macOS compresses pages and uses swap; first-token latency, generation speed, and responsiveness "deteriorate sharply"; allocation can fail. — [ai-on-mac](https://ai-on-mac.com/articles/unified-memory-mac-en)
- KV math: cache = 2 × layers × KV heads × head_dim × 2 bytes (FP16) × context. Llama 3.3 8B = ~8 KB/token → 128K ctx = 1 GB; a 70B model ≈ 5.4 GB at 16K and ~40 GB at 128K. Practical rule: add ≥30% headroom over weights for KV/activations/OS. — [zachrattner calculator](https://zachrattner.com/projects/ai-mac-cluster/llm-speed-calculator); [Contra Collective](https://contracollective.com/blog/kv-cache-context-length-apple-silicon-local-inference-2026)
- Real Apple failure pattern: engineers size memory for weights, then OOM at 16K–32K tokens because KV cache was ignored; advice includes pre-allocating context to actual size (not model max), since `n_ctx=131072` on a 70B costs ~40 GB at boot. — [Contra Collective](https://contracollective.com/blog/kv-cache-context-length-apple-silicon-local-inference-2026)
- The "MLX backend requires 32 GB+" claim appears in one guide (base M4 8–16 GB "will not activate" Ollama's MLX backend) — relevant caveat for the parent's 16 GB M4 if using Ollama; but Veystrix's own MLX usage is independent of that. — [starmorph guide](https://blog.starmorph.com/blog/apple-silicon-llm-inference-optimization-guide)
- Quantized-KV memory example (lossy, reference only): 4-bit KV drops context overhead ~75% (112 KB/token → 28 KB/token; 8,192 tokens 917 MB → 229 MB). — [Lapis](https://lapis.lvrpiz.com/en/blog/how-much-ram-for-local-llm)
- Open-TQ-Metal on 64 GB: int4 KV vs FP16 let Llama-70B go from 73K → 236K max context; under burst load in vLLM (Llama-70B, 4×H100), BF16 TTFT exploded to ~17 s from KV memory saturation while compressed KV stayed <3.5 s and FP8 ~1.3 s — demonstrates memory pressure directly drives TTFT. — [Open-TQ-Metal](https://arxiv.org/html/2604.16957v1); [vLLM TurboQuant study](https://vllm.ai/blog/2026-05-11-turboquant)
- Prefix caching reduces *aggregate* KV memory by sharing prompt KV (100 requests × 2000-token prefix = 200K tokens cached → 1.5 GB Llama-3-8B FP16 without sharing). — [firecrawl radix-attention reference](https://github.com/firecrawl/ai-research-skills/blob/main/12-inference-serving/sglang/references/radix-attention.md)
- Wired memory/pinning avoids swapping weights to SSD (10× recovery in one study) — an exact, output-preserving mitigation for memory pressure. — [Open-TQ-Metal §3.4](https://arxiv.org/html/2604.16957v1)

### Inferences
- On a 16 GB M4, exact levers to reduce KV memory pressure: (1) cap context/`n_ctx` to what is actually used and free caches after each request; (2) paged/block KV allocation so short sequences don't reserve max length; (3) share common prefixes via a prefix cache if Veystrix reuses system prompts/chat history; (4) wired-memory pinning to prevent SSD paging; (5) prefer GQA-native models (both Qwen3 and Nemotron MoE use GQA/MLA-style sharing already — do not alter it). None change logits.
- Avoid the temptation of q8_0/FP8 KV "quality is invisible" advice in blogs: under the parent's bit-identical gate it is still a fail. The blog consensus ("q8_0 KV is invisible quality cost") reflects perplexity/task metrics, not token-digest identity. — [Contra Collective](https://contracollective.com/blog/kv-cache-context-length-apple-silicon-local-inference-2026)

### Gaps
- No direct measurement of Veystrix's two models' KV-cache bytes/token or the 16 GB M4 swap/compression threshold; needs local instrumentation.
- No MLX-native prefix-caching or paged-KV implementation identified (SGLang/vLLM are CUDA-oriented); feasibility of wiring radix caching into MLX is an open engineering question.
- one low-quality/secondary source (starmorph, Contra Collective) makes strong "M4 16 GB won't activate MLX" and benchmark claims; these should be verified locally before relying on them.
