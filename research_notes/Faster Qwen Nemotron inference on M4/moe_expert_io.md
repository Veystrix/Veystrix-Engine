# MoE Expert I/O, Caching, and Offloading Techniques for SSD-Bound Decode on a 16 GB Apple M4

Scope: accelerate DECODE (and TTFT) for Qwen3.8-Flash-Next (MoE, Q4 affine G32, top-10/512) from ~2.3 tok/s to >=5 tok/s and Nemotron from ~6.7 tok/s to >=15 tok/s on a 16 GB M4, with **zero quality loss (bit-exact)**. All methods already measured/rejected on this hardware (ANE, native MTP depths 1-8, lookup drafting v2, expert prefetch, decode overlap, >I/O workers, non-S3FIFO pools, pools >2 GB, perfect expert predictor, cache-aware routing, expert packing, F_NOCACHE, F_RDAHEAD=0, wired-limit sysctl, PLE row prefetch) are treated as ground truth and are NOT proposed as novel below. Note: several sources below post-date/overlap that testing; where a source claims a win for a method the user already rejected, I flag the likely reason for the discrepancy.

## Key Question 1: Which expert-reading / layout / I/O-path techniques are documented to speed MoE decode, with concrete tok/s numbers?

### Takeaway
The strongest evidence is from other Apple-Silicon M4 ports of the **exact same models**. Three bit-exact levers dominate: (1) replace mmap page faults / naive reads with **explicit, sorted, gap-merged pread of only the routed experts**; (2) **co-locate each expert's scattered sub-tensors (gate/up/down + scales/biases) into one contiguous block** ("expert coalescing"/sidecar) to cut read-ops and latency; (3) **remove per-layer CPU/GPU (Python/`mx.eval`) syncs** — on one MLX M4 profile this was 41% of per-token time vs 29% for SSD reads. Layout/coalescing is bit-exact and largely independent of the rejected "expert packing" (which grew disk by +70 GiB with no server gain; the wins here come from contiguity/IOPS, not compression or a new global pack format).

### Cited Findings
- **Exact hardware + exact model, bit-exact MLX port.** Mac mini M4 Pro (64 GB), Qwen3.8-Flash-Next (125B, 512 experts/layer, top-10), 20% expert cache (~7.4 GB): reference fully-resident 2.52 tok/s; **v1 Python pread 8.51 tok/s** (84.3% hit); **v2 native pthread pread + fewer syncs 9.17 tok/s**; v2 + router prefetch 9.73 tok/s (94.7% hit). All cached runs produced greedy output identical to reference. Per-token profile (118 ms): GPU 27%, **Python + `mx.eval` syncs 41%**, SSD reads 29%, bookkeeping 3%; fully-resident llama.cpp GGUF ceiling was 24.6 tok/s. A C++ MLX decode path was bit-exact vs Python (token ids, raw logits, 122/122 cache tensors) at 9.0-9.6 tok/s / ~11.5 GB. — [Jakevin/moe-offload](https://github.com/Jakevin/moe-offload)
- **Same Nemotron family on 16 GB M4:** Nemotron 3.5 Bolt 74B-A9B (IQ2_XXS, 240 experts/layer, top-9) on **Mac mini M4 16 GB** with 4 GB cache: **4.39 tok/s**, 86.1% hit, 8.5 GiB peak RSS (8 GB cache thrashed/aborted). Full-model baseline 13.9 tok/s at 20.8 GiB (does not fit 16 GB). On M4 Pro 64 GB the same model hit 11.07-11.28 tok/s with 4-12 GB caches. — [Jakevin/moe-offload](https://github.com/Jakevin/moe-offload)
- **Profile-free expert coalescing (9 scattered sub-slices -> 1 contiguous block), bit-exact.** Qwen3.6-35B-A3B-8bit on MLX SSD-offload: one expert = 9 sub-slices (gate/up/down × weight/scales/biases = 3.19 MiB) scattered over a 2.5 GB span. Coalescing gives **~20% faster decode, ~10% faster prefill** in the over-DRAM regime; cuts per-cold-expert read 1396 -> 463 µs (3.02×); **9× fewer decode read-ops (486 -> 54/token)**; bytes/token barely change (190 -> 182 MB) — an **IOPS/latency win, not bandwidth**. Deterministic and bit-exact, no trace needed. Optional "clique reorder" of experts (+13% decode, +37% prefill) is the part that risks changing token identity. — [mbolt gist](https://gist.github.com/doramirdor/0aeb975a99eb5a4644a3d105b57e3909)
- **On-disk layout vs mmap, same author.** On Qwen3-Next-80B-A3B IQ3_XXS (M5 Pro): mmap fault streaming is **layout-blind** (profile-guided co-activation reordering gave identical tok/s and pagein volume to stock); **explicit slice reads beat faults by +13-14% end-to-end**; interleaved layout (each expert's up|gate|down contiguous) cut cold reads/token 1418 -> ~370 = **2.23× faster cold I/O**. Caveat noted by author: token-identity cannot be guaranteed under nontrivial expert permutation (router rows must be permuted to match; "equivalent within backend FP noise"). — [llama.cpp discussion #18758](https://github.com/ggml-org/llama.cpp/discussions/18758)
- **Explicit-read prefetch, bit-exact.** Hooking the router top-k node to issue sorted, gap-merged parallel `pread`s of exactly the selected experts' non-resident slices into the page cache: **+31-52% tok/s standalone** on RAM-constrained Qwen3-Next-80B-A3B (M5 Pro, Apple SSD), no file changes; read count 28.6k -> 8.5k, avg read 450 KB -> 1.5 MB. — [llama.cpp discussion #25779](https://github.com/ggml-org/llama.cpp/discussions/25779)
- **Sidecar per-expert layout + direct I/O, bitwise identical.** Qwen3.8-Flash-Next-Coder GGUF on one M4 Pro (48 GB), macOS 26.6: GGUF stores gate/up/down separately (3 reads/expert); sidecar co-locates them (1 read/expert). Decode (3 cold runs): `--moe-cache-mib` 4096 -> 3.97 tok/s (302 MB read/token), 12288 -> 10.06 tok/s (60 MB/tok), 16384 -> 14.14 tok/s (29 MB/tok); all-GPU reference 28.04 tok/s. **Bitwise identical** logits 6/6 and greedy text 4/4. NOTE: uses `F_NOCACHE`, which the user measured 8% slower on their M4 — the transferable idea is the **sidecar contiguity**, not the page-cache flag. — [alexschiltmans per-layer-experts doc](https://github.com/alexschiltmans/llama.cpp-per-layer-experts/blob/per-layer-experts/docs/moe-ssd-streaming.md)
- **Apple Silicon, async pread + pinned cache + cross-layer prediction.** Tencent Palm-Infra (`mollm`), Qwen3.8-Flash-Next on Apple Silicon: always-used dense weights locked in RAM; async pread workers fetch only routed experts; shared cache with Least-Stale ordering. Legacy equal-per-layer cache/no prediction **10.89 t/s** (74.5% hit) -> shared cache + cross-layer prefetch **12.70 t/s** (89.3% hit). Cache sweep: 1 GiB 12.38 t/s (47.9% hit, 5.90 GiB RSS) / 10 GiB 16.19 t/s (83.5%, 14.64 GiB) / 16 GiB 16.53 t/s (88.6%, 20.60 GiB). **Expert cache pinned by default** because macOS VM compressor otherwise compresses cold anonymous buffers and decompresses them inside matmul. — [Palm-Infra ssd-offload doc](https://github.com/TencentYoutuResearch/Palm-Infra/blob/main/docs/ssd-offload.md)
- **M4 MacBook Air, span-merged multi-MB preads + fetch/compute overlap, bitwise identical.** `streamlx` (MLX): expert byte ranges span-merged into multi-MB reads; resident experts start on GPU (`async_eval`) while misses fetched; next-layer routing predicted from current residual (~70% accurate). Laguna-S-2.1 (117B, top-10/256, 2-bit) 8 GiB budget -> 3.4 tok/s, 18 GiB -> **9.2 tok/s**; model formula throughput ≈ `t_compute + miss_bytes / ssd_bandwidth`. — [srcterm/streamlx](https://github.com/srcterm/streamlx)
- **M4 MacBook Air 16 GB, internal SSD ~5.6 GB/s.** `ssdmoe`: Qwen3.5-35B-A3B (K=4) fresh process 7-8 tok/s, warm page-cache 10-12 tok/s, ~1 GB active RAM, ~2.5 GB peak on 3.6k prompt. Exposes `ROUTED_TOP_K` to trade quality for fewer SSD reads (quality-lossy — see Q3). — [RasoulNik/ssdmoe](https://github.com/RasoulNik/ssdmoe)
- **M4 Macs, GPU-vs-SSD streaming.** `SwiftLM` rewrote SSD expert streaming: M1 Ultra 64 GB, Qwen3.5-122B-A10B-4bit 0.58 tok/s (sequential pread, 1 NVMe queue) -> **4.95 tok/s (8.5×) at full top-8 quality**; M6 32 GB Qwen3.6-35B 14.1 tok/s streaming vs 48.4 GPU-resident. — [SharpAI/SwiftLM](https://github.com/SharpAI/SwiftLM)
- **Exact model, io_uring + O_DIRECT out-of-core pager, 100% byte-exact.** PR #31469 on Qwen3.8-Flash-Next (68 GB, 512 experts/layer, top-10, IQ2_XS) with 12 GB VRAM / 16 GB RAM / NVMe (RTX 3060, Linux): stock mmap 1.47/1.63 tok/s (208-235 MiB/tok) -> **`--moe-direct-io` 16.29/22.03 tok/s** (35.37/12.43 MiB/tok), 1 CUDA graph split, 100% byte-exact. Key mechanisms: compact VRAM slot pool, host RAM victim cache, batched io_uring/O_DIRECT pager, on-device KICK/WAIT doorbell overlapping shared-expert compute with miss servicing. (Linux/CUDA, but directly demonstrates how far an SSD-bound top-10/512 model can go when sync/IO path is rewritten.) — [llama.cpp PR #31469](https://github.com/ggml-org/llama.cpp/pull/31469)
- **Expert-pack layout + concurrent direct reads + lossless rANS decompression, 3-tier cache.** SSD-LLaMA: reorganizes each expert into one aligned block, per-completion async H2D to VRAM slot, lossless CUDA rANS reconstructs exact weights in VRAM; full (gate+up+down) cache gives **2.78× over no-cache**. Caching only gate/up yields higher hit rate but lower throughput — must cache all three. — [SSD-LLaMA](https://arxiv.org/html/2609.18110)
- **Other Apple-Silicon points:** omlx (mmap slab reads, bit-identical) gemma-4-26b 100%/50%/25%/12.5% residency -> 122.5/59.4/40.1/29.3 tok/s; DeepSeek-V4.1 12.5% residency on M5 Max 128 GB -> 5.6 tok/s decode. — [omlx doc](https://github.com/jundot/omlx/blob/main/docs/MoE_Expert_Offload.md); Edge0 (Mac mini M4 Pro 24 GB) Qwen3.5-35B-A3B 14.9-17.7 tok/s at ~2.9 GiB active memory. — [Edge0](https://themenonlab.blog/blog/edge0-streaming-moe-ssd-expert-offload); Mference Qwen3.8-Flash-Next 18.2-21.0 tok/s decode on 256 GB M3 Ultra, byte-identical routing A/B measured **+33.9% geometric-mean decode** from protocol change. — [Mference](https://github.com/NeelM0906/Mference)

### Inferences
- The 41%-sync finding is the single most important number for this project: on MLX, decode is only ~29% SSD-bound, so the user's framing ("SSD-read bound") may be partly an artifact of per-layer Python/`mx.eval` synchronization. Removing those syncs (native C++/Metal fused decode) is likely the highest-value bit-exact change and is NOT in the rejected list.
- Coalescing an expert's 9 sub-slices into one block (mbolt A2 / sidecar) is a *different* intervention from the rejected "expert packing": it is deterministic, bit-exact, profile-free, needs no trace, delivers ~3× per-cold-expert I/O and ~20% decode with negligible disk cost — and it composes with any I/O path. This is the most likely "novel" win.
- Explicit sorted/merged pread into the page cache (+13-52%) is also distinct from "expert prefetch" (which predicts *which* experts): it reads exactly the router-selected experts, just as contiguous large ranges instead of 16 KiB faults.
- Raw SSD bandwidth is not the hard ceiling: internal Apple NVMe measurers 2.4-6.06 GB/s (double-buffered), vs the user's effective ~1.86 GB/s (809 MB × 2.3 tok/s). There is ~3× bandwidth headroom if IOPS/latency and syncs are fixed.

### Gaps
- No source reported a bit-exact measurement on a **16 GB M4 running Qwen3.8-Flash-Next specifically**; Jakevin's Qwen numbers are on 64 GB and the 16 GB row is Nemotron. Whether a ~7.4 GB expert cache fits in 16 GB alongside trunk+KV+OS is unproven.
- Whether Veystrix's current expert I/O uses mmap faults, `pread`, or F_NOCACHE was not stated; the applicability of explicit-read/coalescing depends on this.
- "Lossless rANS decompression" bit-exactness holds only if the decompressed weights are bit-identical to the original quantized weights; no independent audit found.

## Key Question 2: What published work reports actual tok/s gains for caching / residency / prefetch policies, and at what memory cost?

### Takeaway
Caching/residency/policy papers report large speedups (1.3-10×) but almost all are evaluated on NVIDIA GPU+CPU setups, and the most-cited numbers are either simulated or rely on large caches (often 10-24 GB) that a 16 GB M4 cannot host. The evidence most relevant to a 16 GB M4 is the Apple-Silicon repos in Q1, which show graceful decode-vs-residency curves and a hard practical cache ceiling around 4-8 GB before thrashing.

### Cited Findings
- **ExpertFlow**: transformer routing-path predictor + token scheduler + predictive cache with runtime misprediction correction; **up to 10× throughput** and **93.72% GPU memory reduction** (e.g. Qwen1.5 35.21 -> 6.52 GB; DeepSeek-MoE 31.35 -> 6.38 GB); RPP up to 95% prediction accuracy; cache hit 91.96% (up to +61.15% over LRU); token scheduler +16.19% throughput. — [ExpertFlow](https://arxiv.org/html/2410.17954v2)
- **SeqMoE**: seq2seq expert prediction + probabilistic Belady eviction + graph-compatible runtime; **45% expert residency -> 96.97% hit rate and 80.22% of full-load performance**. — [SeqMoE](https://arxiv.org/html/2609.12978)
- **Diff-MoE**: priority-driven differential cache (global-hot / temporal-hot / cold tiers) + next-layer predictor; **2.74× / 2.22× / 1.55× over DeepSpeed / Pre-gated MoE / MoE-Infinity**; no model-architecture modification. — [Diff-MoE](https://dl.acm.org/doi/full/10.1145/3712285.3759903)
- **llama.cpp GPU-resident LRU cache (PR #27861, merged)**: instrumented 54k-record workload found **no static skew** (top-32 hot list covers only ~10% vs 6.2% uniform) but **strong temporal locality** (per-layer LRU-64 ~67% hit, LRU-128 ~81%). Decode **18.4 -> 24.2 tok/s (+31%) with 48 slots/layer (~4.1 GiB VRAM)**; separate sweep 0 slots 8.2 -> 280 slots 18.9-19.1 tok/s (24 GB VRAM, 93% hit), 300 slots spilled and collapsed to 9.5 tok/s — a sharp memory cliff. — [PR #27861](https://github.com/ggml-org/llama.cpp/pull/27861)
- **Speculative expert prefetch (YALIS)**: parameter-free quasi-hidden-state next-layer prediction, double-buffered pinned-CPU offload; **5-14% TPOT improvement** over on-demand loading, downstream accuracy largely preserved. — [Speculating Experts](https://arxiv.org/html/2603.19289)
- **SpecPrefetch**: lightweight adapters predict next-layer expert demand, native router still selects final experts; on Snapdragon 8 Elite with NVMe, **4.055 tok/s = +8.12%** vs offloading baseline; up to ~20% with slow-storage emulation. Bit-exact routing by design. — [SpecPrefetch](https://arxiv.org/html/2607.24787v2)
- **MoE-CORE**: separate prefill/decode memory regions, RHAC replacement, cross-layer prefetch; optional approximate expert substitution (quality-risky). — [MoE-CORE](https://arxiv.org/html/2610.01950)
- **ADEPT (two-stage domain-aware)**: 81% cache hit, **simulated TPOT 1100 ms vs measured HF baseline 3797 ms = 3.45×**; peak 43/64 experts resident per layer (~67% of full model, macro-average ~33%). The 3.45× is a *simulation*, not an end-to-end measurement. — [IEEE ADEPT](https://ieeexplore.ieee.org/document/11397596)
- **Fiddler (ICLR 2025)**: move small activations to CPU rather than big weights to GPU; unquantized Mixtral-8x7B (>90 GB) on 24 GB GPU at **>3 tok/s**; 1.26× single-batch, 1.30× long-prefill vs SOTA; 8.2-10.1× vs standard offloading. Bit-exact (execution placement only). — [Fiddler](https://arxiv.org/abs/2402.07033)
- **FlashMoE**: ML-based (Belady-approximating) cache replacement + layer/unit-level SSD subdivision; fine-grained on-demand loading. — [FlashMoE](https://arxiv.org/html/2601.17063)
- **OD-MoE**: cacheless SSD, CPU-GPU parallel shadow model; Mixtral-8x7B **3.69 tok/s (75.5% of full-GPU), full-precision answer quality**, per-worker GPU <1 GB; TTFT ~2244 ms avg. — [OD-MoE](https://arxiv.org/html/2512.03927)
- **MoE-Gen**: module-based batching for *high-throughput* serving; 31× decode throughput on DeepSeek-V2-236B — but this is batched throughput, not single-stream latency. — [MoE-Gen](https://arxiv.org/html/2503.09716v1)
- **vLLM-metal MoE offload**: experts stay on disk, cache in unified memory, runs mlx-lm's own `SwitchGLU` so **outputs identical to fully resident model**; only knob is `moe_expert_offload.cache_gb`. — [vLLM-metal](https://docs.vllm.ai/projects/vllm-metal/en/latest/moe_offload)
- **Prompt/prefix caching for TTFT (Jakevin)**: snapshot full model + KV state at prefix points; on a 14,937-token agent prompt (20 GB cap, M4 Pro) TTFT 315.7 s no-cache -> **63.9 s on prefix-hit (4.94×)**, bit-exact (same logits/state/greedy tokens) when chunk boundaries match; changing chunking can shift logits slightly. — [Jakevin/moe-offload](https://github.com/Jakevin/moe-offload)

### Inferences
- The 10×/9.75× class of gains comes from moving from a very slow baseline (DeepSpeed-MII/naive mmap) to a tuned pipeline; they are not additive multipliers on a 2.3 tok/s baseline that is already doing per-layer caching.
- Memory is the binding constraint on 16 GB: merged llama.cpp PR #27861 shows a cliff at ~24-26 GB slots, and Jakevin's M4 8 GB Nemotron cache thrashed. The realistic resident expert cache on a 16 GB M4 is a few GB, capping achievable hit rates.
- The user's already-rejected "non-S3FIFO pool policies" and "perfect expert predictor" are consistent with the literature's finding that *static* pinning fails (no static skew) and that perfect prediction alone does not help if I/O path/syncs dominate. The remaining policy headroom is small.

### Gaps
- No paper reports tok/s on an Apple M4 with 16 GB for Qwen3.8-Flash-Next bit-exactly. Nemotron-specific published numbers on any Apple Silicon are scarce outside Jakevin.
- Many papers report "speedup vs a deliberately weak baseline" rather than absolute tok/s; cross-paper comparison is not apples-to-apples.
- Minimal published data on expert duplication across layers or KV/expert tiering as separate levers (MoE-CORE's phase split is the closest).

## Key Question 3: Which methods are bit-exact vs quality-lossy under the zero-quality-loss constraint?

### Takeaway
Most I/O/layout/caching methods are inherently bit-exact because they change *when* weights are read, not *which* weights or the math. Quality risk enters specifically through: lower-precision variants/substitution, changing top-k, floating-point router changes, and expert reordering that is not mirrored in router rows. The user's "cache-aware routing" rejection is corroborated: any method that changes the selected expert set or its precision violates the gate.

### Cited Findings
**Bit-exact / no math change (recommended class):**
- Native/async pread, sorted gap-merged explicit reads, coalescing/sidecar contiguity, double-buffered pipelines, cache-replacement policies, pinned caches, prompt/prefix caching — all explicitly reported bitwise/byte-identical in [Jakevin](https://github.com/Jakevin/moe-offload), [PR #31469](https://github.com/ggml-org/llama.cpp/pull/31469), [mbolt gist](https://gist.github.com/doramirdor/0aeb975a99eb5a4644a3d105b57e3909), [alexschiltmans doc](https://github.com/alexschiltmans/llama.cpp-per-layer-experts/blob/per-layer-experts/docs/moe-ssd-streaming.md), [vLLM-metal](https://docs.vllm.ai/projects/vllm-metal/en/latest/moe_offload), [omlx](https://github.com/jundot/omlx/blob/main/docs/MoE_Expert_Offload.md), [PR #25294](https://github.com/ggml-org/llama.cpp/pull/25294).
- Lossless rANS decompression in VRAM reconstructs original weights — [SSD-LLaMA](https://arxiv.org/html/2609.18110).
- Predictor-only prefetch where the native router still picks final experts — [SpecPrefetch](https://arxiv.org/html/2607.24787v2), [MoE-CORE exact path](https://arxiv.org/html/2610.01950).
- Fiddler-style CPU execution of exact weights — [Fiddler](https://arxiv.org/abs/2402.07033).

**Quality-lossy / risky (flag; DO NOT recommend under the gate):**
- **MoE-APEX**: replaces cache-miss experts with **low-precision variants**; 1.34-9.75× speedups — lossy by construction. — [MoE-APEX](https://dl.acm.org/doi/10.1145/3779212.3790187)
- **FloE**: compresses expert matrices; 9.3× compression / 48.7× speedup with **4.4-7.6% average performance degradation**. — [FloE](https://arxiv.org/html/2505.05950v2)
- **PagedMoE / SliceMoE**: bitplane/slice-level caching with on-demand lower precision; cross-precision reuse reduces SSD bytes (2.08 -> 1.41 GiB/tok) but executes reduced-bit experts — quality-risky. — [PagedMoE](https://arxiv.org/html/2611.03173), [SliceMoE](https://arxiv.org/html/2512.12990v4)
- **Expert substitution** (SMoE, MoE-CORE optional substitution, cache-aware routing): replaces low-score experts with similar resident ones — changes expert set; same failure mode as the already-rejected cache-aware routing. — [SMoE](https://arxiv.org/html/2508.18983v3), [MoE-CORE](https://arxiv.org/html/2610.01950)
- **ReMoE**: fine-tunes the router toward recently used experts; +26% reuse, 3.58 -> 3.88 tok/s on vLLM/RTX 3090 — changes routing weights; author claims task accuracy maintained but it violates "exact routing." — [ReMoE](https://arxiv.org/html/2605.27081)
- **Reducing `ROUTED_TOP_K`**: SwiftLM top-8 -> top-2 gives 4.95 -> 6.52 tok/s but "still coherent" = explicit quality loss; ssdmoe exposes the same tradeoff. — [SwiftLM](https://github.com/SharpAI/SwiftLM), [ssdmoe](https://github.com/RasoulNik/ssdmoe)
- **Aggressive expert permutation / reordering**: mbolt notes token-identity cannot be guaranteed under nontrivial permutation; profile-guided co-activation reorder in #18758 is "equivalent within backend FP noise," not provably bit-identical. Coalescing (no reorder) is bit-exact; clique reorder is the risky part. — [mbolt gist](https://gist.github.com/doramirdor/0aeb975a99eb5a4644a3d105b57e3909), [discussion #18758](https://github.com/ggml-org/llama.cpp/discussions/18758)
- **DAOP "graceful degradation" / approximate pre-calculation** and INT8 routers (Mference) also carry accuracy risk despite maintained-benchmark claims. — [DAOP](https://arxiv.org/html/2501.10375), [Mference](https://github.com/NeelM0906/Mference)

### Inferences
- The zero-loss gate cleanly separates the field: all the *systems* wins (I/O path, layout, caching, sync removal, lossless compression) are compatible; all the *algorithmic* wins (precision, substitution, routing changes, top-k) are not.
- The user's existing high bit-exact baseline means the attainable multiplier comes almost entirely from systems work, not from the 5-10× papers that mix in precision reduction.

### Gaps
- No source provides a token-digest-level comparison for expert reordering under MLX's BF16 rounding boundaries; treat any reorder as failing the gate until proven otherwise.
- BF16 rounding at expert-output accumulation under different kernel paths (e.g., C++ vs Python runners) is claimed bit-exact in one repo but not broadly audited.

## Key Question 4: What specifically could push the SSD-bound 16 GB M4 from 2.3 -> 5 tok/s (Qwen) and 6.7 -> 15 tok/s (Nemotron), and is 2× reachable?

### Takeaway
For Qwen, ~2× is **plausible but near the edge**, and only by combining (a) eliminating per-layer Python/`mx.eval` syncs via a native fused decode path and (b) cutting cold-expert I/O via profile-free coalescing + explicit merged reads + a pinned modest LRU cache. For Nemotron, **15 tok/s on 16 GB is probably NOT reachable bit-exactly**: published full-model-resident baselines for the same Nemotron family are ~13.9-14 tok/s at ~20.8 GB, i.e., the target exceeds the fully-resident ceiling on hardware that cannot hold it. Honest assessment: Qwen 5 tok/s is achievable with effort; Nemotron 15 tok/s requires more memory, a faster SSD, or accepting quality loss.

### Cited Findings
- Quantitative budget for Qwen from the M4 profile: 118 ms/token = sync 41% (~48 ms) + SSD 29% (~34 ms) + GPU 27% (~32 ms). Removing syncs ideally -> ~70 ms -> ~14 tok/s ceiling from that profile alone; the observed v1->v2 (Python->native pread + fewer syncs) was 8.51 -> 9.17 tok/s (+8%), and the C++ runner held 9.0-9.6 tok/s. Coalescing cuts the SSD component ~3× (mbolt 1396 -> 463 µs). — [Jakevin](https://github.com/Jakevin/moe-offload), [mbolt gist](https://gist.github.com/doramirdor/0aeb975a99eb5a4644a3d105b57e3909)
- The user's current effective read rate (~809 MB/tok × 2.3 tok/s ≈ 1.86 GB/s) is well below measured Apple NVMe capability (2.97 GB/s sequential, 6.06 GB/s double-buffered on M1; ~5.6 GB/s on M4 Air), so bandwidth headroom for ~2× exists. — [llama.cpp discussion #27149](https://github.com/ggml-org/llama.cpp/discussions/27149), [ssdmoe](https://github.com/RasoulNik/ssdmoe)
- On the exact model out-of-core, a fully rewritten I/O+sync path reached **16-22 tok/s byte-exact** (PR #31469, Linux/RTX) and **9-11 tok/s** on M4 Pro 64 GB (Jakevin), showing the 5 tok/s target is below demonstrated bit-exachievable performance for this architecture. — [PR #31469](https://github.com/ggml-org/llama.cpp/pull/31469), [Jakevin](https://github.com/Jakevin/moe-offload)
- Nemotron ceiling: Jakevin's full-model-resident baseline **13.9 tok/s at 20.8 GiB** on M4 Pro; on 16 GB M4 the best cached result was **4.39 tok/s** (4 GB cache, 86.1% hit). Target 15 tok/s exceeds the resident baseline and is ~3.4× the measured 16 GB cached number. — [Jakevin](https://github.com/Jakevin/moe-offload)
- 16 GB cache-size realism: Palm-Infra sweep shows 10 GiB cache = 16.19 t/s at 14.64 GiB RSS on a *48 GB* Mac; on a 16 GB M4, Jakevin's 8 GB Nemotron cache thrashed. A ~2-4 GB expert cache is the practical ceiling. — [Palm-Infra](https://github.com/TencentYoutuResearch/Palm-Infra/blob/main/docs/ssd-offload.md), [Jakevin](https://github.com/Jakevin/moe-offload)

### Inferences — ranked candidate methods (bit-exact; cross-check against rejected list)
1. **Native/fused decode to remove `mx.eval` + Python per-layer syncs** (C++/Metal runner pattern, KICK/WAIT-style on-device slot resolution). Bit-exact; largest measured single lever (41% of token time). NOT in rejected list. — [Jakevin](https://github.com/Jakevin/moe-offload), [PR #31469](https://github.com/ggml-org/llama.cpp/pull/31469)
2. **Profile-free expert coalescing** (each expert's 9 sub-slices -> one contiguous block / sidecar with the 3 projections together). Bit-exact, ~20% decode, 9× fewer read-ops, negligible disk cost. Distinct from rejected "expert packing." — [mbolt gist](https://gist.github.com/doramirdor/0aeb975a99eb5a4644a3d105b57e3909), [alexschiltmans doc](https://github.com/alexschiltmans/llama.cpp-per-layer-experts/blob/per-layer-experts/docs/moe-ssd-streaming.md)
3. **Explicit sorted/gap-merged pread of exactly the router-selected experts** instead of mmap page faults (+13-52% tok/s), with double-buffered overlap of next-layer I/O under current-layer compute (2.09× pipeline throughput). Bit-exact. — [discussion #25779](https://github.com/ggml-org/llama.cpp/discussions/25779), [discussion #27149](https://github.com/ggml-org/llama.cpp/discussions/27149)
4. **Pin the expert cache in physical memory** (avoid macOS VM-compressor decompress-in-matmul); keep cache modest (<=~4 GB) to avoid thrash. Bit-exact; directly measured on Apple Silicon. — [Palm-Infra](https://github.com/TencentYoutuResearch/Palm-Infra/blob/main/docs/ssd-offload.md)
5. **Span-merge expert byte ranges into multi-MB reads** and raise SSD queue depth via a native pthread/async pool (NOT just more I/O workers). Bit-exact. — [streamlx](https://github.com/srcterm/streamlx), [Jakevin](https://github.com/Jakevin/moe-offload)
6. **Prefix/prompt caching** for TTFT (4.94× on repeated prefixes, bit-exact at fixed chunk boundaries). — [Jakevin](https://github.com/Jakevin/moe-offload)
7. **Layer-major prefill dedup** (stream each distinct expert once per layer per prefill slab) — TTFT/prefill win, bit-exact. — [anemll flash llama.cpp doc](https://github.com/Anemll/anemll-flash-llama.cpp/blob/master/docs/flashmoe-layer-major-dedup-single-sidecar.md)

### Inferences — reachability verdict
- **Qwen 2.3 -> 5 tok/s (2.17×): marginally reachable, bit-exact**, *if* the 41% sync overhead is real in Veystrix and can be cut, combined with coalescing + explicit reads. Evidence: native pread already gave 8.51 tok/s on M4 Pro; a 16 GB-constrained cache lowers this, so the target sits below demonstrated hardware capability but requires the full stack of fixes working together. If syncs are already minimal in Veystrix, 2× is unlikely from I/O alone.
- **Nemotron 6.7 -> 15 tok/s (2.24×): probably not reachable bit-exact on 16 GB** — exceeds the ~13.9 tok/s fully-resident baseline at ~20.8 GB; would need >16 GB unified memory, a much faster SSD, or quality-reducing quantization/top-k. Flag any claimed path to 15 as quality-risky unless it beats the resident ceiling on this exact hardware.
- The single most informative next experiment is a profiler breakdown of Veystrix's per-token time (GPU / sync / SSD) on the 16 GB M4. If the split resembles Jakevin's 27/41/29, prioritize native fused decode; if SSD is genuinely >60%, prioritize coalescing + explicit reads + pinning.

### Gaps
- No bit-exact source reached 5+ tok/s for Qwen3.8-Flash-Next on a 16 GB M4; the closest 16 GB data point is Nemotron at 4.39 tok/s.
- Unknown whether Veystrix's decoder already uses native pread and minimal syncs; without that profile the 2× estimate is speculative.
- No data on whether a ~2-4 GB expert cache can sustain the needed hit rate for the full 512-expert/28-layer Qwen on 16 GB under realistic long-context workloads.
- Cost/latency of building a coalesced sidecar for Qwen's ~68-125 GB expert set on a 16 GB host, and whether it can be streamed rather than fully materialized, is unresolved.
