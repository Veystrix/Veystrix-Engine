# Novel bit-exact MoE expert caching/reuse/prediction techniques to reduce physical SSD bytes per token (Veystrix "miracle" hunt)

Scope: 16 GB Apple M4, single ~3 GB/s SSD. Bit-identical tokens and exact routing are hard requirements. Existing attempts that are explicitly OUT of scope as "novel" (prefetch/lookahead/next-layer router prediction, decode overlap + early submit, perfect predictor + overlap, I/O worker tuning, LRU/cost-aware/least-stale/S3-FIFO, pool 2→4 GB, expert packing/coalescing, K=2 read-sharing, speculative all depths) are noted only where a paper gives a *new quantified* result that changes the calculus.

---

## Q1: Which 2024–2026 techniques actually reduce physical SSD bytes per token while keeping weights bit-identical and routing exact? (ranked by plausible value)

### Takeaway
Only one mechanism family found in the literature reduces *physical SSD bytes per token* while remaining strictly bit-exact on weights and routing: **lossless compression of expert tensors, with compression-state-aware caching and on-the-fly reconstruction**. Two 2026 papers (ZipMoE, SSD-LLaMA) report measured 30–33%+ reductions in SSD traffic with bit-identical reconstructed weights; ZipMoE explicitly targets Apple-Silicon-style unified-memory (UMA) edge devices at ~3.5 GB/s SSD, which is essentially Veystrix's hardware. Everything else that reduces bytes (dynamic precision, expert substitution, routing bias, tying, pruning) changes the model and is disqualified by the bit-exactness constraint.

### Cited Findings

#### RANK 1 — ZipMoE: lossless bit-field compression + multi-state cache + parallel CPU reconstruction (highest value; direct M4 fit)
- **Mechanism.** Offline bit-field decomposition of BF16 expert tensors into (a) low-entropy exponent bits, compressed with LZ4HC/ZSTD into E-chunks, and (b) high-entropy sign+mantissa bits packed byte-aligned into SM-chunks. At runtime a *compression-state* cache keeps full tensors, compressed tensors, SM-chunks and E-chunks in separate pools (F ≺ C ≺ S ≺ E); a cache-affinity scheduler builds per-expert DAGs of SSD-read/decompress/reconstruct ops and overlaps SM-chunk I/O with E-chunk decompression on ≥3 CPU worker threads; a vectorized coalesced GPU kernel reassembles BF16 tensors. The scheduler has a constant-factor optimality proof: ALG ≤ (3 − 1/L)·OPT — [Source](https://arxiv.org/html/2601.21198v1)
- **Bit-exactness verdict: PASS.** Explicitly "semantically lossless"; the reassembled BF16 tensor is bit-identical, no quantization, no routing change — [Source](https://arxiv.org/abs/2601.21198)
- **Measured gain.** Exponent-bit symbol support set is only 14.06% / 11.33% / 14.84% of possible values across three MoEs (entropy 2.65 / 2.56 / 2.55 bits); ZSTD compresses expert parameters to **68%** of original size and LZ4HC to **74%**, near the Shannon lower bound of 66.02% / 65.96% / 66.52% — [Source](https://arxiv.org/html/2601.21198v1). End-to-end: up to **72.77% latency reduction** and **6.76× throughput** vs SOTA on Jetson AGX Orin with a 3.5 GB/s Samsung 970 EVO; decoder-only TPOT reductions of **62.65%–97.97%**, TTFT reductions 53.25%–87.90% — [Source](https://arxiv.org/abs/2601.21198)
- **Why it beats a plain cache.** Caching only SM-chunks (≈50% of tensor bytes) gives **2× tensor coverage** under the same memory budget; on a partial hit, spare CPU cores reconstruct exponent bits with decompression latency fully hidden by I/O of other cache-missed experts — [Source](https://arxiv.org/html/2601.21198v1). This is a *byte-level reuse* mechanism that is orthogonal to and strictly stronger than LRU/S3-FIFO on whole experts.
- **Feasibility on 16 GB M4: HIGH.** Target platforms explicitly include "Jetson, Raspberry Pi, **Apple Silicon**"; UMA/zero-copy into pinned host memory registered for direct GPU access is the design's core assumption; decompression needs only ≥3 of the 6–12 available cores and costs only 7.47% SSD throughput reduction from memory-controller contention — [Source](https://arxiv.org/html/2601.21198v1)
- **Falsifiable test.** Offline: measure ZSTD/LZ4HC compressed size of gate/up/down tensors for the actual Qwen3.8-Flash-Next and Nemotron-Lightning expert packs and the exponent-symbol entropy/support. Online: A/B (baseline raw expert pack) vs (E/S-chunk pack + reconstruction) with *identical* cache GiB, identical routing traces, and a byte-for-byte tensor checksum at the reconstruction output. Pass criteria: (i) checksum equal for every expert; (ii) token IDs identical under greedy decoding; (iii) measured SSD bytes/token drop ≥25%; (iv) tok/s gain > decompression overhead. Kill criterion: entropy/skew below ~15% support (then compression ratio <1.15×).

#### RANK 2 — SSD-LLaMA: per-expert lossless rANS pack + CUDA/on-device decompression cuts SSD traffic 33.2%
- **Mechanism.** Offline lossless transformation of each (layer, expert) gate/up/down triple into one aligned single-read O_DIRECT record ("expert pack"); 4-bit weight values entropy-coded with rANS using offline tables, scales compressed separately; on a miss the compressed record is read with io_uring into pinned RAM, transferred and decompressed directly into a VRAM slot by a CUDA rANS decoder, with an integrity check before use — [Source](https://arxiv.org/html/2609.18110v1)
- **Bit-exactness verdict: PASS.** "After decompression, every byte of the quantized weights and their associated scale data is identical to the original expert pack. Compression therefore introduces no additional numerical approximation"; the system "does not prune selected experts, replace them with resident experts, or change their routing weights" — [Source](https://arxiv.org/html/2609.18110v1)
- **Measured gain.** Physical SSD traffic falls **8.89 → 5.93 GB per generated token, a 33.2% reduction**; compressed-transfer + CUDA-decompression costs 0.54 s/token vs 0.93 s/token for SSD reads, so decompression is not the bottleneck — [Source](https://arxiv.org/html/2609.18110v1). Overall decode rate 2.10×–15.58× over evaluated baselines across three frontier MoE families — [Source](https://arxiv.org/abs/2609.18110)
- **Feasibility on 16 GB M4: MEDIUM-HIGH.** The paper explicitly targets "at most an RTX 5090 and approximately 16 GB of host memory," and reports 80.1% VRAM hit rate with a 22 GiB cache on the RTX 5090 — too large for Veystrix. The *concept* (compressed expert pack + decompress-to-resident-slot) transfers; the CUDA rANS decoder and io_uring do not, and would need a CPU/NEON or Metal decoder. On Apple Silicon, CPU-decompressed bytes in unified memory are directly GPU-readable, which removes the separate H2D step that costs them 0.54 s — [Source](https://arxiv.org/html/2609.18110v1)
- **Falsifiable test.** Build a compressed expert pack for one MoE layer of each target model; measure bytes/token for 200 greedy tokens; verify decompressed SHA-256 equals original tensor bytes for all 512/128 experts; measure CPU decode throughput on M4 (target >3 GB/s effective to keep decompression below the SSD read time).

#### RANK 3 — Cross-precision bitplane prefix reuse (PagedMoE): NOT bit-exact, but its cache-reuse principle is the direct inspiration for RANK 1/2
- **Mechanism.** Stores each expert once as a prefix-compatible tree codebook/bitplane layout so a 1-bit prefix is the valid prefix of the 8-bit representation; a cached low-precision prefix can be *extended* by fetching only missing bitplanes instead of refetching the whole expert. At avg 2.5 bits/expert, 8.89 tok/s on Qwen3.5-397B with a 24 GiB cache = 1.33× independent-precision objects and 1.56× uniform 4-bit — [Source](https://arxiv.org/abs/2611.03173)
- **Bit-exactness verdict: FAIL.** Quality is "close to GPTQ-INT4" / "close to MXFP4" — i.e. lossy dynamic precision, not bit-identical tokens — [Source](https://arxiv.org/abs/2611.03173)
- **Feasibility/transfer.** The *prefix reuse* idea generalizes to lossless compression states: ZipMoE's F/C/S/E pools are exactly "fetch/extend only the missing part of a resident object." Do not reuse PagedMoE's quantization.
- **Falsifiable test (derived, not from the paper).** Replace precision prefixes with lossless-chunk prefixes: store each expert as [SM-chunk, E-chunk]; cache hit on SM only fetches E. Measure bytes/token vs full-object cache.

#### RANK 4 — Exact-routing eviction-only improvement (farthest-future): bit-exact, 2.1× fewer transfers, but needs future knowledge
- **Mechanism.** Change only *which* expert the cache evicts, leave routing untouched; use ~16 tokens of known future demand. On an L40S with real timed transfers: "Changing only which expert the cache evicts, while leaving routing untouched, cuts transfers by **2.1× with no quality loss** and comes within **3.5% of the best possible schedule**. Sixteen tokens of future demand recover 96% of this gain, while a frequency-based rule that uses only past requests recovers 27%." Every method that ran faster than LRU by *changing routing* increased next-token loss by ≥0.067 nats — [Source](https://neurips.cc/virtual/2026/156996); [Source](https://openreview.net/forum?id=8o1IwZ1V36)
- **Bit-exactness verdict: PASS** for the eviction-only variant; FAIL for the routing-changing baselines that were faster — [Source](https://neurips.cc/virtual/2026/156996)
- **Feasibility on 16 GB M4: LOW for the 2.1× number.** The 96%-of-gain result requires 16 tokens of *future* demand, unavailable in autoregressive decode; a purely online frequency rule recovers only 27%. This is the quantitative reason the user's steady-state OPT cache ceiling cannot be beaten online.
- **Falsifiable test.** Offline oracle study: record the true routing trace for a fixed 512-token continuation; run Bélabé/farthest-future eviction at Veystrix's 2–4 GB expert cache and measure the transfer-count floor. Then run the same with a 16-token sliding lookahead supplied by a *non-routing-changing* source (e.g. a prefill-time dry run of a deterministic prefix) and with past-only frequency; the gap between these three is the realizable bit-exact headroom.

#### RANK 5 — Persistent expert slot pool (llama.cpp RFC): bit-exact, measured +52% decode, but a cache not a byte reduction
- **Mechanism / gain.** Persistent pool of `-mec 32` expert slots in accelerator memory; decode tg512 goes 17.54 ± 0.15 t/s vs baseline (~11.5 t/s), **+52%**, with prefill pp512 ≈119 t/s — [Source](https://github.com/ggml-org/llama.cpp/discussions/28248)
- **Bit-exactness verdict: PASS** (cache hit serves the identical weight bytes). **Feasibility: HIGH** but it is exactly the cache approach the user has already pushed to its ceiling; include only as a calibration point.

### Inferences
- Lossless compression is the only found lever that actually reduces the *number of physical bytes* read per token while satisfying both hard constraints. Reported ratios (0.68–0.74 of original from ZipMoE; 0.668 from SSD-LLaMA's 33.2% traffic cut) are consistent across independent papers and hardware, so a ~30% SSD-byte reduction for Veystrix's packs is a defensible planning number, not a speculation.
- Applying ~30% to Veystrix's stated traffic gives Qwen 408 → ~285 MB/token and Nemotron 436 → ~305 MB/token. At 3 GB/s that is still a ~95–102 ms/token pure-I/O floor, i.e. **lossless compression alone cannot reach 15 tok/s for Nemotron** (67 ms/token budget). Compression is necessary but not sufficient.
- ZipMoE's "cache the incompressible half, reconstruct the compressible half on spare cores" is a genuine *byte-level* reuse trick that sidesteps the whole-expert OPT ceiling: it changes the granularity of reuse from "expert" to "bit-field," so a 2 GB cache can cover ~2× as many experts. This is the single most promising "serve more lookups from the same resident bytes" idea found.
- The 2.1× eviction result confirms the user's empirical finding that online policies are tied: the gain comes almost entirely from future knowledge, so it does not invalidate the OPT ceiling.

### Gaps
- No paper reports lossless-compression bytes/token specifically for Qwen3.8-Flash-Next or Nemotron-Lightning, or for their already-quantized (e.g. Q4/MXFP4) expert packs; all compression studies use BF16 or 4-bit models. Entropy of *already quantized* weights may be much lower than BF16 exponent entropy (good) or already near the entropy bound (less gain).
- No source reports an Apple M4-specific lossless-decompression throughput number for ZSTD/rANS on expert tensors; the 7.47% contention figure is from Jetson AGX Orin.
- No source combines lossless compression with a sub-expert cache and reports the marginal byte/token gain over compression alone; ZipMoE reports combined system gains, not a clean ablation isolated to bytes/token.

## Q2: How much bit-exact reuse is extractable from cross-token, cross-layer, and prompt-derived structure within one request?

### Takeaway
Strong within-request *skew* exists (a small set of experts is reused repeatedly), and cross-layer/co-selection correlations are large and statistically robust, but the user's "exact routing" constraint means this structure can only be exploited for cache/compression granularity and physical co-location — not for changing which experts run. Quantitatively, adjacent-token overlap is only ~25% of a layer's expert set, and the entire online-reuse gain is bounded by the OPT ceiling the user already measured.

### Cited Findings
- **Within-request skew / cross-request churn.** "Accesses concentrate on a subset of experts within each prompt, while the identity of that subset changes across prompts"; the exact working set "cannot be fixed at model-loading time or recovered reliably from one global popularity order; it is revealed by the router during execution" — [Source](https://arxiv.org/html/2609.18110v1). MoE-Infinity's EAM (Expert Activation Matrix) traces this request-level structure and reports 2.7×–13.7× improvement over strong baselines using cosine similarity over recent activation sketches — [Source](https://arxiv.org/html/2508.17137v1); [Source](https://arxiv.org/abs/2401.14361)
- **Cross-token overlap is low in absolute terms.** "Adjacent tokens agree on only about a quarter of a layer's expert set in our traces, so most prefetched experts are never read again" — [Source](https://arxiv.org/html/2609.18063v2). This is a direct falsification of any "n-gram of expert sets" strategy that assumes near-identical adjacent sets.
- **Within-layer co-selection is extremely concentrated (training-time measurement, bit-exact by construction).** At top-2, **0.8% of expert pairs in a layer are selected together by 42% of tokens** (independent routing would give 1.6%); 14 pairs with ≥50% conditional confidence carry 16% of tokens; for 73 of 128 experts one partner appears in ≥30% of its tokens. Correlated placement + a deduplicating dispatcher removes **up to 58% of dispatched rows**, and "neither technique changes the router's expert assignments or the expert computation" — [Source](https://arxiv.org/html/2610.09372)
- **Cross-layer prediction is strong (training-time measurement, bit-exact by construction).** 112 of 128 layer-8 experts send ≥30% of their tokens to one specific layer-9 expert (median share 48%); moving a token to its predicted owner GPU raises locally-served next-layer experts from 12.5% to 59% on one node — [Source](https://arxiv.org/html/2610.09372). Related: cross-layer coupling is an emergent property where "the expert activated at layer ℓ strongly predicts the expert activated at layer ℓ+1" — [Source](https://arxiv.org/abs/2602.14159)
- **Correlation tables are cheap to fit and stable.** 1,024 tokens suffice to remove 23.6% (top-2 EP8) / 57.9% (top-6) of dispatched rows; at 4,096 tokens the fitted vs held-out co-selection matrix Pearson r = 0.93 (top-2) and 0.98 (top-6), within one percentage point of using all 524k tokens — [Source](https://arxiv.org/html/2610.09372)
- **Learned predictor ceiling (prediction only, bit-exact if used purely for prefetch).** MoE-Beyond: transformer over token embeddings + layer IDs, 66M activation traces, 97.5% accuracy / 86.6% F1 on unseen prompts, GPU cache hit rate 17% → 72% at 10% capacity; but accuracy is inflated by 6:58 class imbalance (training accuracy starts at 96%) and it needs ~48 A100 GPU-hours and full retraining per backbone — [Source](https://arxiv.org/html/2508.17137v1)
- **Prompt/semantic-hint working set (FineMoE).** Uses "semantic hints from input prompts" plus expert trajectories to build per-layer "expert maps" searched per iteration, with similarity-aware prefetch count δ and an asynchronous map searcher; on-demand miss loading pauses prefetch — [Source](https://arxiv.org/html/2502.05370v2)
- **Physical co-location of co-selected experts.** GRACE-MoE groups experts "often selected together within a layer" onto the same GPU, sends a token to each GPU once, and replicates hot experts; CARE-MoE reports expert co-activation correlation heatmaps for Qwen3-30B-A3B — [Source](https://arxiv.org/html/2610.09372); [Source](https://dl.acm.org/doi/10.1145/3832810.3832869)

### Inferences
- The expert-coupling numbers are from *training* on 128-expert top-2/top-6 models; whether Qwen3.8-Flash-Next (512 experts, top-10) and Nemotron-Lightning (128, top-6) show comparable pair concentration is unverified. With top-10 out of 512, pair co-selection may be far weaker, which would reduce the physical co-location benefit.
- Even if co-selection is strong, applying it to a *single SSD* is not the same as applying it to an EP group: the SSD is one device, so "co-locating on the same device" is already true. The transferable benefit is **physical byte adjacency in the expert pack** (one larger sequential read instead of k small random reads) — but Veystrix already tried "expert packing/coalescing (no server gain)", so this is likely a dead end unless combined with the RANK-1/RANK-2 compression format (where the correlation table can decide which SM/E-chunks share a compression block and cache pool).
- "16 tokens of future demand recover 96% of the eviction gain" plus "adjacent tokens agree on ~25% of expert set" together explain why lookahead/prediction was tied in Veystrix: the theoretical reuse exists but requires a horizon the engine cannot obtain without changing routing.
- FineMoE/MoE-Beyond/MoE-Infinity all reduce *copies* via prediction; Veystrix already tested this class. They are useful only as evidence that within-request skew is real, not as a new mechanism.

### Gaps
- No measured cross-layer top-k overlap percentage for Qwen3.8-Flash-Next or Nemotron-Lightning at their exact top-k/E.
- No study measures whether expert co-selection correlations hold in *pretrained, frozen* models at 512-expert/top-10 scale (the 0.8%/42% figure is measured during pretraining after ~2.1B tokens).
- No paper tests "n-gram of expert sets" as a cache admission signal; the closest is MoE-Infinity's EAM cosine matching and MoE-Beyond's learned multi-label sequence model.

## Q3: Can expert duplication, tying, or substitution be exploited on an already-trained checkpoint bit-exactly?

### Takeaway
No. All weight-sharing, duplication-removal, and substitution techniques either require retraining (changing the weights) or replace the selected expert with a different one (changing the computation). At best they reveal redundancy that motivates compression or a one-time dedup of *bit-identical* tensors, which has not been shown to exist in these checkpoints.

### Cited Findings
- **Cross-layer expert sharing ("Meta Expert").** Shared meta experts let a model match vanilla MoE with **70–80% as many experts / 75–90% as many parameters**, with lower cross-entropy and expert redundancy ρ; 6B-A1.6B models trained 200B tokens — [Source](https://arxiv.org/html/2610.27598v1). This is a *trained-from-scratch architecture*, not a transformation of an existing checkpoint — [Source](https://arxiv.org/abs/2610.27598)
- **Expert tying.** Sharing gate/up/down expert weights across consecutive layers with independent routing/attention cuts unique FFN parameters **up to 75%** at g=4 with "virtually no degradation in perplexity or downstream quality"; implementation is "a single Python-level pointer assignment" in HuggingFace — but it is a *pretraining* modification ("Our pretraining experiments") — [Source](https://arxiv.org/abs/2606.16825)
- **Tying cross-loop agreement (useful negative signal).** With independent per-layer routers but tied experts, top-1 cross-loop agreement is only 0.087–0.126 (chance 0.031 for 32 experts) in the ablation; tying attention or router raises agreement to 0.7–0.9 but hurts loss — [Source](https://arxiv.org/html/2606.16825v1). So even when weights are literally identical, adjacent layers route differently ~85–90% of the time; one resident tied expert does *not* automatically serve two layers.
- **Cluster-based pruning/merging is lossy.** HC-SMoE "clusters experts post-training using hierarchical clustering, merging redundant experts **without retraining**" — merging necessarily changes the weights and therefore the outputs — [Source](https://aman.ai/primers/ai); cluster-driven expert pruning groups "functionally similar experts within each MoE layer using parameter similarity metrics, followed by global cluster pruning, which eliminates redundant experts" — [Source](https://arxiv.org/abs/2504.07807)
- **Expert substitution is explicitly approximate.** SMoE "substitutes low-score activated experts with resident experts of similar score" and MoE-CORE's substitution "does not assert functional equivalence from score proximity"; the PSR paper measures that routing-changing methods increase next-token loss ≥0.067 nats — [Source](https://arxiv.org/html/2610.34721); [Source](https://arxiv.org/html/2610.01950v1); [Source](https://neurips.cc/virtual/2026/156996)
- **Cache-aware routing is also not bit-exact.** Cache-Prior adds a bonus λΔ̄ to resident experts' logits; greedy generation flips 16–25% of BBH items relative to exact routing under each configuration — [Source](https://arxiv.org/html/2610.34721)
- **Determinism caveat even without timing.** With physical-cache-conditioned routing + async prefetch, varying only "prefetch copies in flight" from 1 to 2 to 4 moves perplexity 8.755 → 8.674 → 8.627, and repeated runs on the same GPU differ up to 0.054; the PSR "logical cache" makes routing a deterministic function of token history and removes this dependence, but still changes the model (it is a biased router) — [Source](https://arxiv.org/html/2610.34721)

### Inferences
- Exact expert reuse across layers requires *bit-identical tensors*. The papers that create such identity do so by tying at training time; there is no evidence that independently trained experts in Qwen3.8-Flash-Next or Nemotron-Lightning are bit-identical. A cheap offline scan (hash all 512×48 / 128×23 expert tensors) is therefore a high-value, near-zero-cost falsification test.
- Near-identical (but not bit-identical) experts cannot be substituted under the bit-exact requirement, so similarity/dedup research (HC-SMoE, Cluster-Driven Pruning, DeRS) is disqualified regardless of its measured quality retention.
- The PSR "logical cache" insight is still valuable *mechanically*: if Veystrix ever uses a residency-dependent policy, it must be a deterministic function of token history, not physical transfer timing, or token outputs become hardware/load-dependent.

### Gaps
- No published hash/duplicate-tensor audit of any 512-expert-per-layer model; no source reports the fraction of byte-identical experts within or across layers of the target models.
- No source evaluates whether a *lossless delta* representation between highly similar experts (store expert B as A + lossless residual) reduces average SSD bytes; this would preserve exactness if the residual is lossless and B is reconstructed exactly, but it appears unstudied.

## Q4: What do the named prior systems deliver on bit-exactness and bytes/token, and why don't they solve Veystrix's problem?

### Takeaway
The named systems (ExpertFlow, Fiddler, MoE-Infinity, FlashMoE, PracMoE/SeqMoE-class, PagedMoE, PSR) all either (a) reduce *copies* via prediction/caching that Veystrix already tried, or (b) change the model. None reports a bit-exact reduction in physical SSD bytes/token comparable to ZipMoE/SSD-LLaMA.

### Cited Findings
- **MoE-Infinity (2024).** Request-level expert activation tracing capturing "selective activation, group activation, and skewed reuse"; activation-aware cache; reported latency reductions up to 20× and cost >8× in serving — [Source](https://arxiv.org/abs/2401.14361); [Source](https://www.emergentmind.com/papers/2401.14361). Bit-exact (caching only) but a cache policy, already covered by Veystrix's attempts.
- **Fiddler (ICLR'25).** Uses the CPU's *compute* to process experts resident in CPU memory so weights need not move to GPU; 8.2× latency improvement on Quadro RTX 6000 and 10.1× on L4 vs offloading baselines — [Source](https://arxiv.org/abs/2402.07033); [Source](https://openreview.net/pdf?id=WX7lxohjFe). Bit-exact, but a CPU/GPU partition decision, not an SSD-byte reduction; the M4 has no separable CPU/GPU memory bandwidth to exploit in the same way.
- **ExpertFlow (2025).** Adaptive expert prefetching + cache-aware routing + token scheduling; reported GPU memory reduction 93.72% and throughput 9.99× vs a baseline — [Source](https://arxiv.org/abs/2510.26730); [Source](https://alphaxiv.org/abs/2510.26730). The "cache-aware routing" component changes which experts run, so not bit-exact as published; the adaptive-horizon/scheduling components are prediction, already tried.
- **FlashMoE (2026).** ML-based cache replacement combining recency and frequency; beats LRU by 21% and LFU by 51%, translating to 22% and 35% I/O reduction, and beats ARC/LeCaR — [Source](https://arxiv.org/abs/2601.17063); [Source](https://doi.org/10.48550/arxiv.2601.17063). Bit-exact but a cache policy; 22–35% "I/O reduction" is copy count, not physical bytes.
- **FineMoE (EuroSys'26).** Fine-grained expert maps from semantic embeddings and expert trajectories, similarity-aware δ prefetch count, asynchronous map search — [Source](https://arxiv.org/abs/2502.05370); [Source](https://arxiv.org/html/2502.05370v2). Bit-exact (prefetch only) but prediction, already tried.
- **PSR (2026).** Deterministic *logical* cache + bounded prefetch-steered routing; 10.7 ms/token at 50% residency on OLMoE (2.3× vs exact LRU) and 1.9× on Moonlight — [Source](https://arxiv.org/html/2610.34721). NOT bit-exact: routing bias changes outputs (mean benchmark deltas near zero but 16–25% of BBH items flip) — [Source](https://arxiv.org/html/2610.34721)
- **PagedMoE (2026).** 1.33× vs independent precision objects at 2.5 bits — NOT bit-exact — [Source](https://arxiv.org/abs/2611.03173)
- **Edge0 (2026), Mac-specific.** On a 16 GB MacBook M2 with an 18.4 GiB int4 checkpoint: on-demand 4.8/3.5/1.8 tok/s → prerouter 8.6/6.4/3.3 tok/s at K=2/4/8 (+80–84%); "both arms move within a few percent of the same bytes per step" (e.g. 125.1 vs 126.9 MiB at K=8), i.e. **the gain is latency hiding, not byte reduction** — [Source](https://arxiv.org/html/2609.18063v2). NOT bit-exact overall (prerouter replaces routing; int4 + recovery LoRA); its executor paths alone are element-wise verified to ≈0.24% bf16 kernel residual — [Source](https://arxiv.org/abs/2609.18063)
- **vllm-metal MoE offload (Mac/MLX).** MRU cache in unified memory; "outputs are identical to the fully resident model" — a clean bit-exact baseline, but it is a cache and explicitly warns every MoE layer waits for routing before reading experts — [Source](https://docs.vllm.ai/projects/vllm-metal/en/latest/moe_offload)
- **SSD-offloading energy result.** Offloading MoE weights to SSD consumes ~4.9× more energy per token for DeepSeek-R1 vs resident; relevant to the "miracle" framing because the byte-reduction techniques also reduce energy — [Source](https://arxiv.org/abs/2508.06978); [Source](https://arxiv.org/pdf/2508.06978v1)

### Inferences
- The literature's headline speedups are mostly "hide the read" or "change the expert," not "read fewer bytes." Veystrix has already exhausted the first two categories. This is why lossless compression is the only remaining novel category.
- Edge0's Mac result is the closest hardware analogue and is instructive: a +80–84% gain came from moving the *same bytes* off the critical path, with only ~1 core of 8 and ≤12% disk utilization used. Veystrix's 52–68% I/O wait at 2.3–7 tok/s suggests a similar "latency, not bandwidth" component may still exist, but Veystrix reports SSD saturated under worker tuning, so the overlap lever is weaker here.

### Gaps
- No paper measures a bit-exact bytes/token reduction on an Apple M4 with a ~3 GB/s SSD for these specific model sizes.
- "PracMoE" and "SeqMoE" could not be located as distinct 2024–2026 papers in the searches performed; these names may refer to practitioner write-ups or be misremembered. No claims are made about them.

## Q5: What is the realistic ceiling on 16 GB M4, and what falsifiable experiments should be run first?

### Takeaway
Bit-exact byte reduction of ~30% is well-supported and cheap to test; the larger targets (15+ tok/s Nemotron) are arithmetically unreachable from byte reduction alone at 3 GB/s and would require serving fewer distinct experts, which is forbidden. The recommended program is: (1) offline compression-ratio + duplicate-hash audit, (2) sub-expert SM/E-chunk cache A/B, (3) oracle eviction study to bound any remaining bit-exact headroom.

### Cited Findings
- ZipMoE's compressed sizes (ZSTD 68%, LZ4HC 74%, entropy floor ~66%) and SSD-LLaMA's 33.2% traffic reduction bound the plausible bit-exact byte saving — [Source](https://arxiv.org/html/2601.21198v1); [Source](https://arxiv.org/html/2609.18110v1)
- The 2.1× eviction transfer reduction is 96% recoverable with 16 future tokens but only 27% with past-only frequency — [Source](https://neurips.cc/virtual/2026/156996)
- Adjacent-token expert-set overlap is ~25%, and prerouter gains come from load-time hiding at constant byte count — [Source](https://arxiv.org/html/2609.18063v2)
- Even a 22 GiB VRAM cache yields only 80.1% hit rate on DeepSeek with the SSD-LLaMA system on an RTX 5090; Veystrix's 2–4 GB pool is far below that — [Source](https://arxiv.org/html/2609.18110v1)
- The M4-specific MLX/vllm-metal offload path is bit-exact but cache-bound — [Source](https://docs.vllm.ai/projects/vllm-metal/en/latest/moe_offload)

### Inferences
- Arithmetic check (inference, not a sourced fact): 436 MB/token at 3 GB/s = ~145 ms I/O floor even with zero compute; a 33% byte cut gives ~97 ms, still above the ~67 ms/token needed for 15 tok/s. For Qwen, 408 MB → ~285 MB gives ~95 ms floor vs ~200 ms needed for 5 tok/s, so 5 tok/s is plausible if compute and I/O overlap well and the cache removes additional bytes. **Budget expectation: compression helps Qwen reach the 5 tok/s tier; it cannot by itself deliver Nemotron 15 tok/s.**
- The falsifiable test set below is ordered by cost/benefit; the first two are offline and do not touch engine code.

**Proposed falsifiable experiments (derived from the cited mechanisms):**
1. **Offline entropy + duplicate audit (hours).** For both model packs: (a) histogram exponent-symbol entropy/support per tensor; ZSTD/LZ4HC size vs raw; (b) SHA-256 every (layer, expert) gate/up/down tensor and count exact duplicates within/b across layers. Pass: compressed size ≤0.75× raw, or ≥1% byte-identical experts.
2. **Bit-exactness gate (always run first).** For any candidate technique, require byte-identical reconstructed expert tensors and identical greedy token IDs over 500 tokens on 20 prompts; reject on any mismatch.
3. **SM/E-chunk cache A/B (ZipMoE-derived).** Fix cache GiB and routing trace; compare whole-expert cache vs split SM/E pools with 4-thread CPU decompression. Measure bytes/token and tok/s. Pass: ≥25% fewer SSD bytes with identical tokens.
4. **Oracle eviction upper bound.** Replay a recorded 512-token routing trace at 2 GB and 4 GB caches; compute Bélabé/farthest-future transfer count and the 16-token-lookahead and past-only-frequency approximations. This directly measures whether any bit-exact cache-policy headroom remains above Veystrix's S3-FIFO result.
5. **Co-selection-based physical packing (only if #4 leaves headroom).** Fit the co-selection table from ≤4,096 tokens (r>0.93 achievable per the paper) and order expert records in the compressed pack by co-activation; measure random-read count and bytes/token. Given Veystrix's prior null result on packing, treat as low priority.

### Gaps
- No source provides the target models' compressed-size ratios or duplicate-expert counts; experiment #1 must supply these before any projection can be trusted.
- No source combines all three bit-exact levers (lossless compression + sub-expert cache + oracle eviction) and reports the joint bytes/token; the joint gain may be sub-additive.
- The energy argument (4.9× from SSD offload) is from a different model/hardware; no M4 energy numbers available.
